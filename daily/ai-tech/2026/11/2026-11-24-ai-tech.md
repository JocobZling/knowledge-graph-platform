2. **GitHub Issue状态与仓库看板（11/23，4/5）：** Backlog/Todo/In progress/In review/Done/Not planned/Duplicate七种状态，API及MCP可读写，Agent指派触发状态自动流转。官方：https://github.blog/changelog/2026-11-23-issue-statuses-and-repository-boards-are-in-public-preview/

4. **Bitdefender发现Agent配置投毒（11/17，5/5）：** 22个恶意GitHub链接利用AGENTS.md/CLAUDE.md、session hooks及MCP配置诱导执行或自动触发恶意代码。这与11/22报道的PyPI发行包投毒是不同攻击路径。原始研究：https://www.bitdefender.com/en-us/blog/labs/how-ai-agents-become-new-targets-in-github-malware-campaign

## 2. AI / 大模型 Top News

### 2.1 Shirudo：运行中Linux系统的临时防护
**OpenAI/Cisco｜2026-11-23｜新颖度5/5｜开源发布。** 官方：https://openai.com/index/introducing-shirudo/；项目：https://github.com/shirudo-dev/shirudo

Shirudo以eBPF在Linux系统中加载有针对性的防护程序（shield）。防护可先观察影响，再由操作员审批后强制执行；shield有签名验证、Linux eBPF verifier检查和TPM相关证明机制。受控测试中，Codex生成的shield在Elasticsearch服务运行期间阻断Java4Shell攻击尝试，未要求JVM重启。**这是特定演示，不等于已证明对所有漏洞有效，更不能替代正式补丁。**

金融实践：可以借鉴“建议→沙箱验证→人工审批→部署→状态证明→撤销”的闭环，但不在银行生产主机直接试装。需确认内核版本、eBPF权限、系统性能、兼容性和安全审批。

### 2.2 GitHub Issue状态成为Agent可操作的工作流对象
**GitHub｜2026-11-23｜新颖度4/5｜Public Preview。** 官方：https://github.blog/changelog/2026-11-23-issue-statuses-and-repository-boards-are-in-public-preview/

新增Backlog、Todo、In progress、In review、Done、Not planned、Duplicate七种状态，Issue状态可通过GraphQL、REST及MCP访问；指派Agent自动进入In progress，关联PR和审查状态可推动流转。仓库看板支持按状态分组。**新意是Agent与人共享显式任务状态，并非仅新增界面标签。** 对测试经理助手的任务创建、文档生成、失败重试，应有独立持久化任务状态和人工复核节点。

### 2.3 GitHub Secret Scanning减少Slack Webhook误报
**GitHub｜2026-11-23｜新颖度3/5｜检测器改进。** 官方：https://github.blog/changelog/2026-11-23-secret-scanning-reduces-false-positives-for-slack/

对`slack_incoming_webhook_url`采用更精确的URL格式判断，排除不符合Slack incoming-webhook URL格式的字符串。官方没有给出误报率变化或漏报率数据。日志脱敏检测平台可以借鉴“规则前置格式校验→AI精筛→人工复核”的分层机制，但要同时测漏报，不能单独追求误报下降。

### 2.4 Bitdefender：恶意仓库指令与Hook攻击Coding Agent
**Bitdefender Labs｜2026-11-17｜新颖度5/5｜独立安全调查（回溯7天）。** 原始研究：https://www.bitdefender.com/en-us/blog/labs/how-ai-agents-become-new-targets-in-github-malware-campaign

研究者识别22个恶意GitHub链接，利用AGENTS.md、CLAUDE.md、会话启动Hook、MCP配置、编辑器任务等路径，使Agent受诱导执行恶意脚本，或在仓库被信任后由配置直接触发。恶意载荷可能窃取CI凭据、SSH密钥、云Token，并试图污染其他仓库的Agent配置。**与此前PyPI包启动钩子事件不同：本次入口是仓库级指令与开发工具配置。** 建议将第三方仓库中的指令文件与可执行Hook视为不可信输入。

## 3. 科技行业动态

**3.1 AI辅助防护延伸到操作系统运行时（11/23）。** OpenAI/Cisco将AI生成的临时安全防护与eBPF、签名验证和人工审批结合。实际推广仍取决于内核兼容、性能及回滚安全；目前不能以单一演示宣称生产普适。来源：https://openai.com/index/introducing-shirudo/

**3.2 开发工具信任链面临新攻击面（11/17，近日再获关注）。** Bitdefender调查说明仓库中的Agent指令、Hook、MCP配置都可能影响执行；这不同于普通代码依赖投毒。安全准入需要检查“谁能修改指令文件、谁能运行脚本、是否继承开发者凭据”。来源：https://www.bitdefender.com/en-us/blog/labs/how-ai-agents-become-new-targets-in-github-malware-campaign

## 5. Agent Ecosystem

**5.1 Agent / Skill / MCP：** 将仓库指令、Skill、MCP配置和Hook都纳入能力准入，禁止第三方仓库自动执行未经审查的初始化命令。Skill描述是业务提示，不是系统权限来源。

**5.2 Workflow / 编排：** 借鉴GitHub显式Issue状态，业务任务至少区分QUEUED、RUNNING、WAITING_APPROVAL、SUCCEEDED、FAILED、CANCELLED；模型回答“已完成”不得直接写成业务成功，须回读Java服务端状态。任务重试应绑定attempt_id与幂等键。

**5.3 Browser Agent / Tool Calling / 安全：** 浏览器操作、Shell Hook、MCP工具执行均属于可产生副作用的执行面。运行时保护不替代最小权限、审批、网络隔离和审计；安全检查失败时高风险操作默认拒绝。

**本周最值得体验：** 在完全脱敏的Mock仓库演练“恶意AGENTS.md要求执行setup脚本”，检查Coding Agent是否拒绝未经授权的自动执行（不要放置真实恶意代码）。

**Agent 实践启发：** Agent的工具权限与任务状态必须由宿主/后端约束；模型不能自行授予权限或宣告业务成功。

## 6. 开源推荐

**[shirudo-dev/shirudo](https://github.com/shirudo-dev/shirudo)**｜**224 Stars（2026-11-24 GitHub网页快照）**｜**BSD-2-Clause；BPF程序BSD/GPL双许可证**。核心能力：eBPF临时防护、签名校验、部署状态验证与回滚研究。推荐理由：提供“AI提出防护→验证→人审→执行”的新型安全工程案例。**注意：** 项目处于早期，Stars快速变化；不建议未经内核、兼容性和安全审批直接部署到银行服务器。

## 7. 企业实践

**OpenAI + Cisco：** 以Linux运行时为执行面，使用Codex生成有针对性的shield，在受控Elasticsearch/Java4Shell演示中阻断攻击尝试，且应用继续运行。效果仅为该测试场景的成功验证，未公布可外推的生产故障率、性能损耗或覆盖率。可借鉴：将AI生成的高风险操作放在“自动建议—独立验证—人工审批—审计证明”链路内。

## 9. 今日实战

**测试经理智能助手的任务状态验收**（全为Mock数据）：

```json
{
  "task_id": "mock-task-001",
  "capability": "create_test_task",
  "status": "WAITING_APPROVAL",
  "attempt_id": 1,
  "approved": false,
  "business_verified": false
}
```

用例：未批准不得执行；批准后只执行一次；重试不得重复创建；工具超时不等于成功；模型声称完成但Java状态仍RUNNING时，UI只能显示运行中。

## 10. Today Worth Thinking

**当Agent已经生成“安全修复方案”或“任务已创建”的回答，真正能够证明执行安全、结果正确和状态可追溯的证据在哪里？** 企业Agent的验收需要后端状态、权限记录、执行证据与独立回读，而非模型自述。

## 11. 30分钟 Action

- **0—10分钟：** 为一个Mock任务接口定义QUEUED、RUNNING、WAITING_APPROVAL、SUCCEEDED、FAILED五种状态与合法转换。
- **10—20分钟：** 编写未审批、重复提交、超时、重试、跨用户查询五条负向用例。
- **20—30分钟：** 用Java Mock验证任务状态、幂等键、用户归属和结果回读，形成PASS/FAIL表。

**完成标准：** 未授权写入0次，重复提交仅产生一次业务效果，模型不能伪造成功状态。

## 13. 我的备注：金融测试、Agent Testing与智能测试平台

**测试经理智能助手：** 继续保障Vue3 iframe、Dify工作流、DeepSeek V4、Java Capability API和PostgreSQL的一期交付。未来扩展任务创建、文档生成时，先沉淀统一Task状态机、attempt_id、幂等键与人工审批，避免在Prompt里维护真实状态。探索工程再考虑不同Harness和MCP适配，不因Shirudo发布直接换框架。

**日志脱敏检测平台：** 已有report/server两级状态及AI独立状态，继续扫描与失败重扫要绑定执行轮次；对AI精筛误报优化同时评估漏报，不能只追求更少告警。Shirudo仅作为运行时防护研究线索，不与日志脱敏产品功能混同。

**Agent Testing：** 新增仓库指令注入阻断率、Hook执行审计覆盖率、任务状态回读一致率、幂等成功率、人工审批绕过率和规则误报/漏报联合指标。

**今日结论：** 从模型生成建议到系统执行动作，中间必须有可审查、可拒绝、可回滚、可证明的可信执行边界。
