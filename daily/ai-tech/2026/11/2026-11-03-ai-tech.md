### 2.1 OpenAI LifeVal：评测从知识问答走向真实生活任务
**主体：OpenAI｜发布时间：2026-11-02｜重要程度：高｜新颖度：5/5｜性质：研究基准**  
**官方：** https://openai.com/index/lifeval/

OpenAI 发布 LifeVal，用于衡量个人助手在找托育、办理公共事务、家庭预算、购物、教育和照护等任务中的表现。任务选取参考美国及跨国时间使用研究，并结合 **3,995 名受访者**的代表性调查。研究展示的若干单任务高分是示例任务的表现，不应被误读为总体成功率，更不能推断金融场景的可靠性。

**实质变化：** 评测对象从回答文本扩展到任务分解、网页/电脑操作、连接器调用和用户最终目标。  
**对 Agent Testing 的启发：** 建议将智能测试助手的验收从“回答是否通顺”拆成意图正确、工具路径正确、事实正确、权限合规和业务结果可回读五个门禁；涉及写入时增加副作用核验。

### 2.2 香港金管局 Project SAGE：代理式金融治理进入专项探索
**主体：香港金融管理局（HKMA）｜发布时间：2026-11-02｜重要程度：高｜新颖度：5/5｜性质：监管与产业倡议**  
**官方：** https://www.hkma.gov.hk/eng/news-and-media/press-releases/2026/11/20261102-4/

SAGE 全称为 **Securing Agentic Finance with Governance and Enablement**。四大工作方向是：①B2C/B2B/M2M场景探索；②Agent 身份及委托权限验证（Know Your Agent）；③跨机构互操作标准；④法律责任、治理与消费者保护。同步设立 Agentic Finance Expert Group；金管局还公布银行使用 Agentic AI 的监管讨论文件。

### 2.3 GitHub Actions：公共仓库 pull_request_target 默认阻断改至12月2日
**主体：GitHub｜公告更新：2026-11-02｜重要程度：高｜新颖度：5/5｜性质：安全策略变更预告**  
**官方：** https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2/

GitHub 明确：从 **2026-12-02** 起，公共仓库的 pull_request_target 触发器默认被阻断，除非适用的 Actions 事件策略明确放行。此前预定日期为11月2日，现已延期。**两次临时阻断窗口：11月9日、16日 16:00—18:00 UTC**。私有和内部仓库不受此默认策略影响；GitHub Enterprise Server 也不在此次范围内。

**原因：** pull_request_target 在基准仓库权限上下文运行，若执行来自 fork 的不可信代码，可能泄露机密或污染流水线。  
**对自动化的启发：** 对外部贡献者触发的 Agent CI，分离只读分析与有凭据写入；使用 Actions Insights 检查将受影响的工作流，而非直接放开所有事件。  
**本仓库核验：** 已检查 knowledge-graph-platform 的三个 .github/workflows 文件，当前未发现 pull_request_target 触发器；这不代表其他仓库也不受影响。

### 2.4 OpenAI Pando：为 Coding Agent 并行开发重构 Git 后端
**主体：OpenAI｜发布时间：2026-11-02｜重要程度：高｜新颖度：5/5｜性质：工程实践披露**  
**官方：** https://openai.com/index/scaling-git-at-openai/

OpenAI 介绍内部 Pando Git 后端。它保持 Git 协议与客户端兼容，针对 Agent 产生的大量并行分支、push、fetch 与 CI 克隆进行扩展。采用按分支独立协调、对象存储和 packfile 复用；生产环境 **中位数 push 延迟降低近5倍**，日分发 Git 数据接近 **1PB**。其权衡是提供按引用的因果一致性，而非所有分支的全局同一时刻快照。

**实质变化：** AI 写代码提高的不只是生成速度，也改变版本控制和 CI 的吞吐需求。  
**对测试平台的启发：** 需要把“Agent 提交完成”与“CI 获取到了正确 commit、执行了正确版本”分开验证；注意并行提交、重试、冲突与回读一致性。**边界：** Pando 是内部系统，不能宣称已作为独立开源服务发布。

## 5. Agent Ecosystem（3条）

### 5.1 Agent / MCP / Tool Calling：Know Your Agent 不等于知道用户是谁
金融 Agent 至少应分离三种主体：发起业务的真实用户、代理执行的 Agent/服务身份、实际落地操作的业务服务身份。MCP Tool Catalog 可以描述工具，却不能代替业务授权。建议每次执行保存 user_id、agent_id、capability_id、delegation_scope、policy_version、trace_id，敏感写入还要保存 approval_digest 与撤销检查。

### 5.2 Workflow / Skill：不可信代码不能搭乘高权限自动化
GitHub 的 pull_request_target 调整说明：Agent/Skill 即使只是“辅助 CI”，仍可能通过 fork、依赖或工具输出触达凭据。设计上应区分不可信内容解析、只读分析、人工批准、受控写入四个阶段。工作流策略必须由平台强制，不能由模型输出“我已获得授权”替代。

### 5.3 Browser Agent / 评估：从界面动作走向真实目标完成
LifeVal 的任务导向和 Pando 的工程回读共同提醒：Browser Agent 的点击成功、页面截图、工具成功响应都只是中间证据。应把页面状态、接口响应、数据库事实、用户权限及最终目标分开核验。对纯查询场景不必强行增加写入流程。

**本周最值得体验：** 在 Dify 中构造“工具返回 SUCCESS，但真实查询范围错误”的 Mock 场景，检查独立验证器是否拒绝该回答。  
**Agent 实践启发：** 身份委托与业务结果是两条不同的可信链；权限正确不能保证事实正确，事实正确也不能弥补越权。

## 9. 今日实战（1条）

### 给测试经理智能助手增加 Agent 身份与查询事实双重校验
沿用 **Vue3 iframe → Dify Chatflow → DeepSeek V4 → Java Capability API → PostgreSQL** 的轻量架构，不迁移编排框架。

建议 Java 接口在身份与权限校验后返回：
~~~json
{
  "trace_id": "demo-20261103-01",
  "user_scope": "AUTHORIZED_SYSTEMS",
  "capability_id": "query_execution_summary",
  "metric_version": "v1",
  "query_period": "2026-11",
  "execution_status": "SUCCESS",
  "verified": true
}
~~~
以上仅为契约样例，不是实测数据。关键是 **user_scope 由 Java 从可信登录态推导**，不接受模型自行声明；verified 由独立校验程序给出。对于系统负责人查询，额外校验负责人关系的生效时间。

## 10. Today Worth Thinking

> 如果 Agent 使用合法工具、身份也通过了校验，但回答引用了上一执行轮次的缓存结果，任务算成功吗？

不算。建议把“合法授权”“事实时效”“执行轮次”“结果回读”分成独立的验收维度；权限通过不是事实正确的充分条件。

## 11. 30分钟 Action

**目标：为 Dify 查询工作流补齐六条“身份 × 事实时效”Golden Set。**

| 用时 | 动作 | 产出 |
|---|---|---|
| 0—10 分钟 | 准备授权用户、越权系统、过期缓存、历史负责人等 Mock 数据 | 6条基准样例 |
| 10—20 分钟 | 调用受控 Java Mock API，记录 trace_id、授权决策和数据版本 | 执行轨迹 |
| 20—30 分钟 | 独立核对查询事实、权限和版本，生成 PASS/FAIL | 回归结果表 |

| Case | 场景 | 预期 |
|---|---|---|
| A01 | 当前授权系统执行统计 | VERIFIED |
| A02 | 未授权系统统计 | DENY_SCOPE |
| A03 | 模型伪造 user_scope=ALL | IGNORE_MODEL_SCOPE |
| A04 | 缓存结果属于上个统计周期 | STALE_FACT |
| A05 | 查询历史负责人但返回当前负责人 | RELATION_TIME_MISMATCH |
| A06 | Tool 返回 SUCCESS 但事实与数据库不符 | FACT_MISMATCH |

**完成标准：** 六条用例均有预期与实际结果，越权不泄露数据，陈旧事实不能被标记为 VERIFIED。

## 13. 我的备注：金融测试、Agent Testing 与智能测试平台

### 测试经理智能助手
**优先级建议：高。** 一期继续聚焦执行统计与负责人查询。将 user_id / agent_id / capability_id / metric_version / trace_id 作为轻量追踪契约；Java 后端独立授权，PG 事实回读。先完成 Golden Set，再讨论跨 Agent 协作或模型路由。香港金管局 SAGE 的“Agent 身份与委托”方向值得提前纳入未来写操作设计，但不是一期必须建设的复杂基础设施。

### 日志脱敏检测平台
**优先级建议：中高。** 继续扫描与失败重扫需绑定 report_id、server_id、execution_epoch、event_id；旧轮次回调不覆盖新轮次。AI 精筛只辅助判定，日志文本不能成为授权指令。结合 GitHub CI 安全变化，检查扫描流水线的触发事件、密钥暴露和外部代码执行风险。

### Agent Testing 建议指标
| 指标 | 定义 |
|---|---|
| Verified Task Success | 事实、权限、时效和执行证据同时通过的任务比例 |
| Delegation Integrity | Agent 是否仅在委托权限与有效期内操作 |
| Fact Freshness Accuracy | 查询结果是否匹配统计周期和关系生效时间 |
| Claim–Effect Consistency | Agent 声明与工具轨迹/业务事实是否一致 |
| CI Trigger Exposure | 高权限流水线是否可能被不可信 PR 触发 |
| Cost per Verified Task | 每个真实验收通过任务的总推理/重试/复核成本 |

**今日结论：** 可信 Agent 的建设重点不是先让它获得更多工具，而是先明确谁授权、数据何时有效、任务是否真实完成，以及出了问题如何追溯。
