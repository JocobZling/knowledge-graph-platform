### 2.1 Hebbia金融研究Agent：引用可追溯与PPT要求遵循
**主体：OpenAI / Hebbia｜发布：2026-11-20｜新颖度：5/5（新企业实测案例）**  
官方：https://openai.com/business/customer-stories/hebbia/

Hebbia Matrix在金融研究中将答案链接至源文档和对应摘录。Hebbia使用相同金融研究案例与专家审定标准，对2026年8—9月的GPT-6 Astra预发布构建进行测试。其披露：必需来源类型覆盖较最佳对照高13.6个百分点；被引用摘录中99.5%与问题相关；满足97.9%的适用演示要求，较最佳对照高14.4个百分点。案例中提到约2000份文件的并购尽调**是假设场景**，不是已证实的实际银行项目规模。

**价值：** 对测试报告、需求分析、领导汇报等文档型Agent，建立“每项结论→源文档/数据库记录→引用片段→最终输出”的追溯链，并将模板符合度独立评分。**限制：** 单企业案例与厂商发布，不能直接外推至金融内网DeepSeek V4的表现。

## 5. Agent Ecosystem

**5.1 Agent / Skill / MCP：能力输出必须可验证。** 建议Capability Registry为每项能力补充evidence_policy、output_schema和golden_set_version。Agent选择正确Skill只是第一步，执行结果还应能由可信业务接口回读。

**5.2 Workflow / Tool Calling：证据链与结果链分离。** 工具调用日志证明“调用过什么”，不证明“业务事实正确”。需要保留可信查询结果ID、授权范围、来源版本和最终答案映射；敏感字段按最小化原则脱敏。

**5.3 Browser Agent / 安全治理：** 浏览器截图或模型口述不能替代真实状态验证。对写操作采用审批→执行→回读；对报告生成采用引用→格式校验→人工复核。

**本周最值得体验：** 为一个测试统计问答增加来源记录ID和可点击的脱敏证据字段。  
**Agent 实践启发：** 把“回答正确率”“引用正确率”“格式遵循率”拆开评估，才能定位模型、检索、工具或模板层的问题。

## 6. 开源推荐

**anchore/syft**：https://github.com/anchore/syft  
**Stars：9,950（2026-11-23 GitHub API快照）；License：Apache-2.0。**  
核心能力：从容器镜像、目录及文件系统生成SBOM（软件物料清单）。推荐理由：为Agent Harness、MCP Server、Skill运行容器建立依赖清单，支持后续恶意包公告的版本匹配。Syft生成SBOM不等于自动判定所有依赖安全；还需配合漏洞数据库、恶意包公告和人工准入。内网引入前应完成制品与依赖审核。

## 7. 企业实践

**企业：Hebbia；做法：** 在金融研究任务中将源文档检索、引用摘录和原生PPT输出纳入统一流程，使用同一批案例和专家审定标准比较模型。**效果：** 引用相关性99.5%，演示适用要求满足率97.9%，均为其自身测试。**可借鉴点：** 金融Agent必须保留来源、验证报告模板要求，并将引用证据与最终交付物联动。官方案例没有披露适用于银行内网的部署条件、统一成本或真实客户业务收益。

## 8. 今日工具推荐

**Syft：** 在获准的测试容器上生成SBOM，形成项目名称、依赖、版本、许可证与镜像摘要清单。示例：`syft dir:. -o cyclonedx-json > sbom.json`。仅在可信测试目录执行；SBOM文件本身可能泄露内部组件名称，应按内部资产管理要求保存。

## 9. 今日实战

为测试经理助手的“本月执行情况”问答增加三段式验收：
1. **事实：** 业务Java API返回的统计值与模型答案一致。
2. **证据：** 答案关联查询时间、权限范围、查询结果ID，不暴露其他用户明细。
3. **格式：** 日期范围、统计口径、空结果提示符合约定模板。

Mock样例：`{"question":"我本月执行多少条？","expected_count":125,"source_id":"mock-run-001","authorized":true}`。其中125为虚构数据，不是用户真实工作统计。

## 10. Today Worth Thinking

**“Agent说出了正确数字”与“Agent能够证明数字从何而来”，哪个才是金融业务的验收标准？** 对需要审计与复核的业务，两者缺一不可。模型生成的引用字符串不能自行证明真实性，必须由可信服务端验证其存在与归属。

## 11. 30分钟 Action

- 0—10分钟：选取一个Mock统计API，确定正确值、查询时间和来源ID。
- 10—20分钟：让Agent生成答案并返回source_id，后端回读验证结果。
- 20—30分钟：增加“错误来源ID、跨用户来源ID、空结果”三条负向用例。

**完成标准：** 事实、来源、权限、格式四类断言独立输出PASS/FAIL；错误或越权来源不得通过。

## 13. 我的备注：金融测试、Agent Testing与智能测试平台

**测试经理智能助手：** 一期继续优先打通Dify Chatflow、Java Capability API、PG与iframe入口，不增加重型编排框架。为执行统计和负责人查询统一返回`result_id`、`data_as_of`、`scope`和`trace_id`，由后端校验权限和数据真实性。探索工程再评估Capability Registry及Skill自动发现。

**日志脱敏检测平台：** 保持规则与AI状态独立。AI精筛的真实风险/误报判定应能关联原扫描任务、服务器、规则版本、行号及脱敏上下文，避免只保留模型结论；已有500条样本可增加证据定位正确率。

**Agent Testing：** 在已有工具选择准确率、越权阻断率之外，增加引用存在率、引用归属正确率、业务事实一致率、格式遵循率和SBOM覆盖率。对外网模型案例仅借鉴评估方法，不直接迁移内部敏感数据。

**结论：** 企业Agent从“能答”迈向“可验收”，关键在于可信业务事实、证据追溯与独立质量门禁。
