## 1. 今日摘要

本期四个观察点：**①** AWS 10月30日介绍 AgentCore Runtime Session endpoints，允许通过受认证的会话URL实时预览 Coding Agent 修改中的网页；**②** Google 10月29日发布 A2UI 与 CopilotKit 的集成教程，Agent 可输出受信组件目录中的声明式 UI，而非自由生成可执行前端代码；**③** Google 10月28日展示 Agents CLI 的生成—评分—比较—聚类—优化评测循环；**④** Liquid AI 10月27日推出六款约2B参数的LFM3开放权重多模态/决策模型，其中文本模型支持256K上下文。

**今日判断：** Agent产品的下一个工程增量不只是模型能力，而是把**业务数据、UI组件、执行权限、回归评测和成本**连接成可核验的闭环。对金融内网，应优先复用已有Java API和Vue3组件，不因外部框架更新而更换一期架构。

## 2. AI / 大模型 Top News（4条）

### 2.1 AWS AgentCore：Coding Agent修改网页时可受控实时预览

**主体/日期：AWS，2026-10-30；新颖度5/5；性质：技术公告与可运行示例，并非宣称整个产品当天GA。**  
**官方来源：** [AWS原文](https://aws.amazon.com/blogs/machine-learning/preview-web-apps-live-as-your-coding-agent-builds-them-with-amazon-bedrock-agentcore-runtime/)

AgentCore Runtime每个会话运行在隔离microVM中。Session endpoints把经认证的URL映射到会话内允许的端口，转发HTTP、SSE和WebSocket，因而可在Coding Agent修改Vite网页时实时查看结果。允许端口由服务端配置；未授权端口与无凭据请求被拒绝。会话URL不是长期生产托管地址，官方建议正式应用另行部署。

**关键边界：** URL可访问不等于已授权，调用仍需IAM SigV4或JWT；会话端点通过公共HTTPS访问，示例不支持入站PrivateLink；网页和Agent位于同一会话，必须限制执行角色权限。**对金融测试：** 借鉴“边改边看+独立断言”，但不将该云端方案误认为可直接在完全离线内网落地。可在本地Vue3开发环境模拟同样的预览—验证循环。

### 2.2 Google A2UI × CopilotKit：对话结果变成受控交互组件

**主体/日期：Google A2UI团队与CopilotKit，2026-10-29；新颖度5/5；性质：官方技术集成教程。**  
**官方来源：** [Google Developers Blog](https://developers.googleblog.com/en/build-generative-ui-apps-with-a2ui-copilotkit-agents/)

A2UI以声明式数据表达UI意图，由前端受信组件目录渲染。Google文章介绍其通过AG-UI传输事件，并由CopilotKit连接Google ADK、LangChain、Strands等Agent后端；还提到Vue社区渲染器。相较让模型直接输出HTML/JS，这种方式可限制模型只能组合事先注册的组件。组件内的按钮可回传动作及绑定字段，形成双向交互。

**工程边界：** A2UI结构合法不代表业务参数可信，组件目录校验之外，Java API仍须进行权限、参数、写入审批与幂等验证。Vue支持应核实对应渲染器的成熟度与维护状态。

**测试经理助手启发：** 一期只需把执行统计结果渲染为“指标卡+明细表”，负责人查询渲染为“人员关系卡”；无需立即引入整套A2UI框架。后续若场景增多，可参考受控组件协议而非让模型直接生成前端代码。

### 2.3 Google Agents CLI：Agent质量优化成为可重复的回归流程

**主体/日期：Google，2026-10-28；新颖度5/5；性质：官方技术实践。**  
**官方来源：** [Agents CLI评测教程](https://developers.googleblog.com/en/hill-climbing-agent-quality-with-agents-cli-evaluation/)

文章展示 `eval generate` 生成轨迹、`eval grade` 评分、`eval compare` 对比版本、`eval analyze` 聚类失败、`eval optimize` 优化提示词的闭环。示例使用小型数据集演示：某次不合适的提示词修改使1—5分制均分由4.0下降至2.75。该数据仅为教学示例，不是模型总体基准。

**对Agent Testing：** 每次修改Dify提示词、Tool Schema、上下文保存策略后，固定跑同一套Golden Set；按案例比较，而非只看平均分。业务事实应以数据库/规则断言为准，LLM-as-judge只能辅助评估表达质量。

### 2.4 Liquid AI LFM3：约2B参数的本地多模态/决策模型族

**主体/日期：Liquid AI，2026-10-27；新颖度4/5；性质：新模型族与开放权重发布。**  
**官方来源：** [Liquid AI LFM3发布](https://www.liquid.ai/blog/lfm3)

首批六款约2B参数模型覆盖文本、视觉、音频、Omni和决策任务；文本版LFM3-1.7B标称256K上下文，4-bit权重约1GB，官方提供开放权重及本地推理适配。发布方提供若干Agent/视觉基准结果，但仍需独立复测。

**内网意义：** 小模型可能适合轻量意图分类、日志预筛或本地文档结构化；并不意味着其中文金融术语、复杂Tool Calling或合规要求已经达标。与DeepSeek V4相比，应先用相同脱敏测试集验证准确率、延迟、内存、许可证和离线依赖，避免直接替换主模型。

## 5. Agent Ecosystem（3条）

### 5.1 Agent / Generative UI / Browser Agent：可交互结果不能绕开业务系统

A2UI适合把自然语言结果映射为受控卡片、表格、选择器；Session endpoints适合开发过程中的实时UI验证。二者都不应让模型自行生成拥有任意执行权限的页面代码。建议分层：**Agent输出结构化数据 → 前端组件白名单渲染 → Java校验动作 → 独立数据库回读**。

### 5.2 MCP / Tool Calling / Workflow：大规模工具目录必须在服务端按身份裁剪

10月29日的MoEngage案例表明，约400个私有API不必全部暴露给模型。OpenAPI可作为工具契约，权限策略在服务端过滤可见工具；用户、租户与角色上下文不应成为模型可自行改写的参数。金融测试一期只需少量明确的Capability，未来再考虑统一工具网关。

### 5.3 Skill / Agent Testing / 安全治理：先有可复现失败集，再谈自动优化

Agents CLI的循环提醒我们：提示词改进可能让某类问题变好、另一类问题变差。每次Skill/Prompt/Tool Schema变更，都应绑定版本、固定样本、业务断言与失败分类。LLM评分不能代替权限拒绝、SQL结果、重复副作用等确定性检查。

**本周最值得体验：** 在本地Vue3助手中用固定JSON定义一个“执行统计卡片”，模拟A2UI的受控组件目录；再构造非法组件名、越权系统ID、按钮参数篡改三条负例。

**Agent 实践启发：** 将“生成了可用UI”“通过了权限校验”“业务事实正确”“可审计复现”拆为四个独立验收门禁。

## 7. 企业实践

### MoEngage：约400个私有API变成按权限裁剪的Agent工具

**企业/日期：MoEngage；AWS与企业联合案例，2026-10-29。**  
**来源：** [AWS × MoEngage官方案例](https://aws.amazon.com/blogs/machine-learning/how-moengage-turned-over-400-apis-into-agent-tools-with-agentcore-gateway/)

企业原有约400个REST API，来自25个工程团队、分布于7个AWS区域；案例披露目前通过网关供10个内部Agent使用。方案使用OpenAPI生成工具、Cedar服务端权限策略与私有网络访问；模型不能修改身份上下文，也不能通过客户端过滤替代授权。官方称节省约六个月平台工程工作量，新API接入由数天缩至数小时，属于企业估算，非独立对照实验。

**可借鉴点：** 对已有成熟测试经理平台，优先做“原API→能力契约→权限过滤→Agent调用”，而不是让每个功能单独建设MCP Server。特别注意：`tools/list`可见性过滤与`tools/call`实际执行权限都需要校验。

## 9. 今日实战（1条）

### 为测试经理智能助手增加“受控结果卡片”契约

建议定义后端返回：
```json
{
  "view_type": "execution_summary",
  "schema_version": "v1",
  "query_scope": "AUTHORIZED_SYSTEMS",
  "period": "2026-11",
  "data": {"executed_count": 42},
  "verified": true,
  "trace_id": "demo-trace-001"
}
```

以上为**示例数据，非真实统计**。Vue3仅允许 `execution_summary`、`owner_card`、`error_card` 三种组件。若模型输出未知 `view_type`，统一回退到纯文本错误提示；如请求携带系统ID，Java必须重新按真实登录身份校验，不能信任模型给出的 `query_scope`。写操作一期不开放。

## 10. Today Worth Thinking

> 如果Agent生成了一个漂亮的统计卡片，数据也恰好正确，但它通过未授权系统ID查询得到结果，这次交互是否算成功？

建议分别记录：`ui_schema_valid`、`authorization_passed`、`business_fact_verified`、`trace_complete`。任何权限失败都不能被UI成功或答案正确抵消。

## 11. 30分钟 Action

**目标：完成6条受控UI与业务权限测试，不需要新增框架。**

| 用例 | 输入/场景 | 预期 |
|---|---|---|
| UI01 | 合法execution_summary卡片 | 渲染成功，数据来自受控API |
| UI02 | 未知view_type | 拒绝渲染/安全降级 |
| UI03 | data缺失必填字段 | Schema校验失败 |
| UI04 | 查询未授权系统 | Java返回DENY，不泄露数据 |
| UI05 | Agent修改query_scope为ALL | 服务端忽略伪造范围 |
| UI06 | 卡片按钮触发未开放写操作 | 不执行，审计留痕 |

**0—10分钟：** 准备6条Mock JSON；**10—20分钟：** 通过Postman或前端本地Mock执行；**20—30分钟：** 核对Trace、接口返回和数据库副作用。**完成标准：** 六条均有PASS/FAIL及证据；拒绝场景没有真实写入。

## 13. 我的备注：金融测试、Agent Testing与智能测试平台

### 测试经理智能助手

维持已确定的一期路径：**原平台悬浮入口 → 独立Vue3 iframe → Dify Chatflow/DeepSeek V4 → Java Capability API → PostgreSQL → 独立验证**。今天A2UI最值得借鉴的是**受控组件目录**，而不是引入新的复杂前端框架。先做“执行统计卡”“负责人卡”“权限拒绝卡”，并为每张卡绑定接口事实时间和Trace。

### 日志脱敏检测平台

规则命中和AI精筛输出属于不可信业务数据，不能直接决定工具权限。继续扫描与失败重扫仍需保持`execution_epoch`隔离、`event_id`幂等和Report/Server状态聚合一致性。可借鉴实时预览思路，在任务详情中展示服务器状态变化，但最终验收以服务端事实为准。

### Agent Testing

建议形成四个核心指标：**UI Schema有效率、授权阻断率、Golden Set业务准确率、版本回归逃逸率**。当Agent开始输出交互式组件时，还应记录`action_id`、`user_confirmation`、`capability_id`与实际业务副作用。

**今日结论：** Agent UI可以更灵活，业务权限与结果验证必须更确定。
