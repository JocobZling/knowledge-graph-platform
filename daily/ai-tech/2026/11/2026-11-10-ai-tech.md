## 1. 今日摘要

1. **Agent原语分类（AWS，11/06）**：Amazon Quick将Agent工作拆为Trigger（何时/做什么）、Agent（谁）、Capability（如何），区分Tool、Skill、Workflow及学习上下文。价值在于减少每个接口各自定制一套对话。
2. **元数据驱动MCP数据访问（AWS，11/06）**：Amazon北美分拣中心团队通过统一MCP服务与JSON元数据目录接入数据湖，减少每张表重复开发工具代码；权限仍需在可信服务执行。
3. **跨应用Agent授权（AWS/Okta，11/06）**：使用委托令牌、Gateway、Cedar默认拒绝策略和Trace，将用户身份、Agent身份、工具权限分别绑定。
4. **金融企业实践（Taxbit/Greenlight，11/06）**：Taxbit将身份绑定在代码而非模型参数，使用引用、角色校验与线上评估；Greenlight披露多Agent处理安全和风险工单的经验。

**今日判断：** 在成熟业务平台上构建对话助手，优先统一可复用的业务能力和执行契约，不要让每个功能都依赖单独的Prompt与工作流。

## 2. AI/大模型 Top News

### 2.1 Amazon Quick公开Agent原语分类
**主体：AWS｜发布：2026-11-06｜新颖度5/5｜性质：工程设计文章（非新模型发布）**  
官方：https://aws.amazon.com/blogs/machine-learning/taxonomy-of-agentic-primitives-in-amazon-quick/

AWS把Trigger定义为启动条件与任务说明，把Agent定义为执行主体，把Capability作为工具、Skill、Workflow、子Agent的统一抽象。Tool是有类型Schema的原子操作；Skill是可复用但保留判断空间的指导包；Workflow是有固定控制流和异常处理的确定性编排。文章认为模型是可替换的参数，不应与Agent身份混为一谈。

**新增认知：** “查询负责人”和“查询执行量”应首先成为两个稳定Capability；对话入口只负责识别与路由，不必复制两套对话系统。**限制：** 这是AWS的设计分类，不是行业强制标准。

### 2.2 Amazon运营团队使用元数据驱动MCP统一数据湖查询
**主体：AWS/Amazon NASC｜发布：2026-11-06｜新颖度5/5｜性质：内部工程案例**  
官方：https://aws.amazon.com/blogs/machine-learning/serverless-mcp-server-for-ai-agent-data-lake-access-on-amazon-ecs-fargate/

Amazon北美分拣中心团队面对数千数据集与多个Agent重复维护SQL、Schema和权限的难题，建设Agent无关的MCP数据入口。数据集由JSON元数据描述，新增数据集无需逐个新增专用工具代码；统一服务集中实施权限与审计。文章指出旧方案每张表接入常需数天，但没有提供严格可比较的整体效率提升百分比。

**价值：** 对PG/MyBatis平台可先建立系统、负责人、执行统计的Capability Registry与Schema Catalog；由Java做参数白名单、SQL模板和权限控制，不应直接开放任意LLM SQL执行。**限制：** 云端ECS/Fargate方案不等于可直接部署在银行隔离内网。

### 2.3 Okta Cross App Access + AgentCore：委托授权跨Agent统一治理
**主体：AWS/Okta｜发布：2026-11-06｜新颖度5/5｜性质：参考架构与验证实验**  
官方Part 1：https://aws.amazon.com/blogs/machine-learning/govern-ai-agent-access-with-okta-cross-app-access-and-amazon-bedrock-agentcore-part-1/  
官方Part 2：https://aws.amazon.com/blogs/machine-learning/govern-ai-agent-access-with-okta-cross-app-access-and-amazon-bedrock-agentcore-part-2/

文章用ID-JAG委托令牌将用户与指定Agent绑定；Gateway验证Agent身份，Cedar策略按工具及scope默认拒绝，MCP服务再次检查用户组权限；OpenTelemetry将每次ALLOW/DENY关联到授权事件。作者实验中，只读Agent不能执行创建任务，且错误Agent的令牌在模型调用前被拒绝。**边界：** 这是示例架构，样例代码不适合未经安全审查直接投入生产；既不意味着Okta必须使用，也不意味着仅靠Gateway即可替代业务权限。

### 2.4 Taxbit Assist：金融合规知识助手将身份绑定在可信代码
**主体：Taxbit/AWS｜发布：2026-11-06｜新颖度5/5｜性质：生产案例**  
官方：https://aws.amazon.com/blogs/machine-learning/taxbit-assist-a-grounded-role-aware-ai-agent-on-amazon-bedrock-agentcore/

Taxbit Assist嵌入企业Dashboard：从可信调用服务传入用户身份和角色、工具闭包绑定授权上下文、检索文档附来源、OpenTelemetry采集Trace；10%线上会话抽样评估，离线Golden Set每次PR和每晚执行。其当前版本**不读取客户税务数据**，写操作仅限用户自己的支持工单。官方称模型成本平均每对话低于0.20美元，约四分之三输入Token来自缓存；为单一企业披露值，不能外推到其他业务。

**对金融测试的启发：** 让模型选择Capability，但不能让模型传入或篡改身份；建立“来源相关性”与“答案忠实度”两个独立指标。

## 5. Agent Ecosystem

### 5.1 Agent / Skill / Workflow：以Capability为稳定边界
“什么时候触发”与“由谁执行”应独立于“具体调用哪个接口”。一个业务能力可以由聊天、定时任务、网页按钮或其他Agent复用；Tool负责参数契约，Skill负责经验，Workflow负责可审计的确定性步骤。对现有Dify架构，建议逐步从“每个问句一个分支”转为“意图路由+统一能力清单+参数Schema”。

### 5.2 MCP / Tool Calling：动态工具发现不等于动态授权
MCP服务提供工具Schema和调用协议，但业务后端必须基于可信登录态控制可见系统、字段、行与写操作。即使模型伪造user_id或要求跳过审批，也应由Java拒绝。建议工具结果统一返回trace_id、capability_id、authorization、data_timestamp、result。

### 5.3 Browser Agent / 安全治理：执行与审计要解耦
浏览器Agent或Coding Agent执行了动作，不等于业务状态已完成。保留用户触发、工具调用、数据库回读和人工审批的独立证据；跨系统写入采用幂等键与执行轮次。

**本周最值得体验：** 在本地Mock里将“执行统计”和“负责人查询”声明成两个Capability，由同一Dify意图路由选择调用，测试工具Schema、权限与错误返回。  
**Agent实践启发：** 先让能力可复用、可测试，再考虑更复杂的Agent编排。

## 7. 企业实践

**企业：Taxbit（税务合规软件）**。做法：将身份绑定到可信服务，知识库检索+引用、角色授权、线上10%抽样评估、PR及夜间Golden Set、人工纠正后回写知识库。效果：官方披露平均模型成本低于每对话0.20美元，并有企业客户自助解决集成问题的案例；未披露可普遍推广的任务成功率。**可借鉴：** 对金融测试经理助手，优先上线两个只读能力，使用真实业务回读而非仅LLM评分，逐步扩展到任务创建。来源：https://aws.amazon.com/blogs/machine-learning/taxbit-assist-a-grounded-role-aware-ai-agent-on-amazon-bedrock-agentcore/

## 8. 今日工具推荐

**MCP Python SDK**（https://github.com/modelcontextprotocol/python-sdk）。今日只建议用其本地Mock能力验证工具Schema与调用错误；不接真实PG、不开放公网。对于当前Java项目，也可以直接以OpenAPI/JSON Schema模拟相同契约，无需引入新的Python服务。

## 9. 今日实战

**把两个查询接口统一为Capability目录**。示例：
```json
{
  "capability_id": "query_execution_summary",
  "version": "v1",
  "input_schema": {"system_id": "string", "month": "YYYY-MM"},
  "permission": "TEST_EXECUTION_READ",
  "read_only": true,
  "timeout_ms": 3000,
  "output": ["trace_id", "metric_version", "data_timestamp", "count"]
}
```
另一个Capability为`query_system_owner`。Java负责把可信登录态映射到系统范围，模型只提供业务参数；数据查询通过MyBatis参数绑定/预定义SQL完成。

## 10. Today Worth Thinking

**如果每增加一个查询功能，就要重新设计一整套Prompt和Dify节点，问题到底出在模型能力，还是业务能力边界没有抽象好？** 对成熟业务平台，更大的维护成本往往来自重复实现身份、参数、错误处理和业务口径，而非模型推理本身。

## 11. 30分钟 Action

| 时间 | 动作 | 产出 |
|---|---|---|
| 0—10分钟 | 为执行统计、负责人查询写Capability清单和Schema | 两份JSON契约 |
| 10—20分钟 | 用Mock分别返回成功、参数错误、无权限 | 6个固定样本 |
| 20—30分钟 | 让Dify按意图调用，核对trace_id与后端授权 | 结果矩阵 |

**完成标准：** 两个Capability复用同一调用协议；非法system_id与伪造user_id被拒绝；失败返回结构统一；业务口径和结果可回读。

## 13. 我的备注：金融测试、Agent Testing、智能测试平台

**测试经理智能助手：** 当前独立Vue3 iframe + Dify Chatflow + Java Capability API + PG架构无需推翻。重点解决“对话生硬、依赖现有接口、每个功能要定制开发”的扩展瓶颈：抽取统一Capability注册表、Schema、授权、错误码与Trace。先完成执行统计与系统负责人两项；知识库和普通模型聊天保持独立入口，避免让通用聊天绕过业务能力网关。以后新增自动任务创建再引入审批、幂等和审计。

**日志脱敏检测平台：** 将规则扫描、AI精筛、复扫和人工确认视为不同Capability；统一execution_epoch和事件幂等，避免旧回调覆盖新状态。AI只辅助判断，不直接决定关闭问题。

**Agent Testing：** 重点关注Capability复用率、Tool Schema合规率、越权阻断率、Verified Task Success、Trace覆盖率及每个验证成功任务的成本。

**结论：** 下一阶段的竞争力不是堆叠更多Agent，而是让成熟平台已有能力以统一、受控、可验证的方式被对话调用。
