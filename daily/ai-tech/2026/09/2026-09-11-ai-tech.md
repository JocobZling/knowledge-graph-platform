# AI 与 Agent 每日简报 v2

**日期：2026-09-11**

## 1. 今日摘要

过去 24 小时最值得关注的不是新的旗舰模型，而是 Agent 的交互范式开始从“同步聊天窗口”转向“可长期运行、可暂停审批、可恢复的后台工作单元”。

AWS 9 月 10 日开源 Pizza Bot：任务可以手工、定时或 Webhook 启动，Agent 在后台持续工作；完成结果进入 Unread，需要用户决策的任务进入 Action。其运行状态通过 DeepAgents/LangGraph checkpoint 持久化，审批暂停可以跨会话、跨设备继续；MCP 提供工具，Agent Skills 将专家指令与精简 Tool Set 封装成独立 Worker。更重要的是，这一产品形态默认“用户不会一直盯着 Agent”。

GitHub 9 月 9 日上线 Enterprise Managed Permissions for Copilot Agent Operations：企业管理员可以对 Shell、文件读写和网络域集中设置 Block、Require Approval 或 Allow，而且用户、Workspace、Auto-approval 和历史保存的 Approval 都不能削弱企业限制。这让 Agent Approval 从 UI 提示进一步变成可继承、不可下调的组织策略。

AWS for SAP MCP Server 同期展示了另一条企业落地主线：通过 OAuth 2.0 On-Behalf-Of Token Exchange，把真实用户身份从 Agent/MCP 一直传播到 SAP，由 SAP 按原用户角色授权并在 Security Audit Log 中记录真实操作者，而不是让所有 Agent 共用一个 Service Account。

监管侧，欧盟网络安全局 ENISA 已获得 Anthropic Mythos 5 与 OpenAI GPT-6 Astra 的访问权限，用于评估模型能力及网络安全影响。前沿模型安全验证正在继续从厂商内部 Eval 向外部独立评估延伸。

最近 7 篇日报（9 月 4–10 日）已完成去重：此前已覆盖 Monitor/Fallback、Shared-state Communication、Incident Evidence、Pre-model Runtime、Agent Inventory、Guardian/Gateway 与 Incident Forensics。本期不重复这些主题，主线聚焦：**当 Agent 可以离开用户视线持续工作以后，审批、身份、状态恢复和权限约束能否跨时间保持正确。**

仓库未发现独立 ai-tech 主题索引。

## 2. AI / 大模型 Top News

### 2.1 AWS 开源 Pizza Bot：Background Agent 获得 Inbox + Durable State

Pizza Bot 把 Agent 工作从 Session 改造成 Thread：完成任务进入 Unread，需要人工决定的任务进入 Action；关闭页面或客户端重连不会让 Thread 消失，状态由服务器和 Checkpoint 持久化。

真正值得关注的测试对象是：

```text
Start
→ Running
→ Waiting Approval
→ Disconnect
→ Reconnect
→ Resume
→ Side Effect
→ Completed
```

传统 Chat Agent 测试主要覆盖单次 Request/Response；Background Agent 则必须增加 Pause/Resume、重复执行、过期审批、状态漂移和恢复幂等性。

### 2.2 Pizza Bot：Skill + MCP 开始形成可审查的 Specialist Worker

Pizza Bot 支持 Agent Skills。每个 Skill 使用 SKILL.md 定义专家能力，并绑定自己的短 Tool List；例如 Browser Automation Worker 可以只拥有 Browser MCP，而不继承主 Agent 的全部工具。Skill 还能针对具体 Tool 声明 interruptOn 审批策略。

这提供了一个很实用的最小权限模式：

```text
General Agent
   ↓ delegate
Specialist Skill
   ↓ limited tool set
MCP Tool
```

Agent Testing 不只要测“主 Agent 有什么权限”，还要验证 Delegation 后权限是否被意外放大。

### 2.3 GitHub Copilot：企业 Agent 权限策略进入 GA

GitHub 企业管理员现在可以对 Agent Host 中的 Shell Commands、File Reads/Edits 和 Network Domains 统一定义 Block / Require Approval / Allow。企业限制不能被用户设置、Workspace 设置、Auto-approval 或历史 Approval 降低。

这意味着权限优先级本身也应成为回归对象：

```text
Enterprise DENY
> Team Policy
> Workspace
> User Preference
> Saved Approval
```

高风险环境尤其要测试“下层配置能否意外覆盖上层策略”。

### 2.4 AWS for SAP MCP：Agent 身份从 Service Account 走向 OBO Identity Propagation

AWS for SAP MCP Server 使用 Entra ID + AgentCore Identity + RFC 8693 Token Exchange，把用户身份沿 Quick → MCP → SAP 传播。SAP 最终按真实用户授权，并把动作记在该用户的 Security Audit Log 下。

这解决了企业 Agent 一个非常关键的问题：

```text
谁发起任务？
谁授权？
Agent 代表谁执行？
后台最终记录谁？
```

四个答案应该保持一致，而不是全部变成一个共享技术账号。

## 5. Agent Ecosystem

### 本周最值得体验：Durable Approval Test

准备一个需要人工审批才能写入的无风险任务：

```text
Agent Proposal
→ WAITING_APPROVAL
→ 关闭客户端
→ 等待 10 分钟
→ 修改后台业务状态
→ 重新连接
→ Approve
```

重点验证：审批时是否重新校验当前状态、权限和参数，而不是直接执行 10 分钟前生成的动作。

### Agent 实践启发：Approval 不是一个 Button，而是一份有生命周期的授权

建议 Approval 至少绑定：

```text
actor
resource
action
parameters
policy_version
created_at
expires_at
state_version
```

如果资源、权限或参数发生变化，旧 Approval 应失效或重新确认。

### Workflow 治理：Resume 必须保证幂等

Background Agent 发生进程重启、网络中断或 Checkpoint 恢复时，要区分“最后一步尚未执行”和“已执行但结果未写回”。否则 Resume 很容易造成重复邮件、重复写库、重复支付或重复任务触发。

## 10. Today Worth Thinking

同步 Agent 的安全问题通常发生在一次会话里；后台 Agent 的安全问题会跨越时间。

真正需要问的是：

> 用户 30 分钟前批准的动作，在 30 分钟后的世界里还成立吗？

所以 Background Agent 的核心测试对象不只是 Reasoning，而是 **Temporal Correctness**。

## 11. 30分钟 Action

今天挑一个现有异步任务，画出状态机：

```text
WAITING
→ RUNNING
→ WAITING_APPROVAL
→ RUNNING
→ COMPLETED / FAILED / STOPPED
```

然后只测试三条恢复路径：

1. RUNNING 时进程重启；
2. WAITING_APPROVAL 时用户离线再回来；
3. Approval 产生后业务数据被别人修改。

每条都检查：重复 Side Effect、状态丢失、旧审批继续执行。

这就是第一版 **Background Agent Resume Regression**。

## 13. 我的备注

结合金融测试、Agent Testing 和智能测试平台，今天最值得提前补的是 **Temporal Authorization + Resume Safety**。

现在很多 AI Workflow 仍默认：

```text
请求进来
→ 很快执行完
→ 返回结果
```

但 Agent 化以后更可能变成：

```text
08:30 创建任务
08:35 Agent 分析
08:40 等待审批
09:20 用户审批
09:21 Agent 恢复
09:25 写业务系统
```

这 55 分钟里，数据、权限、配置、模型、规则甚至任务本身都可能变化。

因此金融 Agent 的 Approval 不建议只保存一个 `approved=true`，而应该绑定当时的资源版本、参数 Hash、权限策略和有效期。执行前再次验证：

```text
Approval Subject == Current User
Approval Action  == Current Action
Parameter Hash   == Current Parameters
Resource Version == Current Resource
Policy Version   == Current Policy
Not Expired
```

任一不一致都重新审批。

这对现有日志 AI 精筛也可以直接落地。比如未来 AI Agent 不只是给出误判判断，而是能够触发“批量忽略”“重新扫描”“更新报告”等动作，那么 WAITING_APPROVAL 后 Report 可能已经被规则回调更新。恢复时不能拿旧状态直接覆盖新状态。

第二个建议是把现有 Report / Server 状态机逐渐扩展成 **可恢复状态机**。每一个外部副作用都生成 idempotency_key，并在恢复时先查询执行记录：

```text
checkpoint says: CALL_TOOL
        ↓
side_effect ledger
   ├─ exists → 读取结果继续
   └─ absent → 才重新执行
```

这样 Python 回调、AI 精筛、Agent 重启和人工审批可以共享同一套恢复原则。

第三个值得提前建设的是 **Identity Continuity Test**。AWS SAP OBO 的价值就在于后台系统仍然知道“Agent 是代表谁执行”。金融 Agent 后续接数据库、工单、测试平台或业务后台时，都应尽量避免所有动作最终只留下统一 AI Service Account。

一次完整 Agent Run 最终应该能够回答：

```text
谁发起？
谁批准？
Agent 代表谁执行？
执行时权限是否仍有效？
后台审计记录的是谁？
中断恢复后有没有重复副作用？
```

这会是 Background Agent 真正进入金融生产环境前，比“它能不能自主跑很久”更重要的一组测试能力。
