# AI 与 Agent 每日简报 v2

**日期：2026-09-02**

## 1. 今日摘要

过去 24 小时出现了两类值得同时看的变化：一边是前沿模型能力继续上升，另一边是围绕模型、Skill、MCP 和企业数据的控制面开始同步升级。

Anthropic 9 月发布 Claude Fable 5.1 与 Claude Mythos 5.1：两者使用同一模型，但采用不同安全级别；Fable 5.1 GA，Mythos 5.1 仅通过 trusted access 提供。Anthropic 称 Fable 5.1 典型按 Token 计费工作负载预计比 Fable 5 低约 25%，高度 Agentic 工作负载节省最高约 45%，并将 Enterprise Frontier Safeguards（EFS）作为企业侧新安全架构。

OpenAI 9 月 1 日宣布 Astra 已达到 Preparedness Framework 的 Critical cybersecurity capability threshold：在合适 Tool 和权限下，可自主发现此前未知的软件漏洞并开发利用方式。OpenAI 因此延后部分开发/发布工作以强化保护，并计划限制高级网络安全能力的访问。

Agent 生态侧，AIR 9 月 1 日公开亮相并融资 5000 万美元，其核心对象不是模型 Prompt，而是企业 Agent 使用的 Skill、Plugin、MCP Server 与 Add-on：发现、持续检查、追踪依赖并在组件不合规时阻断或撤销。Agent 软件供应链正在成为独立安全域。

JetBrains Compose Multiplatform 1.12 则把 MCP Server 放进 Compose Hot Reload，使 Coding Agent 可以直接对运行中的 UI 执行 reload、截图、读取 semantic tree、click/type/scroll 和日志读取。Coding Agent 的验证闭环开始从“改代码 + 跑测试”扩展到“改代码 + 观察真实 UI + 操作 UI + 再验证”。

去重方面，已核对 2026-08-26 至 2026-09-01 最近 7 篇 `daily/ai-tech`。近期已覆盖 Event-driven Agent、Adversarial Control Path、Physical Agent、Agent Improvement、Model Supply Resilience、Runtime/Harness 与 Eval Environment Acceptance。本期不重复这些主线；Astra 属于新的 Critical 能力阈值事件，EFS 与 Agent Supply Chain 则属于新增控制能力。

## 2. AI / 大模型 Top News

### 2.1 Claude Fable 5.1 / Mythos 5.1：同一模型按风险能力分层开放

Anthropic 将 Fable 5.1 与 Mythos 5.1 定义为同一底层模型的两种安全配置：Fable 5.1 面向通用编码与知识工作 GA；Mythos 5.1 的高级网络安全和生命科学能力仅通过可信访问计划提供。

这比传统的 `model_name → permission` 更接近：

```text
Base Capability
→ Capability Tier
→ Safeguard Profile
→ Access Program
→ Tool / Data Scope
```

对企业 Agent Testing 的启发是：模型版本之外，应把“能力档位/安全档位”也纳入 Baseline。相同模型在不同访问级别下，允许的 Tool、数据、任务和审计要求可能完全不同。

### 2.2 OpenAI Astra：首个达到 Critical 网络安全能力阈值的 OpenAI 模型

OpenAI 表示 Astra 已达到其 Preparedness Framework 的 Critical cybersecurity threshold。在合适 Tool 和访问权限下，模型可发现未知漏洞，并在无需人工逐步指导的情况下开发利用路径。

OpenAI 因此强化了拒绝训练、滥用防护和可停止潜在未授权活动的监控，并计划让高级 Cyber 能力先进入受限测试与 Daybreak Blue 防御性访问。

这意味着模型能力测试需要与控制测试绑定：

```text
Capability ↑
→ Required Control Tier ↑
→ Access Scope ↓ / Review ↑
→ Release Gate ↑
```

不能继续用同一套权限模板覆盖所有模型。

### 2.3 Enterprise Frontier Safeguards：安全监控数据开始留在客户自己的云账户

Anthropic EFS 的关键不是新增一个过滤器，而是改变监控数据的信任边界：客户数据、监控活动数据与密钥可以留在客户控制的 AWS、Google Cloud 或 Azure 环境中，企业自己决定谁能访问安全事件数据。

Anthropic 表示该架构与超过 100 家企业共同设计；参与方讨论了在系统重要性银行中运行前沿模型时，谁持有数据、谁持有密钥、自动审查能看到什么以及何时允许人工查看。

对金融机构而言，这把一个常见矛盾拆开了：既需要 Safety Monitoring，又不能因为监控本身把高敏数据复制到外部控制面。

### 2.4 AIR：Agent 的 Skill / Plugin / MCP Server 正形成新的软件供应链

AIR 将 Agent 使用的 Skill、Plugin、MCP Server、Add-on 视为可持续发现、评估和撤销的依赖。其公开方案强调：组件上线前后持续检查；发现恶意、脆弱或未批准组件后，可追踪所有依赖它的 Agent / Workflow 并统一撤销。

这使 Agent Governance 从：

```text
Model + Prompt + Tool Allowlist
```

继续扩展到：

```text
Model
+ Skill Version
+ Plugin Version
+ MCP Server
+ Data Source
+ Dependency Graph
+ Trust Status
```

## 3. 科技行业动态

### 3.1 Agent SBOM 正从概念变成现实需求

传统 SBOM 管 Library / Package；Agent 还需要知道“运行时到底接了什么”。Skill、MCP、Browser Extension、Plugin 和远程 Tool 都可能在不改主 Agent 代码的情况下改变行为。

因此建议把 Agent Dependency Manifest 当作一等资产，并支持组件被撤销后反向定位受影响 Workflow。

### 3.2 AI 治理分歧仍在扩大，但技术侧正在形成更细的能力分级

9 月 1 日 G20 技术会议上，美国推动更少新增监管、强调创新与基础研究的 Carolina Principles；与此同时，模型厂商自身却在通过 Critical Capability、Trusted Access、Enterprise Safeguards 等机制增加能力分层与访问控制。政策路线可能继续分化，但企业工程层仍需要把高能力模型当作不同风险等级的软件依赖管理。

## 5. Agent Ecosystem

### 本周最值得体验：Agent Dependency Manifest

给一个现有 Agent 写出真实依赖：

```yaml
agent: log-risk-reviewer
model: model-x
skills:
  - risk-review@3.2
mcp:
  - report-reader@1.4
  - knowledge-search@2.1
plugins: []
data_sources:
  - risk-rule-db
```

然后回答两个问题：`risk-review@3.2` 被撤销后哪些 Workflow 受影响？`report-reader@1.4` 被替换后哪些 Eval 必须重跑？

### Agent 实践启发：能力越高，不应该自动拥有越多权限

更合理的方向恰好相反：

```text
Higher Model Capability
→ More Explicit Scope
→ Stronger Monitor
→ Smaller Default Permission
→ Stronger Release Gate
```

模型更强只是说明它能完成更多任务，不等于它应该默认获得更多生产权限。

### Workflow 治理：把 MCP 变更视为代码依赖升级

MCP Tool Schema、返回结构、权限、远程实现任一变化，都可能改变 Agent 行为。建议 MCP 版本变化自动触发 Contract Test + Tool Regression + High-risk Case。

## 9. 今日实战

给一个 MCP/Skill 建最小依赖登记：

```yaml
component: report-reader
kind: mcp
version: 1.4.0
owner: test-platform
trust_status: approved
permissions:
  - report:read
used_by:
  - log-risk-reviewer
  - report-summary-agent
regression_suite: mcp-report-v3
```

然后模拟 `trust_status: revoked`，预期两个 Agent 都不能继续调用该 MCP，而不是只在下一次部署时才发现。

## 10. Today Worth Thinking

过去我们经常把 Agent 风险理解成“模型会不会做错”。

但生产 Agent 的风险越来越像软件供应链问题：模型可能没变，某个 Skill、MCP、Plugin 或数据源已经变了。

真正需要回答的是：

> 这次 Agent 的能力到底由哪些可变组件共同组成？其中任意一个组件失去信任后，我们能不能立刻知道谁受影响并阻断它？

## 11. 30分钟 Action

今天从一个现有 Agent 开始，列出 5 类依赖：Model、Skill、MCP/Tool、Data Source、Runtime。每个依赖只补四个字段：`version / owner / trust_status / regression_suite`。

然后任选一个依赖假设“今天被撤销”，确认你是否能在 5 分钟内回答：哪些 Agent 受影响、哪些任务要停、哪些测试必须重跑。

这就是第一版 **Agent Dependency Impact Test**。

## 13. 我的备注

结合金融测试、Agent Testing 和智能测试平台，今天最值得提前做的是 **Agent Component Registry + Dependency Regression**。

未来一个 Agent 很可能不是一个固定应用，而是：

```text
Model
× Harness
× Prompt
× Skill
× MCP
× Data
× Permission
× Runtime
```

其中任何一层升级都可能造成行为漂移。传统“模型版本 + Prompt 版本”已经不足以解释一次回归为什么失败。

智能测试平台可以逐渐维护：

```text
Component Registry
      ↓
Dependency Graph
      ↓
Change Event
      ↓
Affected Agent / Workflow
      ↓
Targeted Regression
      ↓
Release / Block
```

对金融场景尤其有价值的是，把 `trust_status` 和 `permission_profile` 一起纳入依赖。一个 MCP Server 即使接口完全兼容，只要 Owner、部署地址、权限或安全状态变化，也应该触发重新验收。

另外，Compose Hot Reload MCP 展示了另一个很适合测试平台的方向：**让 Agent 看到真正运行后的系统，再由独立 Oracle 验证结果。** 以后无论是 Web、桌面还是内部管理平台，都可以从“生成代码”逐步演进到“生成 → 启动 → 操作 → 观察 → 断言 → 修复”的闭环。

这样 Agent Testing 最终管理的就不是某个模型的准确率，而是：

> **一次 Agent 能力由哪些组件组成、每个组件是否仍可信、发生变化后影响了什么，以及最终业务行为是否仍然通过独立验证。**
