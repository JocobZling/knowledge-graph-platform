# AI 与 Agent 每日简报 v2

**日期：2026-09-22**

## 1. 今日摘要

已读取仓库 9 月 15—21 日连续 7 篇 `daily/ai-tech` 日报并完成主题去重。近期已覆盖专业 Agent、Commit Gate、Recovery、Agent-ready Data、Independent Assurance、Agent Oversight、Capability Supply Chain 与 Emergency Stop，因此今天不重复这些主题。

过去 24 小时最值得保留的新增，是 Agent 工程的竞争重心进一步从“选哪个模型”转向“模型外面的 Harness 和 Context 怎么设计”。

9 月 21 日，AWS Strands 团队发布预组装的 Strands harness：一行即可创建通用 Agent，默认集成 Tool、Context Management、Session、Memory、Hook、Skill 与系统 Prompt。官方文档强调它可以跨模型、跨环境运行，并把过去需要开发者自行拼装的 Harness 变成可版本化、可基准测试的工程层。

同日，OpenAI 发布 V7 企业案例。V7 用 Context Graph 把企业文件中的实体、关系、事实、指标与原始证据组织成 Agent 可查询的机构记忆，并通过 MCP 暴露给 ChatGPT、Codex 等客户端。V7 报告 GPT-5.6 Sol 在其 Context Graph 基准上将 Tool-call Error 从 GPT-5.5 的 2.7% 降至 0.2%；在更难的图查询集上，GPT-6 Astra 达到 89% 准确率。上述数字来自 V7 自有评测，应视为企业案例数据而非通用基准。

GitHub 9 月 21 日还开始向 Copilot 推送 Grok 4.7，覆盖 IDE、CLI、Cloud Agent 等入口，并允许企业管理员通过 Model Policy 控制是否启用。

今天主线收敛为：**生产 Agent 的稳定性越来越取决于 Model × Harness × Context 三者组合；模型升级不应掩盖 Harness 与 Context 本身的回归风险。**

## 2. AI / 大模型 Top News

### 2.1 Strands Harness：Harness 从“胶水代码”升级为独立产品层

Strands harness 默认封装 Tool、Context Management、Session、Memory、Hook、Skill 和系统 Prompt，并提供 Python / TypeScript 接口。官方文档还明确提供 Strands Evals 与 Strands Shell 作为配套能力。

这意味着 Agent 的可复现配置不应只记录 `model_name`，而应至少记录：

```text
model_version
harness_version
system_prompt_version
context_policy
skill_set
tool_set
memory_policy
hook_set
```

第三方报道援引 AWS 自测称，其在 6 组基准中使用相同 Claude/GPT 模型时平均减少约 28% Token；由于属于厂商自测且比较对象包含 Coding Agent，今天只作为工程信号，不把它当作通用性能结论。

### 2.2 V7 Context Graph：企业记忆开始从 RAG Chunk 走向结构化 Context

V7 的 Context Graph 在文件进入后抽取 Entity、Relationship、Fact、Attribute、Metric，并把事实连接回原始证据；当 Graph 信息不足时再回落到底层文档 RAG。

这形成一条值得金融 Agent 借鉴的链路：

```text
Document
→ Fact Extraction
→ Entity Resolution
→ Context Graph
→ Evidence Link
→ Agent Query
```

关键不是“记住更多”，而是：**Agent 使用的每条机构记忆是否知道来源、版本和有效时间。**

### 2.3 OpenAI：下一阶段标准开始围绕自动化研究与人类留在自改进环路

OpenAI 9 月 21 日发布《Building standards for the next phase of AI》，把自动化 AI Researcher、Alignment 与“让人类继续处于 self-improvement loop”列为核心方向之一。

对 Agent Testing 的直接启发是：未来测试对象可能不只是一个固定 Workflow，而是会自己产生新代码、新实验和新策略的系统。此时需要验证的不只是 Output，还包括：

```text
Change Proposal
Evidence
Independent Eval
Approval
Rollback
```

### 2.4 GitHub Copilot：Grok 4.7 开始进入多入口 Agentic Coding

GitHub 9 月 21 日宣布 Grok 4.7 逐步进入 Copilot，可用于 VS Code、Visual Studio、Copilot CLI、Cloud Agent、JetBrains、Xcode、Eclipse 等入口。企业管理员可以通过 Model Policy 控制访问。

这再次说明：Agent 平台应把模型视为可替换依赖，而不是把行为契约绑定在某个模型名称上。

## 3. 科技行业动态

### 3.1 Harness Engineering 正成为独立优化对象

过去优化通常集中在 Model / Prompt；Strands harness、Harness Optimizer、Harness-of-Harness 等近期工作说明，新的优化对象正在变成整个 Agent Harness：Context 如何压缩、Tool Result 如何截断、Memory 何时写入、Skill 如何暴露、失败如何恢复。

因此 Benchmark 也应从 `Model A vs Model B` 扩展成 `Model × Harness Configuration`。

### 3.2 Enterprise Context 正成为 Agent 的核心基础设施

V7 案例显示，企业 Agent 的瓶颈并不总是模型推理，而是“哪个文件最新、同一实体在多个系统里叫什么、这个数字来自哪里”。企业 Context Layer 会逐渐承担 Entity Resolution、Provenance、Freshness 和 Evidence Linking，而不是让每个 Agent 重复搜索并临时理解。

## 5. Agent Ecosystem

### 本周最值得体验：Harness A/B Test

固定同一个模型、同一组 20 条任务，只改变 Harness：

```text
A = 当前默认 Harness
B = 新 Harness / 新 Context Policy
```

同时记录 Success Rate、Tool-call Error、Token / Successful Task、Latency、Context Overflow、Human Rework。不要只看“回答是否更好”，而要看同一模型换 Harness 后整个行为曲线如何变化。

### Agent 实践启发：Context 也需要 Provenance

Memory / Context 不应只是：

```text
key → value
```

更适合生产环境的是：

```text
claim
source
effective_time
version
confidence
owner
```

否则错误 Context 一旦进入长期 Memory，会稳定地污染后续 Run。

### Workflow 治理：Model 与 Harness 分开版本化

建议 Trace 至少保存：

```text
requested_model
selected_model
harness_version
context_policy_version
skill_manifest_version
memory_snapshot
```

这样模型没变但行为突然变化时，才能继续定位 Harness / Context Drift。

## 7. 企业实践

### V7：用 Context Graph 给金融与保险 Agent 建立机构记忆

V7 Go 把 SharePoint、Google Drive 等来源中的企业信息整理成 Context Graph，并保留回原始证据的引用；Workflow 再根据任务复杂度把步骤分给不同模型。其做法可以抽象为：

```text
Enterprise Source
→ Context Graph
→ Evidence
→ MCP
→ Agent
→ Auditable Workflow
```

最值得借鉴的不是某个准确率数字，而是把“企业知道什么”从 Prompt / 临时 RAG 中剥离成独立 Context Infrastructure。

## 8. 今日工具推荐

### Strands harness

建议重点看三件事：Context Compaction、Tool Result Truncation、Agent Skills Loading。它们都直接影响长任务的稳定性与 Token 成本，也都应该成为 Regression Test 的对象，而不是隐藏在框架默认值里。

## 9. 今日实战

给现有 AI 精筛增加第一版 Harness Manifest：

```yaml
agent: ai-log-reviewer
model_version: model-x
harness_version: v1
prompt_version: v12
context_policy:
  max_context: fixed
  compaction: disabled
skills:
  - log-sensitive-review-v3
tools:
  - read_scan_result
  - write_ai_review
memory_policy: none
```

以后每次模型、Prompt、Workflow、Context Policy 任一变化，都能明确知道这次 Run 的真实执行组合。

## 10. Today Worth Thinking

如果同一个模型：

```text
Harness A = 90% Task Success
Harness B = 97% Task Success
```

那我们到底是在评测“模型能力”，还是在评测“模型被怎样使用”？

Agent 时代更合理的测试单位，很可能不是 Model，而是：

```text
Model × Harness × Context × Capability
```

## 11. 30分钟 Action

今天从 AI 精筛挑 20 条已有样本，模型和 Prompt 完全不变，只改变一次 Context 组织方式：

```text
A：当前上下文原样输入
B：固定字段 + 明确分隔 + Source / Type 标签
```

比较：误判率、Token、Latency、输出格式失败数。这个实验可以直接回答一个问题：当前提升空间到底在模型，还是在 Harness / Context Engineering。

## 13. 我的备注

今天这个方向很适合现在的日志 AI 精筛，因为当前主要关注 Model 和 Prompt，但实际效果还同时受到 Context 拼装、Dify Workflow、规则结果格式、上下文截断和并发执行方式影响。

建议后面把 AI 精筛的一次执行正式定义为：

```text
AI Runtime =
Model
× Prompt
× Harness
× Context Policy
× Rule Version
× Capability Set
```

第一步不需要改架构，只需要把这些版本全部写入 Report / Trace。

第二步可以建立 Harness Regression。500 条固定测试集不再只在换模型时执行；只要修改 Context 截断、Prompt 拼装、Workflow 节点、Skill、Tool Schema，也触发同一套回归。

第三步是 Context Provenance。现在每条 AI 输入已经有 `r/s/d/l`，可以继续补：

```text
source_server
source_file
rule_version
scan_time
context_window_policy
```

这样未来 AI 判断异常时，可以准确还原“模型当时究竟看到了什么”。

最后可以增加一个很实用的指标：

```text
Cost per Confirmed Finding
```

而不是只统计 Token。因为 Harness 优化真正应该追求的不是“更省 Token”，而是：

```text
更少 Token
+
更低误判
+
更稳定格式
+
更少人工复核
```

这会比单纯追最新模型更适合金融测试平台的长期演进。
