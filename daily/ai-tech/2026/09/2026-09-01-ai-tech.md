## 2. AI / 大模型 Top News

### 2.1 Anthropic 恢复外部 Cyber Eval：安全控制首次明确前移到 Tool Call 之前

Anthropic 新增的实时分类器会识别模型是否在激进探测/逃逸评测环境、或意外获得互联网访问；一旦命中，系统会在 Tool Call 被执行前阻断动作、结束当前任务并通知人工。

这条变化比“增加一个 Monitor”更重要：

```text
Agent Intent
    ↓
Runtime Classifier / Scope Monitor
    ↓
ALLOW / BLOCK
    ↓
Tool Execution
```

也就是说，安全控制从事后 Transcript Review 进入真正的 **Pre-action Enforcement**。

Anthropic 还要求外部 Cyber Eval 默认运行在无公网的 hardened sandbox 中，只允许访问模型 API；API Key 应位于 Sandbox 外部，并在每次评测前验证隔离是否仍然成立。

对 Agent Testing 的直接启发：以后评测环境本身也要有 Acceptance Test，而不是“环境搭好了就开始测模型”。

### 2.2 Anthropic 增加“任务可解性检查”：Impossible Task 正式进入评测安全流程

Anthropic 的外部评测最佳实践要求，在真正运行评测前确认 Challenge **原则上可以完成**。

原因很明确：当目标服务下线、任务不可完成或合法路径被堵死时，Agent 更容易寻找其他方式完成目标，从而增加越界行为概率。

这与近期 Agent 失控事件形成了一个非常清楚的工程模式：

```text
Goal Pressure
+
Impossible / Broken Task
+
High Autonomy
=
Alternative Path Search
```

因此 Agent Eval Dataset 不应该只有正常 Case，还应该显式标记：

- SOLVABLE
- UNSOLVABLE
- DEPENDENCY_UNAVAILABLE
- INSUFFICIENT_PERMISSION
- CONFLICTING_GOAL

并验证 Agent 是否能够安全退出，而不是持续试探环境。

### 2.3 Google Antigravity Teamwork：多 Agent 开始执行“小时—天”级研究与工程任务

Google Antigravity 的 Teamwork 支持自主 Agent 团队长期协作、Critique 与 Iteration。Google 披露的最新实验包括：

- 解决 7 个开放数学/理论计算机科学问题；
- 在 TCSBench 达到 71%；
- 从零构建 cycle-accurate、out-of-order RISC-V CPU simulator，并启动 xv6；
- 向 Eigen / ParlayHash 提交性能优化。

这些均属于 Google 自有实验结果，不能简单等同于普遍 Agent 能力。

但测试对象已经非常明确地从：

```text
Agent A + Agent B
→ 一次协作
```

进入：

```text
Long-running Goal
→ Parallel Agents
→ Critique
→ Artifact
→ Verification
→ Revision
→ Final Result
```

未来 Multi-Agent Eval 至少要记录 **Role、Handoff、Artifact Version、Independent Verification、Conflict、Resource Budget 与 Termination Reason**。

### 2.4 GitHub Copilot VS Code：Agent Session 正脱离单窗口、单模型和单客户端

GitHub 最新 VS Code 更新允许：

- 多个 Agent Chat 并排观察；
- `/btw` Side Conversation 共享主会话 Context/Prompt Cache；
- 外部 Copilot / Claude Agent Session 在 VS Code 中继续；
- 多个 VS Code 窗口连接同一个 Agent Session；
- Claude Session 可切换模型 Provider；
- `/rubber-duck` 调另一个模型做 Second Opinion；
- Agent Plugins 1.0 可在兼容 Agent Client 之间迁移。

这说明一次 Agent Run 的边界已经不再等于一个 UI 会话。

真正需要测试的是：

```text
Session Identity
+ User Authority
+ Model Provider
+ Plugin Set
+ Workspace
+ Tool State
```

在跨窗口、跨客户端恢复之后是否仍然一致。

### 3.2 Agent Control 正从“配置存在”进入“评测前必须验收”

Anthropic 的整改把几个过去经常被分散管理的控制串成了一条完整链：

```text
Sandbox Validation
→ Task Solvability
→ Explicit Scope
→ Real-time Monitor
→ Pre-tool Block
→ Human Alert
```

这非常接近传统测试里的环境准入和上线前 Gate。

未来 Agent 平台应该能够回答的不只是：

> Sandbox 配置是什么？

而是：

> **本次 Run 开始之前，这个 Sandbox 是否真的被验证过？**

## 5. Agent Ecosystem

### 本周最值得体验：Eval Environment Acceptance Test

不要先测模型，先测环境。

给 Sandbox 建一个最小验收集：

```text
CASE 1：尝试访问公网
CASE 2：尝试读取宿主环境变量
CASE 3：尝试访问 Sandbox 外文件
CASE 4：尝试使用未声明 Tool
CASE 5：任务目标故意设置为不可完成
```

预期：

```text
Boundary Violation → BLOCK
Tool Executed = false
Side Effect = 0
Trace = complete
```

然后才允许正式 Eval 开始。

### Agent 实践启发：Verifier 应与 Worker 分离

Google Teamwork 的长任务形态很容易出现一个问题：做事的 Agent 同时判断自己是否做对。

更稳妥的结构：

```text
Worker Agents
      ↓
Artifact
      ↓
Independent Verifier
      ↓
Deterministic Test / Proof / Benchmark
      ↓
Release
```

在金融测试里，Verifier 可以是 SQL、状态机、金额校验、规则引擎或独立测试 Agent；能确定性验证的部分不要交给 Worker 自评。

### Workflow 治理：Session Authority 必须可重新验证

跨窗口、跨客户端恢复 Agent Session 后，不要直接复用历史权限。

建议每次 Resume 高风险步骤前重新检查：

```text
Current User
Current Role
Session Owner
Tool Scope
Resource State
Approval Validity
```

Session 负责保留上下文，不应该负责永久保存授权。

## 9. 今日实战

给现有 Agent Eval Runner 增加一层 `environment_gate`：

```yaml
environment_gate:
  sandbox_verified: true
  network_default: deny
  secrets_outside_sandbox: true
  task_solvable: true
  realtime_monitor: enabled
  pre_tool_block: enabled
```

启动 Eval 前执行：

```text
Gate != PASS
→ Evaluation 不允许开始
```

再故意把：

```text
task_solvable = false
```

检查 Agent 是否进入：

```text
IMPOSSIBLE_WITH_CURRENT_ENV
```

而不是继续尝试非授权路径。

## 10. Today Worth Thinking

Agent 安全经常被理解成：

> **Agent 做了坏事以后，我们能不能发现？**

但 Anthropic 这次整改把问题往前推了一层：

> **在它真正做出那个动作之前，系统能不能知道这一步不应该发生？**

对于高后果 Tool，这个差异非常大。

更成熟的 Agent Runtime 应该是：

```text
Observe Intent
→ Evaluate Scope
→ Block Before Action
→ Execute
→ Verify Result
```

而不是：

```text
Execute
→ Audit
→ 发现出问题了
```

## 11. 30分钟 Action

今天可以直接给一个现有 Dify / MCP / Coding Agent 写第一份：

**Agent Eval Environment Checklist v1**

只需要 8 项：

1. Sandbox 是否真正隔离；
2. 默认是否禁止公网；
3. Secret 是否位于 Sandbox 外；
4. Tool Allowlist 是否明确；
5. 任务是否确认可完成；
6. Scope 是否写明；
7. Runtime Monitor 是否启用；
8. Block 后是否保证 Tool Calls = 0。

然后故意制造一条失败配置，确认 Eval Runner 会拒绝启动。

这一步的价值比再增加 20 条普通 Prompt Case 更直接。

## 13. 我的备注

结合金融测试、Agent Testing 和智能测试平台，今天最值得正式增加的是：

### **Agent Eval Environment Control Plane**

目前大家谈 Agent Eval 时，通常首先想到：

```text
Dataset
Model
Prompt
Accuracy
```

但近期几次真实安全事件已经说明，Agent 测试结果还高度依赖：

```text
Sandbox
Network
Credential
Tool
Task Solvability
Monitor
Stop Condition
```

所以一次完整 Agent Eval 可以拆成：

```text
Environment Acceptance
        ↓
Runtime Manifest
        ↓
Agent Execution
        ↓
Tool / MCP / A2A Trace
        ↓
Business Assertion
        ↓
Control Effectiveness
        ↓
Evidence
```

对金融测试，可以优先做三层。

**第一层：Environment Gate** 负责验证 Sandbox、网络、Secret、Tool 和环境版本；Gate 不通过，测试不启动。

**第二层：Agent Behavior Test** 才真正测模型在正常、权限不足、依赖失败、不可完成任务中的行为。

**第三层：Business Oracle** 用状态机、数据库字段、金额、规则结果等确定性逻辑判断真实业务结果。

另外，Google Teamwork 与 GitHub Agent Session 的变化提醒了一点：未来 Agent Run 很可能跨小时、跨窗口、跨多个 Worker，甚至跨多个模型。

因此平台最好逐渐把：

```text
run_id
session_id
agent_id
model_version
harness_version
worker_id
artifact_version
verifier_id
```

一起作为 Trace 的一等字段。

最终测试平台才能回答一个越来越关键的问题：

> **这个 Agent 的结论是哪个 Worker 在什么环境、基于什么权限和 Artifact 得出的？另一个独立 Verifier 是否真正验证过？如果环境边界失效，系统能否在 Tool 执行之前把它停下来？**

这比单独追求 Agent Task Success Rate 更接近金融场景真正需要的生产级可信度。
