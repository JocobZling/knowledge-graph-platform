## 2. AI / 大模型 Top News

### 2.1 西班牙 AEPD：AI Agent 关联数据泄露进入真实监管案例

AEPD 9月15日披露首起 AI Agent 关联的数据泄露报告。公开信息称，Agent 识别系统漏洞后访问目标系统，并发生个人数据修改和账单信息查看；调查仍在继续，因此目前不应把尚未确认的责任归属扩大解读。

对 Agent Testing 更重要的是：事故判定已经不能只看模型输出，而要检查 `External Access / Data Read / Data Write / Credential Use / Business Side Effect`。一旦 Agent 能够作用于真实资源，安全验收必须以最终副作用为 Oracle。

### 2.2 韩国：自治 Agent 安全开始进入国家级安全指南

韩国国家网络安全机构宣布正在制定新的自治 AI Agent 安全指南，以应对 Agent 在有限人工监督下运行带来的风险。监管方向继续从传统生成式 AI 的内容风险，扩展到身份、权限、工具调用、持续运行和真实系统动作。

对企业最直接的启发是：Agent 安全基线应从 `Model Policy` 升级为 `Agent Runtime Policy`，至少覆盖身份、授权、网络、Tool、数据、审批、审计与失效策略。

### 2.3 AWS：Agents propose, deterministic code validates

AWS 的航空改签参考架构把 AgentCore Agent 放在 Step Functions 的确定性流程中。Agent 负责寻找候选航班和判断补偿建议，但每个结果之后都有确定性 Validation；Agent Task 本身不能写预订系统或发放补偿，真正执行只发生在确定性 Task 中。

这个模式非常适合金融 Agent：`Agent Proposal → Deterministic Validation → Risk/Human Gate → Commit`。模型可以概率化，落账、改状态、支付、发消息等关键副作用不能概率化。

### 2.4 Rubrik MCP：安全平台开始成为 Agent 的受控 Tool Provider

Rubrik 9月15日宣布 Rubrik MCP，为企业 Agent 提供访问 Rubrik 数据、身份和应用情报的可编程路径，并用于多步安全事件响应。Rubrik 表示其 AI 能力已被约三分之一全球客户使用。

值得关注的不是“安全产品也支持 MCP”，而是企业 Tool 正从通用 API 变成带领域语义和治理能力的 MCP Capability。对 Agent 来说，优质 Tool 应尽量返回经过领域整理、权限过滤、可审计的高层事实，而不是让模型自己拼几十个底层接口。

## 5. Agent Ecosystem

### 本周最值得体验：Commit Gate Test

构造一个无风险写操作，例如 `update_report_status`。让 Agent 产生合法 Proposal，然后在 Proposal 生成后、真正 Commit 前修改数据库版本或业务状态。

正确结果必须是：`STALE_PROPOSAL / Side Effect = 0`。重点不是 Agent 能否发现变化，而是确定性 Gate 是否能在 Agent 完全没发现变化时仍然阻止错误写入。

### Agent 实践启发：Agent 应拥有 Proposal 权，而不是天然拥有 Execution 权

建议把高风险能力拆成：`Reason → Propose → Validate → Authorize → Execute`。Agent 可以参与前两步，甚至帮助解释 Validation Failure，但最终 Commit Authority 应独立于模型。

### Workflow 治理：Human Review 只处理真正的 Exception

AWS 的参考架构把可确定性验证的正常案例自动通过，把无法验证、存在歧义或违反规则的案例送人工。这比“所有 Agent 动作都人工审批”更可扩展，也比“高成功率后全部取消人工”更稳健。

## 7. 企业实践

### AWS：把非确定性 Reasoning 包进确定性 Workflow

AWS 的设计不是让 Supervisor Agent 决定所有编排，而是把 Fan-out、Routing、Validation、Retry、Human Exception 和 Audit Trail 放进 Step Functions；AgentCore Harness 只处理 Agent 内部 Reasoning Loop。

这种职责拆分很适合金融系统：`Workflow Engine` 管业务状态机，`Agent` 管复杂判断，`Deterministic Service` 管真实写操作。这样 Agent 升级时不需要重新发明整个交易控制面。

## 9. 今日实战

给现有 AI 精筛的状态更新路径增加一个明确 Commit Contract：

```yaml
proposal:
  action: update_ai_status
  resource: server-123
  target: AI_COMPLETED

preconditions:
  rule_status: COMPLETED
  ai_task_status: SUCCESS
  expected_version: 17

commit:
  allowed_fields:
    - ai_status
```

真正执行时重新读取数据库。只要 `expected_version`、状态机前置条件或允许字段任意不匹配，统一返回 `DENY / STALE_PROPOSAL`，且 DB Write 必须为0。

## 10. Today Worth Thinking

Agent 成功率达到99%，是否就可以让它直接写生产？

不一定。真正关键的问题是：**剩下1%的错误有没有机会越过最后一道控制线，变成真实业务副作用。**

因此高风险 Agent 更值得优化的指标可能不是从99%提高到99.5%，而是让错误 Proposal 的 `Unsafe Commit Rate` 从可见值降到接近0。

## 11. 30分钟 Action

今天挑 AI 精筛或测试平台里一个真实写接口，只做一件事：把“谁可以调用接口”改写成“什么条件满足时这个动作才允许 Commit”。

至少列出：`Actor / Action / Resource / Allowed Fields / Required State / Resource Version / Evidence / Failure Behavior`。

然后构造3个负向 Case：状态已变化、修改了额外字段、Evidence 缺失。三条全部断言 `Side Effect = 0`。这就是第一版 **Commit Gate Regression**。

## 13. 我的备注

结合金融测试、Agent Testing 和当前智能测试平台，今天最值得落地的不是再增加一个 Reviewer Agent，而是先建立 **Commit Gate**。

现在日志 AI 精筛的很多状态更新其实天然适合这个模式。AI 负责判断“这条是否误报”“建议把 AI 状态改为什么”；业务服务只接受 Proposal。真正写库前，由确定性代码重新检查 Server 当前版本、规则状态、AI 任务事实、允许状态迁移和允许修改字段。

这可以直接解决一个现实问题：两路异步回调同时更新同一行时，不再依赖“Agent/回调拿到的旧对象是否足够新”，而是让每次 Commit 都基于当前数据库状态和明确的字段级更新契约。

第二个值得补的是 **Unsafe Commit Rate**。现有指标通常关注 AI Accuracy、误判率、漏判率，但 Agent 化以后建议增加：`Invalid Proposal Count / Gate Reject Count / Unauthorized Field Attempt / Stale Proposal / Unexpected Side Effect`。前四项可以出现，最后一项应该尽量为0。

第三个是把 Red Team 变成回归。以后模型、Prompt、Skill、MCP 或 Workflow 任何一个发生变化，都固定跑一组越权 Case：要求 AI 修改 rule_status、诱导读取不允许的数据、伪造 Approval、重复执行同一 Side Effect、在内部 Tool 不可用时寻找外部替代路径。模型是否会上当可以作为能力指标，但业务系统最终有没有被改错，才是生产安全指标。

最终可以形成一条很稳定的金融 Agent 架构：`Agent Proposal → Deterministic Business Validation → Policy / Human Gate → Atomic Commit → Side-effect Ledger`。模型可以快速演进，真正的业务边界不跟着模型漂移。
