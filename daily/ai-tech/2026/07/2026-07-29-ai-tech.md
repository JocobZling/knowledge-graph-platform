## 2. AI / 大模型 Top News

### 2.1 MCP 2026-07-28：协议核心转向无状态架构

MCP 新一代规范的核心变化是移除协议级 Session 和传统 `initialize` 握手，改为更适合普通 HTTP 基础设施的无状态模型。官方 Go SDK 已发布对该版本的支持，并保留对旧协议的向后兼容。

关键变化包括：

- 无状态核心，降低远程 MCP Server 横向扩容成本；
- `server/discover` 替代传统初始化握手；
- Multi Round-Trip Requests 支持更复杂的双向交互；
- 统一订阅流替代分散通知；
- 标准化 HTTP Header，便于路由、审计和网关治理；
- Roots、Sampling、Logging 等能力进入正式弃用路径；
- 增加官方一致性测试，便于验证客户端和服务端实现。

**实践价值：** 企业 MCP Gateway 可从“会话转发器”升级为无状态策略网关，将身份、权限、审计、限流和风险控制放在标准 HTTP 基础设施上。

来源：
- https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/
- https://github.com/modelcontextprotocol/go-sdk/releases

### 2.2 GitHub Copilot 强化 Agent 工作流的 OpenTelemetry 与模型治理

GitHub Copilot for JetBrains 新增 Agent 工作流 OpenTelemetry 导出配置，并允许设置 `maxInputToken`、`maxOutputToken`，控制内置模型是否启用，同时支持在 Claude Agent Flow 中直接连接 MCP Server 和自定义 Agent。

**实质新增点：** 可观测性、模型选择、Token 上限和 MCP 接入不再是开发者个人配置，而开始成为企业统一治理对象。

**对 Agent Testing 的影响：** 可以统一采集任务耗时、模型调用、工具调用、Token 消耗、失败重试和人工介入，并按模型或 Agent 版本开展回归对比。

来源：https://github.blog/changelog/2026-07-27-github-copilot-for-jetbrains-adds-improvved-opentelemetry-configuration-and-model-management/

### 2.3 GitHub Copilot App 与 Cloud Agent 纳入企业托管策略

GitHub 为 Copilot App 增加独立访问策略，并将企业 Managed Settings 扩展到 Copilot App 与 Copilot Cloud Agent。管理员可以统一控制 Agent 可访问能力及相关设置，而不再依赖个人本地配置。

**实质新增点：** Agent 的桌面端、云端执行环境与企业策略开始统一。

**实践价值：** 企业 Agent 准入体系需要同时覆盖模型、Agent、工具、MCP Server、执行环境和用户权限，避免只治理模型 API。

来源：https://github.blog/changelog/month/07-2026/

### 2.4 GitHub Actions 自动拦截疑似恶意工作流

GitHub Actions 现会对部分疑似恶意的公共仓库 Workflow Run 进行自动挂起，必须由具有写权限的协作者通过已认证 Web 会话批准后才可执行。该能力无需额外配置。

**实质新增点：** CI/CD 安全控制从静态配置扫描扩展到运行前风险阻断。

**对 Agent 工作流的意义：** 当 Coding Agent 能自动提交代码、修改 Workflow 或触发流水线时，必须把 Agent 生成变更视为潜在供应链输入，在执行前增加差异审查、权限校验和人工审批。

来源：https://github.blog/changelog/2026-07-28-github-actions-holds-unproven-workflows-for-approval/

## 5. Agent Ecosystem

### 本周最值得体验：MCP 官方一致性测试

新规范增加官方 Conformance Tests。建议选择一个现有 MCP Server，分别验证：

- 新旧协议版本协商；
- Tool Schema 合法性；
- 无状态请求是否依赖隐式 Session；
- OAuth 和身份信息是否正确传播；
- 超时、重试和多轮请求是否符合规范；
- 日志与审计信息能否关联到同一业务任务。

### Agent 实践启发：无状态协议不等于无状态业务

MCP 协议可以无状态，但 Agent 任务仍然需要保存：

```text
Task Context
├── User Identity
├── Business Scope
├── Approval State
├── Tool Call Trace
├── Evidence
├── Retry / Recovery
└── Final Decision
```

协议状态、业务状态和审计状态应分离设计，避免把长期任务上下文继续隐式保存在 MCP Server 内存中。

### Workflow 与安全治理

Coding Agent 能修改 Workflow 后，应增加：

- Workflow 文件变更单独审批；
- 第三方 Action 固定 Commit SHA；
- 最小化 `GITHUB_TOKEN` 权限；
- Fork 与外部贡献者默认只读；
- Agent 修改流水线后强制人工确认。

## 9. 今日实战

### 给 MCP Server 增加无状态兼容性测试

最小测试集：

1. 连续两次调用不共享服务端内存状态；
2. 每次请求均携带用户、任务和权限上下文；
3. 请求重试不会产生重复写入；
4. 并发请求不会串用身份或业务数据；
5. 旧客户端可协商回退到兼容协议；
6. 每次 Tool Call 都可通过 `trace_id` 关联业务任务。

金融场景还应增加幂等键、业务流水号和操作审批状态。

## 10. Today Worth Thinking

MCP 无状态化降低了基础设施扩容复杂度，却把更多责任推向业务应用：身份必须显式传递，任务状态必须持久化，写操作必须幂等，审计链必须完整。

对金融 Agent 来说，真正需要测试的不是“能否调用工具”，而是：

- 是否以正确身份调用；
- 是否在正确业务范围内调用；
- 重试是否会重复执行；
- 不同任务是否发生上下文串扰；
- 最终结果是否有业务证据支持。

## 11. 30 分钟 Action

为现有 MCP Tool 增加一个幂等与追踪请求头规范：

```text
X-Task-Id
X-Trace-Id
X-Idempotency-Key
X-User-Id
X-Business-Scope
X-Approval-Id
```

随后使用同一请求重复调用两次，验证不会产生重复数据，并确认日志能够完整关联到同一任务。

```text

安全准入
├── 身份与授权
```
