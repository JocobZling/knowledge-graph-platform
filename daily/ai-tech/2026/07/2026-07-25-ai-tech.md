# AI 与 Agent 每日简报 v2 - 2026-07-25

## 1. 今日摘要

今天的高价值新增并不多，但方向非常集中：模型竞争继续从单轮回答能力转向长任务执行能力；与此同时，企业开始把 Agent 质量保障拆解为上线前门禁、生产监控、静默失败识别和业务结果校验。

Anthropic 于 7 月 24 日发布 Claude Opus 5，官方平台信息显示其支持 100 万 Token 上下文、最高 12.8 万 Token 输出，并保持 Opus 4.8 的价格水平；AWS 和 GitHub 同日完成接入，重点强调复杂编码、长时间运行 Agent、多工具协同和错误恢复能力。

更值得测试开发团队关注的是 AWS 近期公开的生产实践：Motorway 通过“工具使用—推理—输出质量”三层评测，将错误结果从约 1/8 降到 1/50；AgentCore 进一步开始识别“系统状态正常但业务结果错误”的静默失败。这些方法比单纯比较模型 Benchmark 更接近企业 Agent Testing 的真实需求。

## 2. AI / 大模型 Top News

### 2.1 Claude Opus 5 发布：长任务执行成为核心卖点

Claude Platform 于 7 月 24 日上线 `claude-opus-5`。公开规格包括：

- 100 万 Token 上下文窗口；
- 最高 12.8 万 Token 输出；
- 默认启用思考能力；
- API 价格为每百万输入 Token 5 美元、输出 Token 25 美元，与 Opus 4.8 一致；
- 面向复杂编码、长文档分析、知识工作和长时间运行 Agent。

**实质新增点：** 重点不是上下文数字本身，而是模型被明确定位为可持续运行数小时、遇到障碍后调整策略并继续完成任务的执行模型。

**对 Agent Testing 的影响：** 模型评测需要增加长任务成功率、连续工具调用正确率、恢复次数、无效执行开销和中途目标偏移等指标。

来源：https://platform.claude.com/docs/en/release-notes/overview

### 2.2 Claude Opus 5 同日进入 GitHub Copilot

GitHub 于 7 月 24 日将 Claude Opus 5 接入 Copilot。GitHub 的早期测试重点提到：自主代码修改、回归验证、多工具协调、针对性修改和减少无效执行开销。

**实质新增点：** 模型发布后立即进入真实 Coding Agent 工作流，而不是只提供聊天入口。

**实践价值：** 测试团队可以围绕同一仓库任务比较不同模型在以下方面的差异：

- 是否准确识别修改范围；
- 是否主动补充回归验证；
- 是否产生无关代码变更；
- 是否能够处理失败检查并重新修复；
- 单次成功任务成本。

来源：https://github.blog/changelog/2026-07-24-claude-opus-5-is-now-available-in-github-copilot/

### 2.3 AWS 发布生产 Agent 三层评测与五阶段质量门禁

AWS 与 Motorway 公布了一套可落地的 Agent 评测体系。该体系将 Agent 质量拆分为三层：

1. 工具使用：工具选择和参数传递，建议门槛高于 95%；
2. 推理质量：逻辑决策和任务推进，建议门槛高于 85%；
3. 输出质量：准确性和帮助程度，建议门槛高于 90%。

部署流程则包括构建期评测、预发布验证、影子模式、A/B 测试和生产发布。案例中，错误结果从约 1/8 降低至 1/50，问题发现时间从数小时缩短到数分钟。

**实质新增点：** Agent Evaluation 被正式放入 CI/CD 门禁，而不是发布后的附属分析。

**对智能测试平台的影响：** 可以直接映射为“工具调用确定性校验 + 推理评审 + 业务结果核验”三层测试架构。

来源：https://aws.amazon.com/blogs/machine-learning/evaluating-ai-agents-a-production-blueprint-with-strands-and-agentcore/

### 2.4 AgentCore 开始识别静默失败

AWS 提出的静默失败是指：调用链完成、延迟正常、错误码为零，但业务结果仍然错误，例如库存接口超时后 Agent 仍声称有货，或审批步骤被跳过。

AgentCore Optimization 基于生产 Trace 分析行为正确性和策略合规性，定位失败发生位置、生成原因说明，并将相似失败聚类，判断是大面积模式还是少量边缘案例。

**关键意义：** Agent 的“技术成功”不等于“业务成功”。

**对金融测试的影响：** 清算核对、账务查询等 Agent 必须把业务断言作为独立成功条件，不能仅依据 SQL 执行成功或接口返回 200 判断任务完成。

来源：https://aws.amazon.com/blogs/machine-learning/detecting-silent-agent-failures-with-amazon-bedrock-agentcore-optimization/

## 5. Agent Ecosystem

### 本周最值得体验：Strands Agents Evals

Strands Agents 的评测框架支持：

- 输出校验；
- 工具轨迹评测；
- 多轮对话模拟；
- 自动实验生成；
- 确定性评分和 LLM-as-judge；
- 自定义业务 Evaluator。

今天最值得体验的不是重新写一个 Agent，而是为已有 Agent 增加一个 `Case + Evaluator`，把工具选择、参数和最终业务结果分别评分。

### Agent 实践启发：用业务成功覆盖技术成功

建议统一任务状态：

```text
TECHNICAL_SUCCESS
├── 模型调用成功
├── Tool 调用成功
└── 流程正常结束

BUSINESS_SUCCESS
├── 业务断言成立
├── 证据完整
├── 无越权或跳步
└── 结果可复核
```

只有两类状态同时满足，任务才应标记为最终成功。

### MCP 与 Workflow 观察

MCP 解决工具接入标准化，但无法自动保证业务正确性。企业 MCP Gateway 后续应同时提供：权限策略、参数校验、调用 Trace、结果断言和风险升级，而不应只做协议转发。

## 7. 企业实践

### Motorway：把评测变成发布门禁

**企业做法：** 对车辆搜索 Agent 建立工具、推理和输出三层评测，并在构建、预发布、影子流量和生产阶段持续执行。

**效果：** 错误结果由约 12.5% 降到约 2%，问题发现时间从数小时降到数分钟。

**可借鉴点：**

- 单次通过不能代表稳定，通过 `pass^k` 检查连续成功；
- 生产失败应自动转成新的回归测试用例；
- 先用 1%—5% Trace 抽样控制评测成本；
- 确定性规则负责工具和参数，LLM Judge 负责推理和语义质量。

### Jefferies：金融交易助手采用 MCP 与知识库组合

AWS 于 7 月 23 日公布 Jefferies 前台交易助手实践。方案使用 Strands Agents、Amazon Bedrock、Knowledge Bases 和 MCP，将模型推理、企业知识和外部工具连接起来。

**可借鉴点：** 金融 Agent 不应直接面对所有系统，应通过受控工具层和统一协议连接数据源；知识检索、工具执行和最终业务校验需要分层处理。

来源：https://aws.amazon.com/blogs/machine-learning/category/artificial-intelligence/amazon-machine-learning/

## 9. 今日实战

### 给清算核对 Agent 建立三层质量门禁

第一层：工具与参数

- 是否查询正确数据库；
- 商户号、清算日期是否准确；
- 是否只执行只读 SQL；
- 查询步骤顺序是否符合规则。

第二层：推理与流程

- 是否正确从汇总表取得汇总流水号；
- 是否按流水号反查清分明细；
- 是否处理空记录、重复记录和跨日数据；
- 异常后是否停止而不是自行猜测。

第三层：业务结果

- 金额计算是否与确定性程序一致；
- 汇总金额与明细金额是否匹配；
- 最终结论是否附带记录数、流水号和差异证据；
- 未通过业务断言时不得输出“核对成功”。

## 10. Today Worth Thinking

Agent Testing 的关键不是证明模型“通常能完成”，而是证明在真实业务约束下，它能够稳定、可解释、低成本地完成。

传统自动化测试把成功定义为接口返回和断言通过；Agent 测试则必须同时评估路径和结果。尤其在金融场景中，一个 Agent 即使最终金额碰巧算对，但查询了错误主体、跳过审批或使用了越权数据，也不能视为成功。

因此，未来智能测试平台需要从测试执行平台升级为 Agent 行为质量平台：既验证模型输出，也验证工具调用、轨迹顺序、业务断言、风险策略和连续稳定性。

## 11. 30 分钟 Action

今天可为清算核对场景新增一个最小 Evaluator：

```python
def evaluate_settlement_result(agent_result: dict, expected: dict) -> dict:
    checks = {
        "merchant_match": agent_result.get("merchant_no") == expected["merchant_no"],
        "settle_date_match": agent_result.get("settle_date") == expected["settle_date"],
        "summary_serial_match": agent_result.get("summary_serial") == expected["summary_serial"],
        "amount_match": agent_result.get("calculated_amount") == expected["calculated_amount"],
        "evidence_complete": bool(agent_result.get("evidence")),
    }
    return {
        "passed": all(checks.values()),
        "checks": checks,
    }
```

先使用确定性程序判定结果，再考虑加入 LLM Judge 评价解释质量。

## 13. 我的备注

结合你目前的金融测试台和 Agent Testing 方向，建议将“成功状态双层判定”作为下一步最小落地点：

```text
工具执行成功
    ↓
流程轨迹合规
    ↓
确定性业务断言通过
    ↓
证据完整可回放
    ↓
Agent 任务成功
```

这比先建设复杂的多 Agent 编排更有价值。它能够直接形成可验证的金融场景样例，也可以自然扩展为 MCP Server 准入、Agent 风险治理和智能测试平台质量门禁。
