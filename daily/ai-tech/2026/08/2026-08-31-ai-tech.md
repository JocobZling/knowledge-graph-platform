# AI 与 Agent 每日简报 v2

**日期：2026-08-31**

## 1. 今日摘要

近 24 小时没有检索到足够高价值的新旗舰模型或重大 Agent 产品发布，因此本期按规则扩展到最近 7 天，不用旧闻凑满“发布数量”。今天真正值得保留的主线，是 **Agent Runtime / Harness 正在从模型外壳变成独立工程层**。

Microsoft Agent Framework 最近新增 Python Channels：同一个 Agent / Workflow 可以通过 OpenAI Responses、Telegram、A2A、MCP 暴露，而身份映射、授权、Session、并发、Checkpoint 和部署仍由应用自己控制。这个边界非常重要：Channel 负责协议转换，不替业务系统做安全决策。

研究与开源侧，Prime Agent 提出 Self-Improving RLM Harness：使用持久 IPython REPL、递归子 Agent、跨轨迹保留的 memory / skill / prompt / subagent specification，以及可记录、可回滚的 Continual Harness refinement。它代表 Agent 的“上下文管理”正在从不断扩大 Prompt，转向把信息、计算、技能和历史放到 Harness 层管理。

同时，最新开放式 AI Research 研究继续表明：Agent 已经可以完成部分端到端研究任务，但真正难点不只是模型智力，而是 Harness 是否能稳定提供执行、恢复、验证、资源控制和独立评测。

去重方面，已核对仓库最近日报。8 月 29 日已重点报道 Agent Improvement / Organization Agent，8 月 30 日已重点报道 Model Supply Resilience、Metacognitive Check 和 Source Provenance；今天不重复这些主线。仓库搜索未发现独立 ai-tech 主题索引文件。

## 2. AI / 大模型 Top News

### 2.1 Microsoft Agent Framework Channels：Agent 与“入口”正式解耦

Microsoft 新增 `agent-framework-hosting` 及 Responses、Telegram、A2A、MCP Channel 包。同一个 Agent 或 Workflow 可以通过多个协议暴露，而不需要为每个入口维护一套 Agent 实现。

核心结构变成：

```text
Responses / Telegram / A2A / MCP
              ↓
        Channel Adapter
              ↓
     Agent / Workflow State
              ↓
       Business Runtime
```

但 Microsoft 明确把身份关联、Authorization、Session ID 映射、并发控制、Checkpoint Store 等留给应用层。

官方来源：https://devblogs.microsoft.com/agent-framework/introducing-agent-and-workflow-channels/

对 Agent Testing 最直接的启发是：同一个 Agent 必须做 **Cross-channel Consistency Test**，而不是只在 Web Chat 里测一次。

### 2.2 Prime Agent：长任务 Agent 开始拥有独立 Harness 状态

Prime Agent 将 RLM（Recursive Language Model）和 Continual Harness 组合起来：持久 IPython 负责程序化信息处理和 test-time compute，子 Agent 可以递归生成并直接通信，Harness 则保存历史、Memory、Skill、Prompt 与 Subagent Specification。

更值得关注的是 `/refine`：Agent 可以基于执行证据对 supplemental harness state 做小幅更新，但不会修改 immutable base system prompt，并保留 snapshot 支持回滚。

论文：https://arxiv.org/abs/2608.23552
GitHub：https://github.com/PrimeIntellect-ai/prime-agent

这比“让 Agent 自动改自己的 Prompt”更接近可治理的持续改进：

```text
Trajectory
→ Evidence
→ Candidate Refinement
→ Snapshot
→ Eval
→ Keep / Rollback
```

### 2.3 开放式 AI Research：评测对象正在从答案变成完整研究轨迹

近期更新的研究《Can AI agents conduct open-ended AI research?》通过真实开放式研究任务考察 Agent 能否进行问题理解、实验、分析和结果产出。它与近期 AutoResearchEval 的共同信号是：Research Agent 已经不能只用最终答案准确率衡量。

更合适的评测对象逐渐变成：

```text
Question
→ Research Plan
→ Evidence / Experiment
→ Tool Trace
→ Analysis
→ Revision
→ Final Artifact
```

论文：https://arxiv.org/abs/2607.27191

对测试平台而言，这意味着未来 Eval Dataset 不只是 Input / Expected Output，而可能需要保存 **Expected Process Constraints + Evidence Requirements + Artifact Assertions**。

### 2.4 Agent Harness 正成为模型能力评测的一部分

Prime Agent 论文特别强调：Harness failure 不应该被误判成 Model failure。执行环境、Context 管理、Recovery、Verification、资源核算都会直接影响长任务最终表现。

这使模型评测需要拆成两层：

```text
Model Capability
+
Harness Capability
=
Observed Agent Performance
```

同一个模型换 Harness 后结果可能明显变化，因此以后做模型横向比较时，必须固定 Harness 版本，或者明确记录 Harness Diff。

## 3. 科技行业动态

### 3.1 Multi-channel Agent 会把身份问题重新放大

当一个 Agent 同时服务 Telegram、Responses、A2A、MCP 时，“同一个人”可能对应多个 Channel Identity。

必须明确：

```text
Channel Identity
→ Canonical User
→ Session
→ Permission Scope
```

如果 Identity Mapping 错误，风险不只是聊天记录串线，还可能出现 Memory、Tool Permission 和业务数据跨用户污染。

### 3.2 企业 AI-native 转型开始暴露组织层面的现实边界

Reuters 8 月 26 日披露 Meta 的 Project OT：公司曾研究大幅压缩部分团队、让 AI 承担更多日常工作，但内部阻力和执行问题使后续裁员计划被叫停。该报道不是“AI 无效”的证据，更值得关注的是：AI Agent 的组织价值不能简单用“可替代多少岗位”衡量。

企业真正需要测的是：任务可自动化比例、异常升级率、人工 Review 成本、错误恢复成本，以及 Agent 失败时组织是否仍保留必要能力。

来源：https://www.reuters.com/investigations/mark-zuckerberg-had-bold-plan-replace-meta-staff-with-ai-heres-how-it-imploded-2026-08-26/

## 5. Agent Ecosystem

### 本周最值得体验：Cross-channel Session Test

给同一个测试 Agent 暴露两个入口，例如 Responses + MCP，构造：

```text
Channel A 登录 user-001
→ 建立 Session
→ 写入一条非敏感 Memory

Channel B 登录 user-001
→ 是否正确恢复同一业务上下文？

Channel B 登录 user-002
→ 是否完全隔离？
```

重点记录：`canonical_user_id`、`channel_identity`、`session_id`、`permission_scope`、`memory_scope`。

### Agent 实践启发：Harness 必须进入版本基线

以后 Agent Baseline 不应只有：

```text
model + prompt
```

建议至少升级成：

```text
model
+ harness_version
+ skill_set
+ tool_set
+ memory_policy
+ session_policy
+ eval_suite
```

否则一次 Harness 升级导致的结果变化，很容易被错误归因到模型。

### Workflow 治理：Refinement 只能修改“可修改层”

可以借鉴 Prime Agent 的边界：Base Policy / Permission / Golden Eval 不允许 Agent 自己改；Memory、Skill Description、Supplemental Prompt 可以产生 Candidate，但必须经过 Eval 和 Rollback Gate。

## 7. 企业实践

### Meta：AI-native 组织改造不能跳过可验证的工作拆分

Reuters 披露的 Project OT 计划曾设想让 AI 接管大量日常工作，由更小的人类团队监督虚拟工作者；但内部执行和组织阻力使部分后续计划被取消。

对企业更可借鉴的不是裁员比例，而是上线前先建立：

```text
Task Inventory
→ Automation Candidate
→ Agent Pilot
→ Quality / Escalation Metrics
→ Human Capacity Check
→ Gradual Rollout
```

如果没有这层验证，组织很容易把“模型 Demo 能做”误判成“生产流程可以稳定无人化”。

## 9. 今日实战

给现有 Agent Trace 增加 Channel 与 Harness 字段：

```yaml
agent_run_id: run-001
channel: mcp
channel_identity: client-017
canonical_user: user-001
session_id: session-882

model: model-x
harness_version: 1.4.0
skill_set: skill-baseline-v3

```

然后把同一 Case 从两个入口各跑一次。

关键断言：

```text
Business Result = Same
Permission Scope = Same
User Isolation = Pass
Unexpected Tool Call = 0
```

## 10. Today Worth Thinking

真实生产表现更接近：


```yaml
agent: log-risk-reviewer
```

## 13. 我的备注

结合金融测试、Agent Testing 和智能测试平台，今天最值得补的一层不是新的 Agent，而是 **Agent Runtime Baseline**。

现在很多 AI 测试很容易记录：

```text
模型版本
Prompt 版本
准确率
```

但未来真正影响结果的变量会越来越多：

```text
Channel
Identity Mapping
Session
Memory
Skill
MCP / Tool
Harness
Checkpoint
Retry
Model
```

因此智能测试平台可以逐渐把一次 Agent Run 看成一个完整的软件运行实例：

```text
Runtime Manifest
      ↓
Agent Run
      ↓
Tool / A2A / MCP Trace
      ↓
Business Assertion
      ↓
Evidence
      ↓
Result Diff
```

对金融场景尤其建议先补两类测试。

第一类是 **Cross-channel Identity Test**。以后同一个业务 Agent 可能从内部门户、IM、MCP、API 甚至其他 Agent 进入，必须证明不同入口不会导致用户、Session、Memory 或权限串线。

第二类是 **Harness Regression Test**。Workflow 编排、Skill、Memory Policy、Tool Schema 任一变化，都应该像代码依赖升级一样触发回归，而不是只在换模型时才跑 Eval。

这和传统测试开发其实非常接近：过去我们固定应用版本、数据库版本、中间件版本再比较结果；未来只不过再多固定一层 Agent Runtime。

真正可持续的 Agent Testing，不是不断追最新模型，而是能够回答：**在完全可追溯的运行基线下，这个 Agent 为什么成功、为什么失败、换了哪一层之后发生了什么变化。**
