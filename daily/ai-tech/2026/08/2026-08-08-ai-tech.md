## 2. AI / 大模型 Top News

### 2.1 Prime Agent：可持续改进的Agent Harness进入开源实践

Prime Intellect近期发布并开源 Prime Agent。它不是新的基础模型，而是面向编码、研究和长时自主任务的Agent Harness。

核心机制包括：

- Persistent IPython：把Python环境作为长期控制平面；
- Programmatic Tool Calling：文件、Shell、Tool和子Agent通过代码组织；
- `rlm(...)`：可启动真实子Agent并行或后台工作；
- Continual Harness：将补充Prompt、Memory、Skill描述和子Agent规范保存为可持续状态；
- `/refine`：根据当前轨迹进行小范围、可审查、可回滚的Harness改进；
- Goal / Heartbeat / Schedule / Autonomous Mode：支持跨会话长任务持续运行。

官方仓库同时明确警告：Prime Agent使用当前用户权限执行模型生成的Python和项目命令，其Worker和Kernel只提供生命周期隔离与恢复能力，**不是安全Sandbox**。

来源：
- https://github.com/PrimeIntellect-ai/prime-agent

这对企业Agent平台很重要：Harness开始从“胶水代码”变成需要单独版本管理、评测和安全准入的一等资产。

### 2.2 ARC-AGI-3研究继续证明：Harness可以显著改变同一模型的Agent表现

近期论文《Tycho: Active Abstraction with Programmatic World Models for ARC-AGI-3》研究让Coding Agent在交互中构建可执行世界模型，并动态决定何时构建、验证、修复、使用或绕过模型。

论文报告，在其公开集实验条件下，GPT-5.6 Sol与Opus 5均完成全部183个公开关卡并达到100 RHAE；作者同时强调，世界模型“更准确”并不自动等于下一步行动更好，真正关键的是Agent能否判断什么时候值得建模和验证。

来源：
- https://arxiv.org/abs/2607.28287

另一项消融研究也发现，验证处理在多个模型/推理强度组合中排名最高，但需要更多资源；基础模型强度与推理预算仍然具有显著影响。

来源：
- https://arxiv.org/abs/2607.15439

对Agent Testing的关键启发是：

```text
Agent能力
= Model
× Harness
× Context Policy
× Tool
× Verification
× Environment
```

因此，比较两个Agent版本时不能只记录Model ID。

## 3. 科技行业动态

### 3.1 模型竞争开始向Harness竞争外溢

ARC-AGI-3近期结果说明，Agent表现越来越依赖模型外围系统。Harness负责决定：

- 上下文如何保留和压缩；
- 何时调用子Agent；
- 是否构建外部Memory；
- 如何验证中间结论；
- 失败后如何修复策略；
- 何时继续自主运行、何时停止。

因此未来企业评测榜单最好同时标记 `model + harness + toolset + policy + environment`，否则不同Agent结果很难公平比较。

### 3.2 “实验闭环自动化”正在成为Agent的重要落地方向

Discovery Loop代表的方向与Coding Agent非常相似：Agent不是一次生成答案，而是不断进行实验、观察结果、更新假设和继续执行。

这种模式也适合测试工程：

```text
生成测试假设
→ 准备数据
→ 执行
→ 获取系统证据
→ 判断失败原因
→ 调整下一轮测试
```

真正需要治理的不是单次生成质量，而是整个反馈循环是否逐步收敛到正确目标。

## 5. Agent Ecosystem

### 本周最值得体验：Prime Agent 的 Harness / Refine 思路

建议不要直接用于敏感项目，先在一次性测试仓库中体验：

```text
固定模型
→ 执行同一任务
→ 保存轨迹
→ /refine
→ 再次执行
→ 对比成功率、Tool轨迹、Token和风险行为
```

真正值得观察的是：Harness更新后，能力提高来自哪里，以及是否同时引入新的权限或行为风险。

### Agent实践启发：Harness也应该有版本号

建议把Agent Manifest扩展为：

```yaml
agent: settlement-check-agent
model: gpt-x
harness_version: 1.4.2
context_policy: compact-v3
skills_version: 2026.08.08
toolset_version: finance-readonly-v5
sandbox_policy: restricted-v2
eval_suite: settlement-agent-v7
```

如果Harness可以通过轨迹持续自我调整，那么每次Refine都应形成可审计Diff，而不是静默修改生产行为。

### Workflow治理：自我改进必须有边界

允许Agent修改Memory和Skill描述，与允许它修改权限、安全策略或基础System Prompt完全不同。

建议分层：

- 可自动优化：Memory、检索策略、低风险经验；
- 需回归测试：Skill、子Agent配置、Prompt策略；
- 禁止自主修改：身份、权限、网络策略、审批规则、安全边界。

```text
风险/缺陷假设
→ 测试设计
→ 数据准备
→ 自动执行
→ 证据采集
→ 根因候选

```

但每一轮都必须保留确定性断言和停止条件，避免Agent为了“继续探索”无限扩大测试范围。

## 9. 今日实战

### 给Agent评测记录增加Harness Fingerprint

```python
import hashlib
import json


def harness_fingerprint(config: dict) -> str:
    payload = json.dumps(config, sort_keys=True, ensure_ascii=False)
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()[:16]


config = {
    "model": "model-x",
    "harness_version": "1.4.2",
    "skills": ["sql-readonly", "report-check"],
    "context_policy": "compact-v3",
    "toolset": "finance-readonly-v5",
}

print(harness_fingerprint(config))
```

每次评测把Fingerprint与结果、Trace一起保存。只要Harness、Skill或Toolset变化，就不能继续把结果当作完全相同的Agent版本。

## 10. Today Worth Thinking

过去我们常把Agent性能归因于模型：

> 换一个更强模型，Agent就会更强。

ARC-AGI-3近期结果越来越清楚地提示另一件事：**模型能力只是上限的一部分，Harness决定能力能否被稳定释放。**

这也意味着Agent安全不能只审模型。一个安全性相对稳定的模型，被放进拥有持久Memory、并行子Agent、Shell和自我改进能力的Harness后，整体风险边界已经发生变化。

## 13. 我的备注

结合金融测试、Agent Testing和智能测试平台，近期最值得补的一层不是继续堆模型，而是建立 **Agent Configuration Baseline**：

```text
Agent版本
├── Model
├── System Prompt
├── Harness / Workflow
├── Skills
├── MCP / Tools
├── Context / Memory
├── Sandbox / Permission
└── Eval Suite
```

这可以直接解决Dify工作流测试中一个很实际的问题：为什么两次看起来使用同一个模型，结果却明显不同？

如果只比较最终输出，很难判断差异来自召回、Prompt、模型随机性、Tool返回还是Workflow变化。把Harness和上下文策略也纳入版本后，每次评测就可以形成：

```text
Configuration Diff
→ Trace Diff
→ Result Diff
→ Root Cause
```

对金融Agent尤其重要：允许Agent根据历史失败“学习”是有价值的，但所有学习结果必须可见、可回滚、可回归测试，且绝不能自主扩大数据库、网络或交易权限。
