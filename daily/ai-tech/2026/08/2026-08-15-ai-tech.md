## 2. AI / 大模型 Top News

### 2.1 NVIDIA SkillSpector 2.9.4：MCP 与 Skill 安全边界继续前移

SkillSpector v2.9.4于8月13日发布。该版本重点强化HTTP暴露的MCP扫描服务：远程调用方不能再指定扫描器宿主机的本地文件路径或本地YARA目录；同时拒绝Skill目录中的符号链接内容，并在Git克隆输入时关闭symlink materialization。

新增检测还包括：

- 用大量空白隐藏Prompt Injection指令；
- Skill中携带Python字节码或`__pycache__`；
- 高影响风险的最低评分约束；
- 对`allowed-tools`最小权限声明的更明确支持。

实质变化是：Skill安全不再只是“看文档和代码”，而是逐渐形成 **扫描 -> 风险修复 -> 权限声明 -> 签名 -> 发布** 的供应链门禁。

官方项目：https://github.com/NVIDIA/SkillSpector
官方发布：https://github.com/NVIDIA/SkillSpector/releases/tag/v2.9.4
官方文档：https://docs.nvidia.com/skills/agent-skill-trust-pipeline

### 2.2 SkillSentry：Agent Skill 需要 Runtime Assurance，而不是一次性验收

8月10日提交的论文《SkillSentry: Reliable Skill Execution for LLM Agents via Runtime Assurance》指出，即使Agent具备完成某个Skill的能力，也可能在类似任务或重复运行中偏离Skill步骤、遗漏关键动作或错误执行子步骤。

SkillSentry通过DSL表达Skill运行时指导，并结合Skill规格与历史成功/失败轨迹，对Agent执行过程持续监测与纠偏。论文在15个Skill、两类Agent和多种模型组合上的实验中报告，平均任务成功率提升24.1%，且重复运行方差下降。

这里真正值得企业借鉴的不是论文中的具体提升数字，而是测试对象变化：

`Skill Definition -> Skill Execution Trace -> Runtime Deviation -> Corrective Guidance`

论文：https://arxiv.org/abs/2608.09253

### 2.3 AEROBAT：Agent Testing开始尝试自动生成行为假设与实验

AEROBAT是一套自动化Agent行为科学研究的多Agent系统。用户指定目标行为后，它可以自动执行：假设生成、实验设计、控制实验、行为评估、统计分析和报告生成。

论文针对12类目标行为生成并验证79个假设，共设计1240个受控实验、执行23512轮模拟。研究重点并不是证明某个Agent“更好”，而是展示 **Agent行为研究本身也可以被自动化和规模化**。

这对Agent Testing很有启发：未来测试平台不一定只接收人工写好的测试集，也可以根据历史Trace和失败模式自动生成新的行为假设和对照实验。

论文：https://arxiv.org/abs/2608.10030

### 2.4 多Agent训练出现“Simulator Collapse”：单一模拟用户会让Agent学偏

8月12日提交的论文《One Frozen Simulator Is Not Enough》研究多轮人机交互Agent训练中的Simulator Collapse：如果训练长期依赖单一LLM模拟用户，策略会过拟合该模拟器的主导行为模式，在新的模拟器或真实用户上泛化变差。

作者提出Verbalized Sampling和多模拟器Co-Training，并在三个多轮Benchmark中报告更好的held-out表现。

对企业最重要的启发是：

> Agent测试不能长期只依赖一个“标准模拟用户”。

应该至少加入不同模型、不同Persona、不同输入分布和真实历史样本，避免测试集本身变成Agent可以“刷分”的固定环境。

论文：https://arxiv.org/abs/2608.12253

## 3. 科技行业动态

### 3.1 Skill 正在从 Prompt Asset 变成 Software Supply Chain Asset

Skill通常同时包含说明、脚本、依赖、Tool权限、远程资源和执行逻辑。它的风险结构越来越接近软件包，而不是普通Prompt。

企业后续更合理的Skill生命周期应是：

`Author -> Scan -> Review -> Sign -> Publish -> Runtime Monitor -> Revoke`

其中静态扫描只能覆盖一部分问题，运行时Trace和行为偏差检测必须补上。

### 3.2 Agent Evaluation 从“固定测试集”走向“主动实验”

AEROBAT与Simulator Collapse研究共同指向一个趋势：高质量Agent评测不仅需要更多Case，更需要 **实验设计能力和测试环境多样性**。

Agent Testing未来可能增加：

- 自动生成行为假设；
- 对照组/实验组；
- 多模拟用户；
- 重复运行稳定性；
- Trace偏差分析；
- 自动扩展失败样本。

## 5. Agent Ecosystem

### 本周最值得体验：给一个Skill做“静态扫描 + 运行时回归”

不要只运行一次SkillSpector后就结束。选一个带脚本或Tool调用的Skill，做两层验证：

1. 静态层：Prompt Injection、依赖、权限、远程资源、MCP风险；
2. 运行层：重复执行10次，记录步骤完成率、Tool调用序列、参数漂移和失败位置。

如果静态扫描完全通过，但同一任务10次出现不同执行路径，就说明“安全”和“可靠”是两个不同问题。

### Agent 实践启发：Skill版本变更应该触发Trace Regression

建议Skill Manifest至少记录：

```yaml
skill_name: log-risk-review
skill_version: 1.3.0
allowed_tools:
  - log.read
  - report.write
scanner_result: passed
runtime_baseline: trace-set-v5
```

Skill文件、脚本、依赖、`allowed-tools`任一变化后，除静态扫描外，还应重跑Runtime Baseline。

### Workflow治理：把Skill偏差定义成可观测事件

可以增加三类事件：

- `STEP_SKIPPED`：预期步骤未执行；
- `UNEXPECTED_TOOL_CALL`：调用不在Skill声明中的Tool；
- `ORDER_DEVIATION`：步骤顺序偏离关键流程。

它们比只记录最终PASS/FAIL更适合定位Agent不稳定。

### NVIDIA：把Skill发布拆成扫描、声明、签名和验证

NVIDIA当前公开的Agent Skill Trust Pipeline要求Skill发布前至少完成：窄化用途和权限、运行SkillSpector、修复或记录高风险发现、补充Skill Card、对已审核目录进行OMS签名，并随发布包提供扫描报告、评测数据、Benchmark报告与验证说明。

## 9. 今日实战

给Skill增加最小运行时断言：

```yaml
skill: log-risk-review
required_steps:
  - load_scan_result
  - load_context
  - ai_review
  - persist_decision
forbidden_tools:
  - shell.exec
  - external_http
max_retry_per_step: 2
```

运行10次后统计：

- Required Step Completion Rate；
- Unexpected Tool Call Rate；
- Retry Distribution；
- Final Business Assertion。

最终结果正确但步骤经常偏离，也应该进入风险列表。

## 10. Today Worth Thinking

企业很容易把Skill理解为“可复用Prompt”。但一旦Skill能够调用MCP、Shell、HTTP、文件系统或数据库，它实际上已经接近一个 **可执行的软件组件**。

真正的问题因此从：

> 这个Skill写得好不好？

变成：

> 这个Skill声明的能力、实际执行的能力和运行时行为是否始终一致？

## 11. 30分钟 Action

今天选一个已有Codex/Claude/Dify Skill或MCP辅助流程，完成三件事：

1. 列出它真正需要的Tool；
2. 把额外Tool从权限中删掉；
3. 连续执行10次同一任务，记录Tool调用序列。

只检查两个指标：

- 是否出现未声明Tool；
- 关键步骤是否每次都执行。

如果10次结果都对，但Tool路径明显不同，也值得单独建问题跟踪。

## 13. 我的备注

结合金融测试、Agent Testing和智能测试平台，下一步可以正式增加一层 **Skill准入与运行时回归**。

建议结构：

`Skill Registry -> Static Scan -> Permission Review -> Test Run -> Trace Baseline -> Publish -> Runtime Monitor`

其中金融场景可以给Skill分三级：

- L1：纯分析，无外部Tool；
- L2：只读Tool，例如查询日志、数据库、文档；
- L3：写操作、外网、Shell、任务创建、状态变更。

L1可以以自动扫描为主；L2增加数据边界和Tool回归；L3必须增加人工审批、幂等、Kill Switch和运行时监控。

对于现有日志AI精筛场景尤其适合：规则扫描、AI复核、结果落库本来就已经是一条Skill-like Workflow。可以把“规则失败后AI跳过”“白名单导致AI跳过”“AI执行失败”等状态转换为明确步骤，再通过Trace验证每种状态路径是否真的按照预期执行。

这样智能测试平台后续不仅能回答“模型是否准确”，还可以回答：

> Skill有没有越权？有没有漏步骤？不同模型下执行路径是否稳定？升级后有没有出现新的行为偏差？

这会比单纯管理Prompt版本更接近真正的Agent工程治理。
