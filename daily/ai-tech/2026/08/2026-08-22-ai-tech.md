# AI 与 Agent 每日简报 v2

**日期：2026-08-22**

## 1. 今日摘要

近 24 小时最值得关注的新变化，是 Agent 正从“完成一次任务”继续向“长期存在、等待事件、记住过去并持续行动”演进。

8 月 21 日，Anthropic 宣布把 Claude Mythos 5 的高级网络安全能力扩大给更多防御者：Mythos 5 已进入 Claude Security，并计划集成到合作伙伴的网络安全产品；同时设立 3500 万美元基金支持开源软件安全，并继续扩展 Cyber Verification Program。其核心治理思路是把“直接访问高能力模型”和“只获得补丁、告警等防御性结果”区分开来，以缩小高风险能力的暴露面。

另一条更贴近 Agent 工程的主线来自 Cursor 和 UiPath。Cursor 8 月 19 日更新 Cloud Agents：Agent 可以订阅 PR、Slack Thread 或定时事件，被事件唤醒后继续工作；`/goal` 允许它长期保持目标，Subagent 则在独立 VM 和干净上下文中运行。UiPath 同日推出 Agent Memory Preview，包括 Episodic Memory 和 Escalation Memory，并允许多个 Agent 共享 Memory Space。

这意味着 Agent Testing 需要新增一个过去不突出的对象：**Persistent Agent Reliability——一个 Agent 运行数小时、数天甚至跨多次唤醒以后，目标、身份、权限、记忆和状态是否仍然正确。**

最近 7 篇日报已覆盖 Skill 供应链、Multi-Agent 监督、Policy Gate、A2A、Runtime Monitoring、Control Effectiveness、Browser/Computer Agent 与 Harness Engineering；今天不重复这些主题，主线转向 **Persistent Agent + Memory Governance**。

## 2. AI / 大模型 Top News

### 2.1 Anthropic 扩大 Claude Mythos 5 的防御性网络安全能力

8 月 21 日，Anthropic 宣布 Claude Mythos 5 已进入 Claude Security，并将逐步集成进合作伙伴的网络安全工具。Anthropic 同时宣布 3500 万美元开源软件安全基金，并计划扩大 Cyber Verification Program。

官方来源：https://claude.com/blog/bringing-claude-mythos-5-to-more-defenders

最值得关注的不是单一模型能力，而是 Anthropic 对能力暴露面的拆分：高风险场景下，用户不一定获得模型的自由交互能力，而可以只获得漏洞补丁、安全告警等特定防御结果。

可以抽象成：

```text
Frontier Capability
      ↓
Risk Classification
      ↓
Direct Model Access / Restricted Output
      ↓
Verification
      ↓
Audit
```

这与企业 Agent 的 Safe Action 思路高度一致：不必把底层高权限 Tool 直接交给 Agent，而可以只开放经过约束的业务结果。

### 2.2 Cursor Cloud Agents 开始真正“等待事件再继续工作”

Cursor 8 月 19 日更新 Cloud Agents 与 Harness。Cloud Agent 现在可以订阅 PR、Slack Thread 和计划任务；当外部事件发生时重新唤醒并继续处理。它创建的 PR 还可以被 Agent 持续跟进，包括修复 CI 和处理 Bot Comment。

官方来源：https://cursor.com/changelog/08-19-26

同时新增 `/goal`，用于给 Agent 一个持续目标直到完成；Custom Mode 可以把 Skill 固定成长期 Playbook；运行中的 Agent 接收新指令时也不再立即打断当前动作，而是在下一次 Tool Call 边界处理 Steering。

这让 Agent 生命周期从：

```text
Prompt → Run → Result → End
```

变成：

```text
Goal
 ↓
Run
 ↓
Wait
 ↓
External Event
 ↓
Wake Up
 ↓
Resume
 ↓
Verify
```

测试重点随之改变：跨唤醒状态恢复、旧上下文污染、重复事件、事件乱序和目标漂移都需要单独验证。

### 2.3 UiPath 推出 Agent Memory：记忆开始成为平台级 Runtime 能力

UiPath 8 月 19 日发布 Agent Memory Preview。Episodic Memory 会检索语义相似的历史输入和执行结果并加入当前上下文；Escalation Memory 则会复用人类过去如何解决相似升级事件的经验，减少同类问题重复升级。

官方来源：https://docs.uipath.com/agents/automation-cloud/latest/release-notes/august-2026

Memory 被存储在独立 Memory Space 中，并可被多个 Agent 共享。

这意味着 Memory 不再只是“聊天记录”，而成为新的 Agent 基础设施：

```text
Experience
→ Memory Write
→ Retrieval
→ Context Injection
→ Decision
```

于是 Agent Testing 也需要覆盖：**写错记忆、召回错记忆、过期记忆、跨 Agent 泄漏、错误人工处置被永久学习。**

### 2.4 GitHub 的无人值守 Agent 开始展示“克制”比“多做事”更重要

GitHub Agentic Workflows 8 月 21 日公开的 Code Simplifier 日常 Agent，会每天从确定性候选列表中寻找低风险简化机会。值得注意的是，它会主动放弃范围过大或风险过高的候选，只处理能够验证的小改动，并执行语法和 Build 验证。

来源：https://github.github.com/gh-aw/blog/2026-08-21-agent-of-the-day/

这个案例最值得借鉴的不是自动改代码，而是一个长期无人值守 Agent 的设计原则：

> **成功并不等于每天必须产生变更；正确地决定“不做”也是成功结果。**

对于长期 Agent，这一点比单次任务成功率更重要。

## 3. 科技行业动态

### 3.1 Agent 正从 Session Runtime 进入 Persistent Runtime

过去多数 Agent 仍围绕一次会话设计。现在 Cursor 的 Subscription/Goal、UiPath Memory 等能力正在补齐长期 Agent 所需的几个基础设施：Event、Memory、State、Isolation、Recovery。

更完整的 Persistent Agent 结构可能是：

```text
Identity
  +
Goal
  +
Memory
  +
Event Subscription
  +
Runtime State
  +
Policy
  ↓
Persistent Agent
```

长期运行带来的风险并不是简单把一次执行风险乘以 N，而是会出现状态积累和历史影响。

### 3.2 Memory Governance 会成为 Agent Governance 的独立层

当 Agent 能把一次人工处置永久记住时，Memory 本身已经具备“改变未来行为”的能力。

因此至少需要管理：Memory Source、Owner、Scope、TTL、Confidence、Version、Delete/Correct、Audit。

尤其在企业环境中，“Agent 记住了什么”应当和“Agent 能调用什么 Tool”一样可查询、可删除、可审计。

## 5. Agent Ecosystem

### 本周最值得体验：Agent Wake-up / Resume Test

找一个支持长任务或后台 Agent 的环境，构造：

```text
开始任务
→ 执行到一半
→ WAIT
→ 外部事件
→ RESUME
```

恢复后只检查四件事：

1. Goal 是否仍然一致；
2. 已完成步骤是否被重复执行；
3. 身份与 Tool 权限是否发生变化；
4. 新事件是否覆盖了旧任务的正确状态。

### Agent 实践启发：Memory 必须有 Provenance

不要只保存：

```text
“这个问题以后直接跳过。”
```

至少保存：

```yaml
memory_id: mem-001
source: human-review
source_run: run-20260822-01
scope: log-review
confidence: high
created_at: 2026-08-22
expires_at: 2026-11-22
```

否则三个月后很难回答：这个 Agent 为什么会这样判断？

### Workflow 治理：长期 Agent 必须允许 No-op

无人值守 Agent 如果 KPI 是“每次都产生动作”，很容易主动制造不必要的变更。

因此结果状态应该允许：

```text
COMPLETED_WITH_CHANGE
COMPLETED_NO_ACTION
DEFERRED_HIGH_RISK
WAITING_EVENT
ESCALATED
```

而不是只有 SUCCESS / FAILED。

## 7. 企业实践

### GitHub：让长期 Agent 保持“小步、可验证、可以不做”

GitHub Agentic Workflows 的 Code Simplifier 每日运行，但并不要求每天必须改代码。它先从确定性候选集筛选低风险目标，遇到范围过大或风险不合适的改动直接放弃；真正修改后再做语法和 Build 验证。

这种设计可以抽象成：

```text
Scheduled Wake-up
      ↓
Candidate Set
      ↓
Risk / Value Filter
      ↓
No-op OR Small Action
      ↓
Deterministic Verification
      ↓
Human-reviewable Change
```

对企业 Agent 来说，“主动克制”是长期无人值守的关键能力。

## 9. 今日实战

给现有 AI 精筛或 Agent Workflow 增加一个最小“经验记忆”实验。

不要直接让 Agent 自动学习所有历史结果，只选择 10 条人工确认的高置信案例：

```yaml
memory_source: human_confirmed
memory_scope: address_false_positive
confidence: high
ttl_days: 30
```

下一轮遇到相似案例时，让系统同时输出：

```text
当前模型判断
召回的历史 Memory
最终判断
```

先观察 Memory 到底是在帮助判断，还是在制造 Anchoring Bias。

## 10. Today Worth Thinking

Agent 有记忆以后，很容易产生一个直觉：

> 记得越多，Agent 越聪明。

但企业场景更可能是：

> **记忆质量比记忆数量重要。**

错误知识、过期规则、一次特殊审批、已经失效的环境信息，如果被长期保留，都会把一次错误放大成持续错误。

所以 Memory 系统真正重要的能力可能不是 Remember，而是：

**Know what to forget.**

## 11. 30分钟 Action

今天可以直接给一个现有 Agent 设计第一张 Memory Schema：

| 字段 | 作用 |
|---|---|
| memory_id | 唯一标识 |
| source | 来源 |
| scope | 生效范围 |
| confidence | 可信度 |
| created_at | 创建时间 |
| expires_at | 失效时间 |
| evidence | 原始证据 |
| status | ACTIVE / REVOKED / EXPIRED |

然后从历史记录中手工挑 **5 条真正值得长期复用的经验**填进去。

重点不是接模型，而是先判断：到底什么东西配被称作“Agent Memory”。

## 13. 我的备注

结合金融测试、Agent Testing 和智能测试平台，今天这个方向很值得提前设计，但不建议一上来就做“大而全的长期记忆”。

更适合先做：

### **可审计的测试经验记忆层**

```text
人工确认结果
   ↓
Memory Candidate
   ↓
质量门禁
   ↓
Scoped Memory
   ↓
后续任务召回
   ↓
模型判断
   ↓
效果回归
```

金融测试里真正适合沉淀的，不是所有聊天和执行日志，而是少量高价值经验，例如：

- 某类规则命中为什么属于误判；
- 某类环境异常如何恢复；
- 某种状态组合为什么必须停止；
- 某个业务字段在特定系统里的真实含义。

而且 Memory 不应该直接改变状态机、权限和硬规则。它只应该影响“语义判断与建议”。

可以保持三层：

```text
Memory → 提供经验
Model → 做语义判断
Policy / State Machine → 做确定性约束
```

另外，长期 Agent 对现有测试平台还有一个很现实的启发：现在很多异步任务其实已经具有 Persistent Agent 的雏形——任务启动后等待回调、跨时间恢复、聚合多个 Server 状态、处理失败与重试。

未来真正 Agent 化时，最需要补的可能不是 Prompt，而是：

**Wake-up 是否幂等、Resume 是否恢复正确状态、Memory 是否污染后续任务、长时间运行后权限是否仍然符合最初授权。**

如果这四件事能被平台化测试，Agent Testing 就从“每次跑得对不对”进一步进入“长期运行以后还能不能一直对”。
