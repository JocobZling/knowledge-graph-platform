# AI 与 Agent 每日简报 v2

**日期：2026-08-18**

## 1. 今日摘要

近 24 小时最值得关注的新增事件，是 Google 发起的 Agent2Agent（A2A）协议于 8 月 17 日进一步转入 Agentic AI Foundation（AAIF）这一更聚焦 Agent 生态的治理体系。A2A 解决独立 Agent 之间的发现、通信和协作，MCP 主要解决 Agent 与 Tool / Data 的连接，两者开始形成清晰的互补关系。

这意味着企业 Agent 架构正在从“一个 Agent 接很多 Tool”继续演进到“多个 Agent 通过标准协议互相委托，再由各自 Agent 调用 MCP / Tool”。对 Agent Testing 来说，新的测试对象不只是模型和 Tool，而是 Agent Card、能力声明、身份认证、跨 Agent 任务状态、协议兼容、委托链和故障传播。

研究侧，本周值得补充的是 FlowScout：它不是让 LLM 模拟 Tool，而是从历史执行记录中挖掘 Tool 协作骨架，再用真实执行反馈优化 Workflow。论文报告在四类任务中，相比基线 Tool 调用正确性至少提升 92.69%，执行质量至少提升 17.66%；这些属于论文实验结果，仍需在真实企业 Workflow 中复测。

最近 7 日日报已覆盖 Local Agent、模型路由、Provider Reliability、模型升级回归、Skill 供应链、Multi-Agent 冲突、Policy Gate 与 Resource Budget，因此本期不重复这些主题，重点转向 **Agent Interoperability Testing**。

## 2. AI / 大模型 Top News

### 2.1 A2A 转入 Agentic AI Foundation：Agent 互操作进入更集中治理阶段

8 月 17 日，Axios 报道 Google 创建的 A2A 协议将成为 Agentic AI Foundation 的托管项目。A2A 的目标是让不同厂商、不同框架、不同服务器上的 Agent 以标准方式发现能力、交换消息并协作，而不要求暴露各自内部 Memory、Plan 或 Tool 实现。

其工程意义可以简化为：

`Agent A -> A2A -> Agent B -> MCP / Tool`

A2A 解决 Agent-to-Agent，MCP 解决 Agent-to-Tool / Resource。随着两层协议逐渐组合，企业不再需要为每一对 Agent 单独编写私有集成。

来源：Axios（2026-08-17）及 A2A 官方规范。

### 2.2 A2A 1.x 已把 Agent Card、协议绑定和长任务生命周期做成显式协议对象

A2A 当前正式规范以 Agent Card 描述 Agent 的身份、能力、Skill、输入输出模式和安全要求，并支持 JSON-RPC、gRPC、HTTP/JSON 等协议绑定。规范还要求不同协议绑定在功能、行为、错误处理和认证上保持语义等价。

这直接产生一类新的测试：

`同一个 Agent + 不同 Protocol Binding -> 结果是否语义一致？`

此外，A2A 是 Async First，原生考虑长任务和 Human-in-the-loop，因此 Task Cancel、Streaming、恢复和状态一致性也成为协议级测试对象。

来源：A2A Protocol Specification 1.x。

### 2.3 FlowScout：用真实执行反馈生成 Tool Workflow

8 月 10 日提交的 FlowScout 研究尝试从历史任务记录自动生成 Agent Workflow。与只让 LLM 模拟 Tool 的方法不同，它把 Workflow 表示成 LLM Node、Tool Node 和依赖边，先挖掘常见 Tool 协作骨架，再使用 Monte Carlo Tree Search 和真实执行反馈优化拓扑。

论文报告其生成的 Workflow 相比 PM4Py、ReAct 和 AFlow，在四类任务上 Tool Invocation Correctness 至少提升 92.69%，Execution Quality 至少提升 17.66%，并降低重复运行的性能波动。

对企业最值得借鉴的是：**历史成功 Trace 可以反过来成为 Workflow 设计数据。**

来源：arXiv:2608.10039。

## 3. 科技行业动态

### 3.1 Agent 协议栈开始分层

企业 Agent 技术栈正在逐渐形成：

`User / System -> Agent -> A2A -> Agent -> MCP -> Tool / Data`

因此以后说“支持 MCP”已经不足以描述一个完整 Agent Platform。还需要说明 Agent Discovery、Agent-to-Agent 委托、身份传播、Task Lifecycle 和跨 Agent Trace。

### 3.2 Agent Testing 从单体测试进入分布式系统测试

当任务跨 Agent 执行后，传统分布式系统问题重新出现：超时、重复投递、状态漂移、部分成功、重试、取消传播、身份丢失、版本兼容和链路追踪。

因此 Multi-Agent Testing 不应只测“几个 Agent 会不会合作”，还应测试协议和状态机。

## 5. Agent Ecosystem

### 本周最值得体验：A2A + MCP 最小链路

构造两个简单 Agent：

`Coordinator Agent --A2A--> Review Agent --MCP--> Tool`

只做一个任务，例如“读取一条扫描结果并判断是否需要复核”。记录 Coordinator 的委托、Review Agent 的 Agent Card、MCP Tool 调用和最终结果。

重点不是做复杂 Demo，而是看一条 Trace 能不能跨越 A2A 与 MCP 保持完整。

### Agent 实践启发：Agent Card 应该像 API Contract 一样被测试

Agent Card 声明 Skill、输入输出模式、安全要求和协议。如果声明与实际行为不一致，下游 Agent 会基于错误能力做规划。

因此至少要验证：`Declared Skill == Actual Capability`、认证要求一致、协议版本兼容、输入输出 Schema 可用。

### Workflow 治理：跨 Agent 委托必须传播身份与 Trace

建议每次委托至少保留：`user_id / source_agent / target_agent / task_id / trace_id / delegated_scope / protocol_version`。

否则最后只知道“Agent B 调了 Tool”，却无法回答是谁授权 Agent A 再委托给 Agent B。

## 7. 企业实践

### Google / Linux Foundation：把 Agent 间集成从厂商私有接口推向开放协议

A2A 最值得企业借鉴的不是“必须采用 A2A”，而是把 Agent 能力声明、发现、委托和任务生命周期从业务代码中抽离出来，形成可替换的协议层。

这样未来 Agent A 从 Google ADK 换成其他框架时，只要协议 Contract 保持兼容，下游 Agent 不需要全部重写。

## 8. 今日工具推荐

### A2A Inspector / TCK

A2A 官方项目组织已经提供 Inspector 和 Technology Compatibility Kit。相比手工跑 Demo，更值得关注的是用 TCK 思路验证 Agent 实现是否真的符合协议，而不是“能连通就算支持”。

## 9. 今日实战

给一个 Agent 定义最小 Contract：

```yaml
agent: log-review-agent
protocol: A2A
version: 1.x
skills:
  - review_log_risk
input: scan_result
output: review_decision
security: delegated-user
```

然后设计 5 个 Case：正常委托、未知 Skill、协议版本不兼容、目标 Agent 超时、目标 Agent 成功但回包丢失。

最后检查 Task State 和 Trace 是否仍然一致。

## 10. Today Worth Thinking

MCP 解决了“Agent 能调用什么 Tool”，A2A 开始解决“Agent 能把什么任务交给谁”。

真正复杂的企业风险会出现在两者连接处：

`User -> Agent A -> Agent B -> MCP -> Tool`

如果每一层都单独合法，但委托链组合后权限扩大，系统仍然可能越权。

所以未来 Agent Governance 很可能需要从 Tool Permission 进一步演进到 **Delegation Permission**。

## 11. 30分钟 Action

今天从现有智能测试 Workflow 中挑一个步骤，假设它未来要委托给另一个 Agent。

写下 6 个字段：`source_agent`、`target_agent`、`skill`、`input_schema`、`delegated_scope`、`timeout`。

再补 3 条失败用例：目标 Agent 不支持 Skill、执行超时、执行成功但响应丢失。

这已经是第一版 Agent-to-Agent Contract Test。

## 13. 我的备注

结合金融测试、Agent Testing 和智能测试平台，今天最值得补的是 **Agent 委托链测试**。

目前测试 Agent 容易按单体理解：

`Agent -> Tool -> Result`

但后面更可能变成：

`Test Planner Agent -> Case Agent -> Data Agent -> MCP / DB`

这时最危险的不是某个 Agent 单独越权，而是权限在委托过程中逐层放大。

建议平台后续增加一类 Delegation Trace：记录发起人、源 Agent、目标 Agent、委托 Skill、继承权限、实际 Tool、最终业务断言。并增加四类测试：能力声明一致性、委托权限不扩张、跨 Agent 状态一致性、部分失败恢复。

这和现有金融测试状态机很契合：一个 Report 下多个 Server / Worker 的状态聚合，本质上已经包含分布式任务状态问题。未来如果执行节点逐渐 Agent 化，可以把现有“状态聚合 + 幂等回调 + 失败恢复”的工程经验直接迁移到 Agent-to-Agent Workflow，而不是重新从 Prompt 层开始设计。
