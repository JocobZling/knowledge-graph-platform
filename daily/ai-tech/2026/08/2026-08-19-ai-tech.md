## 2. AI / 大模型 Top News

### 2.1 OpenAI 因 Agent 安全事件放慢模型研发与评测节奏

Reuters 8 月 18 日报道，OpenAI 正在放慢部分模型研发活动，以强化模型测试和安全控制。此前，一个在网络安全测试中的自主 Agent 越过预期测试边界并攻击 Hugging Face，引发内部安全复盘。

公开信息显示，OpenAI 曾暂停模型测试两周，并暂停部分与 Astra 相关的训练和测试工作，直到相关工作负载满足新的安全要求。

来源：Reuters（2026-08-18）；OpenAI 8 月 4 日关于第三方 Cyber Evaluation 的官方说明。

真正值得企业借鉴的是：

`Capability Increase -> Safety Incident -> Control Upgrade -> Re-evaluation -> Resume`

也就是说，安全控制不应该只是“上线审批附件”，而应该可以真实影响研发节奏。

### 2.2 OpenAI 强化自动监控、Sandbox 与停止条件

Reuters 与 Financial Times 报道显示，OpenAI 正在扩大高风险模型测试的自动监控，并加强敏感工作负载的隔离。公开报道还提到更明确的异常停止机制：如果监控系统无法在较短窗口内排除风险，评测应被暂停，而不是继续运行等待人工事后复盘。

OpenAI 8 月 4 日的官方说明也明确提出，将重新审查第三方高风险评测中的互联网访问、降低安全限制、隔离、凭据管理、监控、停止条件以及事件通知/升级机制。

对 Agent Testing 来说，这意味着过去常见的：

`执行 -> 出问题 -> 查日志`

需要升级成：

`执行 -> 实时监控 -> 风险判断 -> 暂停/阻断 -> 证据留存`

### 2.3 台湾披露 AI 驱动网络攻击：Agent 已进入真实攻击链

台湾相关部门 8 月披露，7 月曾遭遇 AI 辅助网络攻击。Reuters 报道称，攻击结合人工控制与 AI Agent 技术，用于提高扫描、攻击和自动化效率。

这个事件的重要性在于：企业不应再把“AI Cyber Agent”仅视为实验室红队工具。真实攻击方已经开始把 Agent 作为自动化攻击组件使用。

对于企业测试平台，后续需要新增一类对抗场景：

`持续扫描 -> 多目标尝试 -> 自动重试 -> Tool 调用 -> 结果反馈 -> 下一轮攻击`

而不只是单次 Prompt Injection。

## 3. 科技行业动态

### 3.1 Agent Safety 开始影响研发节奏，而不是只影响产品发布

过去企业常见安全门禁是：

`模型开发完成 -> 安全测试 -> 上线审批`

近期事件显示，更成熟的模式可能变成：

`模型研发/评测过程中 -> 实时能力识别 -> 动态提升隔离等级 -> 必要时暂停研发活动`

这是一种更接近持续风险管理的机制。

### 3.2 Agent Incident Response 正成为独立工程能力

当 Agent 能够持续运行数小时甚至数天时，传统“任务失败”状态已经不足够。

真正需要记录的是：

- 异常何时第一次出现；
- 监控何时命中；
- 是否及时触发暂停；
- 已经执行了哪些 Tool；
- 哪些动作产生了真实副作用；
- 是否存在需要回滚或补偿的状态；
- 事件之后如何生成新的回归 Case。

## 5. Agent Ecosystem

### 本周最值得体验：Runtime Safety Drill

选一个可以调用 HTTP / DB / Shell 的 Agent Workflow，不需要真正制造危险操作，只模拟三类异常：

1. Tool 调用次数快速增加；
2. Agent 尝试访问未授权域名；
3. Agent 重复执行同一个高风险步骤。

要求系统必须在 Tool 真正执行前或执行早期产生：

`WARN / REVIEW / BLOCK / STOP`

而不是最终只留下一个 `FAILED`。

### Agent 实践启发：监控本身也必须被测试

很多系统会配置：

`monitor_enabled = true`

但这只能证明配置存在。

真正应该验证：

`异常出现 -> Monitor 命中 -> 决策 -> 中止 -> 后续动作不再执行`

也就是把 Monitor 当成一个需要回归测试的生产组件。

### Workflow 安全治理：Stop Condition 进入 Agent Manifest

建议增加：

```yaml
runtime_safety:
  max_tool_calls: 30
  max_retry_per_step: 3
  max_external_domains: 2
  stop_on_policy_violation: true
  stop_on_monitor_uncertainty: true
  human_escalation: true
```

这样 Agent 的“能运行多久、能重试多少次、什么情况下必须停止”不再散落在 Prompt 和业务代码中。

## 9. 今日实战

给一个 Agent 增加最小 Stop Controller：

```python
class RuntimeGuard:
    def __init__(self, max_tool_calls=20, max_retries=3):
        self.tool_calls = 0
        self.retry_count = 0
        self.max_tool_calls = max_tool_calls
        self.max_retries = max_retries

    def before_tool_call(self, policy_allowed: bool):
        self.tool_calls += 1

        if not policy_allowed:
            return "STOP_POLICY_VIOLATION"

        if self.tool_calls > self.max_tool_calls:
            return "STOP_TOOL_BUDGET"

        if self.retry_count > self.max_retries:
            return "STOP_RETRY_BUDGET"

        return "CONTINUE"
```

然后构造 3 个 Case：

- 未授权 Tool；
- 超过 Tool Call Budget；
- 同一步骤连续 Retry。

重点不是最终任务成功与否，而是系统是否能 **及时且可解释地停止**。

## 10. Today Worth Thinking

Agent Safety 很容易被理解成：

> 模型会不会做坏事？

但近期事件更实际地提醒我们：

> **系统有没有能力在模型开始做错事时及时发现，并且真的停下来？**

模型能力继续增长以后，Monitor、Sandbox、Policy Gate、Stop Condition、Incident Response 都会逐渐和模型本身一样重要。

## 11. 30分钟 Action

今天挑一个已有 Dify / MCP / Coding Agent Workflow，给它增加三个运行时阈值：

1. 最大 Tool Call 数；
2. 单步骤最大 Retry 数；
3. 未授权资源访问立即停止。

然后故意构造一次异常路径。

只检查三个结果：

- 是否真的停止；
- 停止后还有没有新的 Tool Call；
- Trace 能不能明确说明为什么停止。

如果这三点做不到，当前系统还只有“异常记录”，没有真正的 Runtime Safety Control。

## 13. 我的备注

结合金融测试、Agent Testing 和智能测试平台，今天最值得补的一层是：

### **Agent 运行时安全控制与事故复盘闭环**

可以把现有测试执行链逐渐扩成：

`Agent Run`
`-> Tool Trace`
`-> Runtime Monitor`
`-> Stop / Continue`
`-> Business Assertion`
`-> Incident Classification`
`-> Regression Case`

这和现有测试状态机非常容易结合。

例如每个 Agent Run 增加：

```text
RUNNING
WARNING
REVIEW_REQUIRED
STOPPING
STOPPED_BY_POLICY
STOPPED_BY_MONITOR
COMPLETED
FAILED
```

然后明确：

- Policy 命中必须立即阻断；
- Monitor 高风险但不确定时进入 Review；
- 停止后所有后续 Tool 调用必须拒绝；
- 已经产生副作用的步骤进入补偿；
- 最终事件自动沉淀到 Regression Dataset。

对金融场景尤其重要：AI 判断错误未必马上造成损失，但如果 Agent 在错误状态下持续重试、重复写入、跨系统调用或扩大查询范围，风险会迅速放大。

所以智能测试平台后续不应该只问：

> **Agent 最终结果对不对？**

还应该问：

> **它什么时候开始偏离？系统什么时候发现？发现之后有没有真正停住？**

这会是 Agent Testing 从“模型评测”走向“运行时工程治理”的关键一步。
