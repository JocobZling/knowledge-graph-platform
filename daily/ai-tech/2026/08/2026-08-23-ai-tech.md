# AI 与 Agent 每日简报 v2

**日期：2026-08-23**

## 1. 今日摘要

近 24 小时最值得关注的新增，是 Model Context Protocol（MCP）核心维护者在 8 月 22 日发布新路线图。路线图把下一阶段工作明确收敛到五个方向：Agentic Messaging、HTTP-native Transport、Agent Identity 与企业级安全、Primitives 改进、SDK Developer Experience。

这次更新的意义不只是“协议又要加功能”。MCP 正从最初的人机交互式 Tool Protocol，继续向真正适合长期 Agent、云端 Agent、Subagent Delegation 和大规模 Tool Catalog 的生产协议演进。

其中最值得企业关注的是 Agent Identity：当前 MCP 授权仍大量围绕“人在浏览器里批准访问”设计，但未来调用方越来越可能是没有人在场的云端 Agent，或者代表用户继续委托 Subagent。路线图因此明确推进 DPoP、Workload Identity Federation、ID-JAG / Enterprise-Managed Authorization 与标准 Token Exchange。

最近 7 篇日报已经覆盖 Skill 供应链、Multi-Agent 监督、Policy Gate、A2A、Runtime Monitoring、Control Effectiveness、Browser/Computer Agent、Harness 与 Persistent Agent / Memory。本期不重复这些主题，主线转向 **Agent Identity + Delegation + MCP Protocol Testing**。

## 2. AI / 大模型 Top News

### 2.1 MCP 发布新路线图：Agentic Messaging 成为正式优先级

MCP 核心维护者 8 月 22 日发布新路线图。现代 Agent 已经不再适合简单 request-response：任务可能长时间运行、服务器需要主动推送结果、执行过程中还需要 Steering。

路线图将 Tasks、`subscriptions/listen`、progress notification、server-initiated events（webhook / channel）放进统一的 Agentic Messaging 演进方向，并计划推动 Tasks extension（SEP-2663）进入正式规范。

官方来源：https://blog.modelcontextprotocol.io/posts/mcp-roadmap/

对 Agent Testing 来说，测试对象因此从一次 Tool Call 扩展为：

```text
Task Created
→ Running
→ Progress
→ Server Event
→ Steering
→ Resume
→ Completed / Failed / Cancelled
```

真正需要验证的是事件重复、乱序、断线重连、取消传播以及 Steering 后旧动作是否继续执行。

### 2.2 Agent Identity：MCP 开始正面解决“到底是谁在调用 Tool”

路线图明确指出，当前 MCP Authorization 主要围绕人在浏览器中批准访问设计，但生产环境中越来越多调用者是云端 Agent，它可能代表用户工作，也可能进一步把更窄的权限委托给 Subagent。

MCP 下一阶段计划推进 DPoP，并围绕 Workload Identity Federation、ID-JAG、Enterprise-Managed Authorization 和标准 Token Exchange 建立 Agent Identity / Delegation 路径。

这会把调用链从：

```text
User Token → Agent → Tool
```

推进到：

```text
User Identity
   ↓ delegation
Agent A Identity
   ↓ narrower delegation
Agent B Identity
   ↓
MCP Tool
```

金融 Agent 最关键的断言将变成：**委托后的权限不能大于委托前权限。**

### 2.3 MCP Tool Catalog 要做 Progressive Discovery

路线图指出，当 MCP Server 暴露上百个 Tool 时，模型在用户还没有提出具体问题前就需要承担整个 Tool Surface 的上下文成本，同时 Tool Selection 质量也会下降。

因此 MCP 正推进 Progressive Discovery：先暴露一个较小的入口，再随着对话和任务范围收窄逐步揭示更多 Tool。

这意味着 Tool Discovery 本身也会成为 Agent Runtime 行为：

```text
Intent
→ Discover Capability
→ Narrow Tool Set
→ Select Tool
→ Execute
```

后续 Agent Evaluation 不应只统计“最终 Tool 选对率”，还应该统计 Discovery Precision、无关 Tool 暴露率、Tool Schema Token Cost，以及高风险 Tool 是否被过早暴露。

### 2.4 Forge v0.18.0：Delegated per-user MCP Authentication 落到开源 Runtime

Forge 8 月 20 日发布 v0.18.0，新增 delegated per-user MCP authentication、OAuth 2.1 discovery、dynamic client registration，同时强化 egress control 和 audit attribution。

项目定位是让 Agent 同时支持 A2A、MCP、Skill，并在 Runtime 层提供策略、出站访问控制和审计。它说明 Agent Identity / Delegation 已经不只是协议讨论，而开始进入具体 Runtime 实现。

官方更新：https://useforge.ai/changelog/

## 3. 科技行业动态

### 3.1 Agent 身份正在从 API Key 走向 Workload Identity

长期 Token 和共享 API Key 最大的问题，是系统很难回答“这个动作到底代表谁”。Agent 一旦可以后台运行、跨时间唤醒并继续委托，这个问题会迅速放大。

更合理的身份模型是：User、Agent、Subagent、Tool 四层身份分别存在，并在 Trace 中保留 delegation chain，而不是让所有动作最终都表现为同一个 Service Account。

### 3.2 MCP 正从 Tool Connector 进入分布式 Agent Infrastructure

Tasks、Events、HTTP-native Transport、Agent Identity、Progressive Discovery 放在一起看，MCP 的边界已经明显超出最初的“统一 Tool 接口”。它正在承担更多分布式运行时问题：身份、异步任务、事件、协议兼容和大规模能力发现。

这也意味着传统 API Testing、分布式系统测试和 IAM 测试会越来越多地进入 Agent Testing。

## 5. Agent Ecosystem

### 本周最值得体验：Delegation Scope Test

构造一条最小委托链：

```text
User
→ Coordinator Agent
→ Review Agent
→ MCP Tool
```

给 Coordinator `read + review` 权限，但只委托 Review Agent `read`。

然后故意让 Review Agent 请求 `write`。

关键断言不是模型会不会主动拒绝，而是 MCP / Policy 层必须确定性 DENY。

### Agent 实践启发：身份要进入 Trace，而不是只进 Token

建议至少记录：

```yaml
user_id: tester-001
source_agent: coordinator
target_agent: reviewer
delegated_scope: log.read
actual_tool: log.read
identity_provider: workload-identity
auth_decision: allow
trace_id: xxx
```

这样 Incident 才能回答“谁代表谁做了什么”。

### Workflow 治理：Tool Discovery 也需要最小暴露原则

Agent 不需要在任务开始时看到全部 200 个 Tool。可以按 Domain / Risk / Intent 分层发现，尤其高风险写操作只有在明确任务阶段才进入候选集。

## 7. 企业实践

### MCP 社区：Agent Identity 建在现有身份标准上

新路线图没有尝试为 Agent 再发明一套孤立认证协议，而是选择 DPoP、Workload Identity Federation、Token Exchange 等已有安全标准作为基础。

企业可以借鉴的原则是：

```text
现有 IAM
  ↓
User / Workload Identity
  ↓
Delegation Token
  ↓
Agent
  ↓
MCP Policy
```

Agent 平台不应该重新维护一套不可审计的“AI 专属账号体系”。

## 9. 今日实战

给一个现有 Agent Tool 调用增加最小 Delegation Context：

```json
{
  "user": "tester-001",
  "agent": "review-agent",
  "delegatedBy": "coordinator-agent",
  "scope": ["report.read"],
  "tool": "report.update"
}
```

因为 `report.update` 不属于委托 Scope，预期必须在 Tool Execution 前得到：

```text
DENY_SCOPE_ESCALATION
```

并验证数据库没有任何副作用。

## 10. Today Worth Thinking

过去 Agent 权限经常被理解成：

> 这个 Agent 能调用哪些 Tool？

但 Multi-Agent / Persistent Agent 出现以后，更关键的问题会变成：

> **这个 Agent 当前是代表谁、基于哪次授权、还能把多少权限继续交给下一个 Agent？**

Capability 只是第一层，Delegation Chain 才决定生产 Agent 的真实 Blast Radius。

## 13. 我的备注

结合金融测试、Agent Testing 和智能测试平台，今天最值得提前补的是 **Agent Identity Test**。

现在很多内部 AI Workflow 只区分“哪个用户发起”，但 Agent 化以后至少会出现：

```text
用户身份
+ Agent身份
+ 执行服务身份
+ 被委托权限
+ 实际资源权限
```

这五个东西如果混在一起，后面很容易出现一种隐蔽风险：用户本来只能读，但 Agent 背后的 Service Account 可以写，于是 Agent 实际能力超过了用户授权。

测试平台可以先建立四类固定 Case：

1. **Identity Propagation**：跨 Agent / MCP 后用户身份是否仍可追踪；
2. **Scope Non-escalation**：Subagent 权限不得大于 Parent Agent 委托范围；
3. **Token Lifetime**：任务结束、撤权或超时后旧授权不能继续使用；
4. **Audit Attribution**：最终写操作必须能同时还原 User、Agent、Tool 和 Resource。

对金融场景尤其重要的是，不要把“模型知道自己不应该写”当成权限控制。真正的结构应该是：

```text
Model Intent
    ↓
Agent Identity + Delegated Scope
    ↓
Policy Decision
    ↓
Tool Execution
    ↓
Business Assertion
    ↓
Audit Evidence
```

这样 Agent Testing 才能从“它会不会选错 Tool”，进一步回答：

> **即使模型选错了 Tool，系统身份和权限链能不能保证它最终做不了不该做的事。**

这会是金融 Agent 从 Demo 进入真正生产环境之前非常关键的一层。
