## 2. AI / 大模型 Top News

### 2.1 OpenAI Atlas到达停止服务日期，Browser Agent能力收敛到ChatGPT与Codex

OpenAI官方帮助中心明确：Atlas计划于2026年8月9日停止工作，浏览器Agent能力转移到ChatGPT与Codex。新的方向包括多标签页、下载、更好的导航、账号登录支持等；Atlas书签、标签页和浏览历史不会自动迁移，Cookie与会话文件需要作为敏感数据处理。

来源：https://help.openai.com/en/articles/20001371-evolving-atlas-into-chatgpt-for-browser-based-agentic-work

实质变化不是简单的产品下线，而是Browser Agent从独立浏览器产品向通用Agent运行时收敛。对企业测试而言，被测对象也从“一个浏览器”变成`Agent + Browser Runtime + Login Session + Tool/Connector`。

### 2.2 ChatGPT Work云浏览器支持可验证的HTTP请求身份

OpenAI近期更新的Cloud browser allowlisting文档显示，ChatGPT Work云浏览器使用Web Bot Auth为出站HTTP请求签名，并基于RFC 9421 HTTP Message Signatures携带`Signature`、`Signature-Input`和`Signature-Agent`头；网站侧可通过公开密钥验证请求确实来自ChatGPT。

来源：https://help.openai.com/en/articles/11845367-chatgpt-agent-allowlisting

这比依赖IP或User-Agent更适合Agent身份治理。企业系统可以把“来自已验证Agent的请求”作为独立身份类型，再叠加用户身份、业务权限和操作范围，而不是把Agent流量当普通浏览器流量处理。

### 2.3 Meta Muse Code：并行子Agent进入编码产品

Reuters 8月5日报道，Meta推出Muse Code beta，由Muse Spark 1.2驱动，支持代码编写与调试、长复杂任务、多个子Agent并行执行，并保留持久活动日志以支持崩溃后的任务恢复。

来源：https://www.reuters.com/technology/meta-launches-new-ai-coding-tool-powered-by-muse-spark-12-2026-08-05/

对Agent Testing的增量价值在于：编码Agent的测试不能只看最终Patch，还要评估子Agent之间的任务拆分、共享上下文、失败恢复和活动日志是否足以还原责任链。

## 3. 科技行业动态

### 3.1 Browser Agent开始需要独立的机器身份

浏览器Agent正在从模拟人类点击走向可被服务端识别和验证的自动化主体。未来企业访问控制更合理的模型是：`Human Identity + Agent Identity + Session + Capability`，而不是仅判断账号是否登录。

### 3.2 Coding Agent进入并行子Agent与可恢复执行阶段

Muse Code、Prime Agent等近期产品共同说明，长任务Agent开始把并行子任务、持久状态和失败恢复作为基础能力。测试指标应增加子任务成功率、恢复成功率、重复副作用、跨Agent上下文污染和最终证据完整性。

## 5. Agent Ecosystem

### 本周最值得体验：给Browser Agent增加“身份断言”

在测试环境中不要只记录用户账号，额外记录：`agent_provider`、`agent_runtime`、`request_signature_verified`、`session_owner`、`capability_scope`。然后验证同一用户通过人工浏览器和Agent访问时，审计系统能否准确区分两类行为。

### Agent实践启发：Agent身份不能替代用户授权

即使HTTP签名证明请求来自ChatGPT，也只能证明“谁在执行”，不能证明“是否允许执行当前业务动作”。完整授权应至少是：`用户身份 × Agent身份 × 资源 × 动作 × 会话风险`。

### Workflow治理：Browser Agent增加会话边界

登录Cookie、下载文件、浏览历史、跨标签页状态都属于Browser Agent上下文。任务结束后应明确哪些状态销毁、哪些可持久化、哪些禁止进入模型上下文。

## 7. 企业实践

### OpenAI：从独立Atlas迁移到统一Browser Agent运行时

**做法：** 停止独立Atlas产品，把浏览器Agent能力迁入ChatGPT和Codex；同时提供云浏览器请求签名能力，帮助网站验证Agent来源。

**可借鉴点：** 企业内部如果存在多个Browser Agent，不必每个Agent独立建设浏览器基础设施。可以统一Browser Runtime、身份签名、会话隔离、下载扫描、网络策略和审计，再向不同Agent提供受控能力。

## 9. 今日实战

为Browser Agent请求建立最小审计结构：

```python
def audit_agent_request(user, agent, resource, action, signature_ok):
    return {
        "user": user,
        "agent": agent,
        "resource": resource,
        "action": action,
        "agent_identity_verified": signature_ok,
        "requires_policy_check": True,
    }
```

注意`signature_ok=True`不能直接等价于`authorized=True`，后续仍需业务权限判断。

## 10. Today Worth Thinking

Browser Agent越来越像一种新的“机器用户”。如果企业仍只用传统账号和IP判断访问主体，就很难回答：这个动作是用户本人完成、Agent代用户完成，还是被网页内容诱导后执行？未来Agent审计需要同时保留Human Intent、Agent Identity和Execution Evidence。

## 11. 30分钟 Action

选一个现有Browser Agent或Dify HTTP工具，给执行日志增加5个字段：`human_user_id`、`agent_id`、`session_id`、`requested_action`、`authorization_result`。执行一次正常访问和一次越权访问，确认日志能区分“身份验证成功”和“业务授权成功”。

## 13. 我的备注

结合金融测试、Agent Testing和智能测试平台，建议在现有MCP/Tool准入之外新增一层“Agent执行主体审计”。金融系统里真正需要回答的不是“这个账号有没有权限”，而是“谁授权了哪个Agent，以什么身份，在什么会话中，对什么资源执行了什么动作”。

可以形成：

```text
Human User
→ Agent Identity
→ Session
→ Skill / MCP / Browser Tool
→ Capability Policy
→ Business Authorization
→ Execution Trace
→ Result Assertion
```

近期最小落地点是把Agent身份、用户身份和业务授权结果同时写入Trace。后续再把Browser Agent、MCP Agent和Coding Agent统一纳入同一套身份与审计模型。
