- 工具与数据访问权限；
- 关键操作审批记录；
- 完整执行轨迹与证据；
- 异常暂停和人工接管能力；
- 安全事件发现、报告和复盘机制。

### 2.2 Agent安全从自愿承诺进入可审计监管阶段

欧盟AI监管框架对通用人工智能模型和具有系统性风险的模型提出更强的透明度、风险缓解与安全保障要求。近期Agent越界事件使一个关键问题更加明确：

> 模型在单轮对话中表现安全，不代表其在数小时或数天的工具执行中仍然安全。

企业Agent需要建立运行期控制，而不能只做上线前测试：

```text
上线前准入评测
  ↓
灰度执行与权限限制
  ↓
实时轨迹监控
  ↓
高风险行为阻断
  ↓
人工接管
  ↓
事件复盘与回归测试
```

对金融机构而言，应特别关注Agent是否可以通过多个低风险步骤组合形成越权查询、敏感数据外发、权限提升或绕过审批。

### 2.3 Microsoft Agent Framework支持从MCP Server发现Agent Skills

Microsoft Agent Framework于7月28日公布.NET能力：Agent可以从MCP Server发现并动态加载Agent Skills。中心团队可以一次发布Skill，由多个Agent按需调用，无需把全部Skill文件复制到每个项目或每次重新部署应用。

这一变化解决了Skill分发问题，但同时引入新的治理要求：

- Skill来源是否可信；
- Skill版本是否经过审批；
- Skill是否声明依赖的Tool和权限；
- Agent加载Skill前是否进行完整性校验；
- Skill更新后是否需要重新执行回归测试；
- 不同项目是否可以加载不同安全等级的Skill。

建议企业把Skill视为可执行供应链组件，而不是普通Prompt模板。

来源：
- https://devblogs.microsoft.com/agent-framework/

### 2.4 新论文提出Browser Agent需要独立识别类别

论文《What Does It Take to Detect an AI Agent?》研究了Browser Agent与人类、传统Bot之间的行为差异。

研究结果显示：

- 二分类模型把39.1%的真实AI Agent误判为人类；
- 另一种二分类Transformer误判率为34.5%；
- 引入“人类、Bot、AI Agent”三分类后，Agent识别显著改善；
- `mouse_event_rate`和`teleport_click_ratio`两项行为特征即可在实验中达到很高的Agent识别效果。

该研究目前基于受控实验，不能直接等同于生产系统结论，但它揭示了一个重要治理问题：Browser Agent既不是传统爬虫，也不是普通人类用户，需要独立身份和访问策略。

来源：
- https://arxiv.org/abs/2607.26935

## 3. 科技行业动态

### 3.1 AI监管对象从模型扩展到Agent系统

过去AI治理重点主要包括训练数据、模型能力、内容安全和输出透明度。随着Agent能够操作浏览器、代码仓库、数据库和企业应用，治理对象正在扩展到完整系统：

```text
Model
Agent
Skill
MCP Server
Tool
Credential
Environment
Trace
```

企业后续需要建立组件级清单和依赖关系，而不是只维护模型清单。

### 3.2 Agent能力开始采用“中心发布、动态发现”模式

Microsoft的Skill动态发现与GitHub此前的Agent Resource Discovery方向一致：Agent不再长期携带所有工具和Skill，而是在任务执行时从可信Registry中搜索和加载能力。

这可以降低上下文膨胀和重复部署成本，但也使能力发现链路成为新的攻击面。企业必须限制Agent可以访问哪些Registry、可以发现哪些Skill，以及哪些Skill允许自动加载。

## 5. Agent Ecosystem

### 本周最值得体验：MCP Skill Discovery

建议使用Microsoft Agent Framework搭建一个最小实验：

```text
Skill Registry / MCP Server
├── sql-readonly-check
├── test-case-generator
└── report-summarizer
        ↓
Agent按任务动态发现
        ↓
准入策略筛选
        ↓
加载Skill并执行
```

重点不要只验证“能否加载”，而应验证：

1. 未授权Skill是否不可见；
2. Skill版本变化后能否识别；
3. Skill需要的Tool权限是否显式声明；
4. Skill内容被篡改时是否阻断；
5. 加载和执行过程是否进入统一Trace。

### Agent实践启发：Skill必须具备软件供应链属性

企业Skill至少应包含以下元数据：

```yaml
name: settlement-readonly-check
version: 1.2.0
owner: testing-platform
risk_level: medium
required_tools:
  - settlement-db-readonly
required_scopes:
  - merchant:read
approval_status: approved
checksum: sha256:...
```

没有版本、责任人、权限声明、审批状态和完整性校验的Skill，不应进入生产Agent。

### Browser Agent治理

Browser Agent访问企业系统时，建议增加独立身份标签：

- `human-user`；
- `service-bot`；
- `browser-agent`；
- `supervised-agent`；
- `autonomous-agent`。

不同身份采用不同的速率限制、页面权限、敏感操作审批和审计保留周期。

## 7. 企业实践

### Microsoft：把Skill分发从项目内文件升级为中心能力服务

**做法：** 将Agent Skills发布到MCP Server，由Agent在运行时发现和加载。

**效果：** 中心团队可以统一维护领域能力，减少Skill复制、版本漂移和重复部署。

**可借鉴点：** 企业建设Skill中心时，不应只提供上传和下载功能，而应同时提供：

```text
Skill注册
├── 版本管理
├── Owner与责任边界
├── 权限声明
├── 安全扫描
├── 测试报告
├── 审批发布
├── 灰度范围
└── 使用审计
```

金融测试场景可优先沉淀只读查询、测试数据生成、字段核验、报告解析等低风险Skill，高风险写操作Skill应强制人工审批。

## 9. 今日实战

### 建立最小Skill准入检查器

准入规则可先采用确定性校验：

```python
REQUIRED_FIELDS = {
    "name",
    "version",
    "owner",
    "risk_level",
    "required_tools",
    "approval_status",
    "checksum",
}


def validate_skill(metadata: dict) -> dict:
    missing = sorted(REQUIRED_FIELDS - metadata.keys())
    approved = metadata.get("approval_status") == "approved"
    checksum_ok = str(metadata.get("checksum", "")).startswith("sha256:")

    return {
        "passed": not missing and approved and checksum_ok,
        "missing_fields": missing,
        "approved": approved,
        "checksum_ok": checksum_ok,
    }
```

后续再增加Tool权限、依赖版本、安全扫描结果和回归测试报告检查。

## 10. Today Worth Thinking

Agent生态正在从“每个应用内置全部能力”转向“运行时动态发现和组合能力”。这会提高复用效率，但也意味着Agent的行为由模型、Skill、Tool和外部Registry共同决定。

因此，未来Agent Testing不能只测试一个固定Prompt，而需要测试：

- Agent在不同Registry结果下会选择什么Skill；
- Skill升级后行为是否发生变化；
- 多个相似Skill之间是否选择正确；
- Skill与Tool权限是否匹配；
- 非法Skill是否可能通过描述诱导被选中；
- 最终行为是否仍满足业务规则。

真正的测试对象将从单一Agent实例升级为动态组合的Agent供应链。

## 13. 我的备注

结合金融测试、Agent Testing和智能测试平台，建议新增一个“Agent能力资产中心”，统一管理：

```text
Agent
├── Model
├── Skill
├── MCP Server
├── Tool
├── Workflow
└── Evaluation Suite
```

每项资产都记录版本、Owner、权限、风险等级、测试状态和使用范围。

近期可以从Skill开始切入，因为Skill比模型更接近具体业务行为，也更容易形成可落地的准入机制：

```text
Skill注册
  ↓
静态规则检查
  ↓
Tool权限核验
  ↓
回归测试
  ↓
人工审批
  ↓
灰度发布
  ↓
运行监控与撤回
```

这可以自然衔接现有MCP Server准入、Agent Trace、智能测试平台和金融测试台，并形成一套更完整的Agent供应链治理体系。
