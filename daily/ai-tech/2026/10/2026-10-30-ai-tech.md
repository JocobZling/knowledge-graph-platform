### 2.1 Mistral Large 4 正式开放权重：从API预览进入可自托管评估
**发布日期：2026-10-29｜主体：Mistral AI｜新颖度：5/5｜性质：关键能力可用性更新**

Mistral 于10月6日先推出 Large 4 公测；10月29日开放权重，Hugging Face 官方介绍列出 FP8、NVFP4 两种正式格式，社区提供 GGUF 量化。模型约1T总参数、49B激活参数（计入部分嵌入/输出层的口径约52B），标称最大上下文1M Token，支持文本和图像输入、文本输出。模型使用 **Mistral Ecosystem Open-Weight License**，并非无附加条件的标准MIT；开展 Model-as-a-Service 业务需另行评估许可条件。

### 2.2 AWS Step Functions 可直接作为 Agent MCP 工具：执行顺序不再由模型自由决定
**发布日期：2026-10-29｜主体：AWS｜新颖度：5/5｜性质：新产品能力**

Amazon Bedrock AgentCore Gateway 新增内置 Step Functions 连接器：将已有 Standard/Express 状态机暴露为 MCP 工具，无需额外编写 Lambda 桥接或自建 MCP Server。Agent决定是否启动流程、提交什么输入；状态机按既定定义执行步骤、重试与错误处理。标准流程可保留执行历史，支持长任务与人机协作。

**最值得注意的安全细节：** `StartExecution` 等4个操作可将 `stateMachineArn` 固定在网关配置中；`DescribeExecution`、`StopExecution` 等其他操作需靠网关IAM服务角色约束范围；`SendTaskSuccess/Failure/Heartbeat` 依赖任务令牌，必须将令牌当作机密。工具暴露并不自动代表权限最小化。

**金融测试借鉴：** 对话助手未来创建测试任务时，Agent只生成经过校验的“创建申请”；固定的Java工作流负责检查权限、审批、参数快照、幂等、落库和审计。不要让模型临时决定跳过审批节点。

官方来源：[AWS 10月29日发布](https://aws.amazon.com/about-aws/whats-new/2026/10/step-functions-workflows-ai-agent-tools/)；[AgentCore Step Functions连接器文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-connector-step-functions.html)。

### 2.3 OpenAI 更新 Model Spec：强调意图、透明度与人的自主权
**发布日期：2026-10-29｜主体：OpenAI｜新颖度：4/5｜性质：模型行为规范更新，非模型GA**

新版 Model Spec 围绕五项价值组织：忠实理解人的意图、尽量减少伤害、诚实透明、维护人的自主性、关怀。公告指出新增/调整了上下文、监督与自主性相关指导，并精简了部分旧风格规则。这是公开行为规范变化，**不能据此推断所有现网模型在当天都完成相同更新**。

**Agent Testing启发：** 把“用户授权意图”“实际工具动作”“风险提示是否充分”“是否未经确认扩大权限”分开评测。模型声称‘我理解你要做什么’，并不构成业务系统的有效授权。

官方来源：[OpenAI 10月29日公告](https://openai.com/index/updated-model-spec/)；[Model Spec](https://model-spec.openai.com/)。

### 2.4 新论文：将业务流程图与API Schema结合，减少Agent调用错误
**论文日期：2026-10-27｜主体：Saiful Khan、Afrah Farea｜新颖度：5/5｜性质：研究预印本**

论文《Grounding LLM Agents in Business Processes》将 OData 服务元数据与 BPMN 业务流程装入类型化属性图，检索不仅找到接口，还返回调用顺序、字段和枚举约束。在论文的81个多步骤任务上，所评估Agent的任务完成率为 **38.7%**，对照的分块检索基线为 **10.3%**；在另一组101次写操作试验中，完整类型上下文将无效调用降至3次。以上均为作者在特定服务集和模拟调用环境中的实验结果，不能直接推广为企业生产成功率。

**关键认识：** Agent正确选择接口，还可能因顺序错误、无效字段或伪造枚举而失败。对于测试经理助手，不必先建设复杂知识图谱；一期可以用明确的 Capability Schema + 状态迁移规则表达同样的约束。

论文：[arXiv:2610.37242](https://arxiv.org/abs/2610.37242)。

## 5. Agent Ecosystem（3条）

### 5.1 Agent / MCP / Workflow：让Agent选择流程，不让Agent改写流程
AWS连接器体现了一种工程分层：`意图识别 → 受控工具入口 → 固定业务流程 → 审计回读`。当业务需要“校验资格→审批→写入→复核”时，模型只能提出调用，不应决定跳过哪一步。对金融系统，建议以服务端状态机和数据库事务落实。

### 5.2 Skill / Tool Calling：Schema、授权和执行证据分开治理
Skill和MCP负责能力发现与调用格式，真实权限仍由后端验证。应至少记录 `capability_id`、`schema_version`、`actor_id`、`policy_decision`、`approval_digest`、`execution_id`。对写操作尤其要测试无效枚举、越权系统、参数漂移和重复提交。研究显示，完整类型上下文有助于减少无效调用，但它不能替代服务端参数校验。

### 5.3 Browser Agent / 安全治理：外部内容不是审批
网页、文件、工具响应可能包含与用户目标无关的指令。浏览器代理即使找到了可调用按钮，也不等于获得操作授权。对高风险行为保留人工确认、执行前参数快照、外部来源标记与独立审计。

**本周最值得体验：** 不接真实云资源，在Dify里把“创建测试任务”拆成 `PREVIEW → APPROVED → EXECUTED` 三个状态，用Java Mock验证Agent无法直接从预览跳到执行。

**Agent 实践启发：** 让模型做不确定的语义工作，让确定性系统掌控权限、顺序、幂等与审计。

## 7. 企业实践

## 9. 今日实战（1条）

### 用Java Mock验证“Agent无法绕过创建任务审批”

设计三段式能力：
```text
Dify / DeepSeek V4（意图与参数提取）
  -> POST /capabilities/task/preview    # 只生成预览与approval_digest
  -> 用户确认（服务端记录用户身份、摘要、有效期）
  -> POST /capabilities/task/execute    # 服务端验证授权/摘要/幂等键
  -> PostgreSQL                         # 事务写入与审计
  -> GET /capabilities/task/{id}        # 独立回读
```

请求示例（仅演示）：
```json
{
  "request_id": "demo-20261030-01",
  "capability_id": "create_test_task",
  "system_id": "SYS-DEMO",
  "task_name": "回归测试",
  "approval_digest": "sha256:mock-only",
  "idempotency_key": "task-demo-001"
}
```

服务端至少检查：当前登录身份、系统权限、参数白名单、摘要与预览一致、审批未过期、幂等键未使用；拒绝场景不落库。摘要必须由服务端按规范化参数计算，不能直接信任模型传入的字符串。

## 10. Today Worth Thinking

> 如果Agent成功调用了一个“创建任务”工具，但跳过了应有的审批环节，这算成功吗？

答案应该分层：工具调用成功、业务目标达成、权限合规和流程合规是四个独立指标。业务成功不抵消流程违规。建议定义 `VerifiedTaskSuccess = business_ok AND authorized AND process_compliant AND evidence_complete`。

## 11. 30分钟 Action

**任务：做一张“审批与执行一致性”六用例回归表。**

| Case | 场景 | 预期 |
|---|---|---|
| P01 | 只预览，未确认就执行 | DENY_APPROVAL |

| P04 | 相同幂等键重复提交 | 仅创建一条 |

## 13. 我的备注：金融测试、Agent Testing与智能测试平台

### 测试经理智能助手
一期继续使用 **Vue3独立前端 + iframe、Dify Chatflow、DeepSeek V4、Spring Boot/MyBatis-Plus、PostgreSQL**。执行统计和负责人查询保持只读，优先完善Golden Set、权限范围和事实时间戳。后续若增加任务创建，按本期三段式审批设计，而不是让模型直接写数据库。Mistral Large 4仅进入候选评估清单，先审许可和内网硬件可行性。

### 日志脱敏检测平台
继续扫描/失败重扫本身就是固定状态机：`request → authorize → select_servers → new_execution_epoch → scan → aggregate → verify`。Server作为事实来源，Report聚合不直接相信回调顺序；通过 `execution_epoch + event_id` 隔离迟到/重复回调。AI精筛只辅助判定，人工复核与同条件复扫才构成风险关闭证据。

### Agent Testing建议指标

| 指标 | 计算/验证要点 |
|---|---|
| Process Compliance | 必经审批、校验步骤是否全部执行 |
| Approval-to-Execution Match | 真实执行参数是否匹配已批准快照 |
| Tool Schema Validity | 参数字段、类型、枚举、顺序是否有效 |
| Side-effect Idempotency | 重试或重复回调是否造成重复写入 |
| Evidence Completeness | 审计、回读和事实来源是否齐全 |
| Cost per Verified Task | 总成本 / 独立验收通过任务数 |

**今日结论：Agent可以越来越自主地选择工具，但金融业务流程必须保持可控、可复现、可拒绝、可追溯。**
