## 2. AI / 大模型 Top News（4条）

### 2.1 Codex Ultrafast：内部事故调查从小时级走向分钟级

- **主体/日期：** OpenAI，2026-10-26；**新颖度：5/5（新公开内部实践）**。
- **官方来源：** [How Ultrafast cut incident investigation from hours to minutes at OpenAI](https://openai.com/index/openai-cut-incident-investigation/)。
- **核心事实：** OpenAI称Ultrafast是Codex的一种高速模式；内部工程师在事故响应中并行查阅日志、Slack上下文与变更线索。一位安全架构师表示，过去整理结构化与非结构化证据需1—2小时，现在约10—15分钟；另有员工表示多数交互能在30秒内响应。
- **边界：** 这是OpenAI内部案例与受访者陈述；没有公开跨组织的P95延迟、误判率或成本对照，不应写成公开版全面GA或普遍性能保证。
- **工程价值：** 对日志脱敏检测平台可借鉴“故障线索并行收集—结构化摘要—人工复核”，尤其要保留源日志位置、服务器、任务轮次和证据时间戳。**速度提升必须与定位准确率一起评估。**

### 2.2 CodeRabbit Secure：跨仓库安全审查与隔离验证

- **主体/日期：** OpenAI / CodeRabbit，2026-10-26；**新颖度：5/5（新披露企业能力实践）**。
- **官方来源：** [GPT-6.1 Sol helps CodeRabbit strengthen security across complex codebases](https://openai.com/index/gpt-6-1-sol-coderabbit-code-security/)。
- **核心事实：** CodeRabbit在其安全Agent中使用GPT-6.1 Sol作为主要模型，结合其他模型与安全工具，检查PR之外的共享库、依赖、认证模块和跨仓库影响。对用户选定的风险可尝试在隔离沙箱复现，生成待审核修复PR。
- **边界：** 厂商没有给出可独立复核的总体漏洞召回率、误报率或修复成功率；跨仓库分析依赖权限、索引完整性和代码上下文。
- **测试启发：** 同一PR应分别验证代码审查发现、跨仓库影响、隔离复现、修复回归与人工审批。AI审查应独立于AI编写代码的Agent，避免同源自评。

### 2.3 OpenAI Signals：公开工作任务使用结构化数据

- **主体/日期：** OpenAI Economic Research，2026-10-26；**新颖度：5/5（新数据集与分析口径）**。
- **官方来源：** [ChatGPT’s expanding world of work](https://openai.com/index/chatgpt-expanding-world-of-work/)；[Signals数据入口](https://openai.com/signals/data/)。
- **核心事实：** 新数据映射165类Intermediate Work Activities（IWA），覆盖近100个国家，按季度展示2025Q1至2026Q3工作用途。持续可比的74个国家中，最常见10类活动的平均占比由2025Q1的56.0%降至2026Q3的51.1%。
- **边界：** 数据基于个人ChatGPT账户的消息分类，**不含企业账户和Codex**；公开数据经过隐私处理、阈值抑制与统计噪声，不可直接当作企业AI生产率或岗位替代率。
- **实践价值：** 给企业AI项目设定“任务分类口径”提供参考：将执行统计、负责人查询、故障分析、报告生成分开计量，不以总会话量衡量价值。

### 2.4 AWS Continuum正式GA：从漏洞清单走向可验证修复PR

- **主体/日期：** AWS，2026-10-22；**新颖度：5/5（独立产品GA，7天窗口内）**。
- **官方来源：** [AWS Continuum GA公告](https://aws.amazon.com/blogs/aws/aws-continuum-for-code-vulnerabilities-is-now-generally-available/)；[What's New](https://aws.amazon.com/about-aws/whats-new/2026/10/aws-continuum-for-code-vulnerabilities-is-now-generally-available/)。
- **核心事实：** 服务从代码仓库和AWS资源拓扑、身份、网络可达性建立上下文图；对可复现发现使用隔离沙箱验证，并给出攻击路径、影响范围和修复PR。
- **发布状态与约束：** 2026-10-22 GA，首批在美国东部（弗吉尼亚北部）和美国西部（俄勒冈）可用。当前修复需要人员审核合并；未来有条件自主执行属于后续能力，不应写成当前默认自动修复。
- **实践价值：** 银行安全平台可借鉴“发现→证据等级→业务影响→隔离验证→修复PR→回归→人工关闭”流程，不必照搬其云服务。

## 5. Agent Ecosystem（3条）

### 5.1 Tool Calling / 安全治理：修复建议不能跳过独立验证

CodeRabbit与AWS Continuum均体现“发现→隔离复现→修复建议→人工批准”路径。**Agent选择工具与生成PR不是批准上线。** 服务端应固定权限、记录PR关联Finding ID、验证版本与环境，避免把模型结论当作安全证明。

### 5.2 Skill / MCP / Harness：成本评估需要绑定任务与执行环境

[AWS 10月21日Tokenomics文章](https://aws.amazon.com/blogs/aws-cloud-financial-management/tokenomics-for-coding-agents-benchmark-cost-and-quality-on-your-own-code/)提出同时比较模型、Harness和托管路径。其示例在21项任务上，按任务路由的总成本比全部使用最高端模型低44.7%，平均质量评分低4.8%；**这仅是其样本结果，不能外推。** 配套开源项目提供 `swe-router` Skill，依据已测任务表现给出模型建议，而不是自行替换用户模型。MCP工具描述、Skill版本、模型版本、上下文预算与成本应共同入账。

### 5.3 Browser Agent / Workflow：真实UI回归补足静态代码审查

[Greptile 10月26日案例](https://openai.com/index/greptile-code-review-codex-astra/)展示使用GPT-6 Astra的Computer Use，在PR开发环境中调整手机视口、模拟操作并发现静态审查不易识别的隐藏按钮。对于Vue3 iframe助手，应同时测试展开/收起、视口缩放、权限失败提示、超时重试和表格溢出。浏览器操作必须使用测试环境与测试账号。

**本周最值得体验：** 用3个固定业务用例比较“Dify单次分类+受控Java API”和“Dify多次工具推理”的耗时、工具次数、准确率与成本；不要只比较Token。

**Agent 实践启发：** 以 `task_id + trace_id + model_version + workflow_version + tool_manifest_hash + verification_result` 形成最小执行证据，能将“答案对了”与“过程合规、成本合理”分开。

## 7. 企业实践

### Greptile：把PR验证扩展到真实用户工作流

**披露日期：2026-10-26。** [OpenAI × Greptile官方案例](https://openai.com/index/greptile-code-review-codex-astra/)介绍Greptile将代码知识库通过MCP供Codex读取，并使用GPT-6 Astra的浏览器操作能力验证真实页面行为，例如手机视口下按钮被遮挡。其团队将AI代码的回滚频率作为长期质量信号之一。

**做法：** 代码审查与UI行为测试组合；让Agent理解代码库约定，结合真实页面验证，而不是只读Diff。

**效果：** 官方披露其知识库已接入大量客户，并表示更充分的上下文与较少回滚有关；**未提供可独立核验的统一回滚改善百分比**，本期不编造效果数字。

**可借鉴点：** 测试经理智能助手上线前，除接口返回正确外，需检查iframe真实可见性、交互、权限提示与页面恢复。建立“缺陷定位—复现视频/截图—代码位置—回归结果”的证据链。

## 10. Today Worth Thinking

> 如果Agent用10秒完成一个错误答案，另一个用40秒完成正确且有证据的答案，哪个“效率更高”？

建议以 `每个验证通过且合规的任务成本` 为主要指标，结合P95延迟、失败重试率与人工复核成本。速度本身不是质量。

## 11. 30分钟 Action

**今天完成一个小规模“工具选择与质量成本”基线。**

| 时间 | 操作 | 产物 |
|---|---|---|
| 0—10分钟 | 固定3个用例：执行量查询、负责人查询、无权限系统查询 | Golden Set v0.1 |

## 13. 我的备注：金融测试、Agent Testing与智能测试平台

### 测试经理智能助手

- **一期不换架构：** 仍以Dify编排、DeepSeek V4意图识别、Java权限和实时SQL查询为主；先稳定执行统计与系统负责人查询，再扩展。
- **下一步：** 将Golden Set拆成意图正确、工具正确、权限正确、事实正确、UI可见五项；在iframe环境测试手机/小窗口、会话恢复、错误提示与表格渲染。
- **价值指标：** 以“验证通过的业务任务数、人工节省时间、单成功任务成本”替代单纯会话量。

### 日志脱敏检测平台

- 将“规则扫描结果、AI精筛结果、人工复核、修复验证”分开；AI误判判断不得直接关闭高风险发现。
- 继续扫描/失败重扫必须依赖 `execution_epoch`、`event_id` 和状态机校验；旧轮次或重复回调不得覆盖当前Server事实状态。
- 借鉴Continuum的证据等级：正则命中、上下文语义判断、独立复测与人工确认分别记录，不混为“已证明风险”。

### Agent Testing建议指标

| 指标 | 定义 | 门禁建议 |
|---|---|---|
| Verified Task Success | 通过事实和权限双重验证的任务比例 | 不以模型自评为准 |
| Time to Evidence | 从提问到可核验证据的耗时 | 记录P50/P95 |
| Tool Path Compliance | 工具调用与权限契约符合比例 | 越权零容忍 |
| Cost per Verified Task | 总成本/通过验证任务数 | 任务集与模型版本固定 |
| UI Regression Fidelity | 浏览器执行结果与预期交互一致率 | iframe真实视口回归 |
| Finding Closure Evidence | 风险关闭是否附独立复测证据 | 无证据不得自动关闭 |

**今日结论：** 让Agent更快之前，先定义什么是“有证据的正确完成”；让Agent自动修复之前，先确保权限、沙箱、复测和人工批准能形成闭环。
