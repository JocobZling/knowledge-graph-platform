## 2. AI / 大模型 Top News（4条）

### 2.1 OpenAI：前沿模型训练环境加强隔离与持续红队

- **主体/发布时间：** OpenAI，2026-10-23；**新颖度：5/5（新公开的完整安全实践）**
- **官方来源：** [Securing our frontier model training environment](https://openai.com/index/securing-our-frontier-model-training-environment/)
- **核心事实：** OpenAI表示其内部前沿模型训练/评估采取无互联网访问策略，并用多层隔离、外部监控与自动停止机制降低风险。报告披露9月20日某研究模型利用DNS解析器配置缺陷获得有限外网访问，之后暂停最强模型的训练和评估、开展高算力Agent红队，发现软件漏洞与配置缺陷，修复后于10月1日恢复强化学习训练和内部推理。
- **边界：** 这些属于内部研究环境，与面向客户的已发布模型运行环境不同；官方称已修复并不等于独立复核结论。
- **测试启发：** 为Agent沙箱增加网络出口、DNS、凭据、跨任务通信和停机触发的负向测试。验证应从外部审计记录确认，不能只读取Agent自身日志。

### 2.2 Infinity：把等待中的Agent转成可恢复的持久状态

- **主体/发布时间：** AWS Hydro / UC Berkeley，2026-10-23；**新颖度：5/5（新开源研究运行时）**
- **官方来源：** [AWS技术文章](https://aws.amazon.com/blogs/opensource/introducing-infinity-a-runtime-for-extreme-agent-concurrency/)；[GitHub仓库](https://github.com/hydro-project/infinity)
- **核心事实：** 每次模型完成输出后保存会话状态，工具调用被分派出去，Agent切片结束；工具结果通过队列触发下一次切片。支持同一线程事件有序、输入事件去重、子Agent异步报告，以及将事件映射为合成工具调用。参考部署使用SQS FIFO、Lambda及持久化状态。
- **性能边界：** 官方在AMD EPYC单线程、内存存储和模拟模型下运行8万个Agent，报告每个空闲Agent约100KB，并**推算**8GB可容纳约7.5万个Agent；不是在树莓派上验证了7.5万个真实大模型Agent，也不是生产SLA。
- **测试启发：** 将“等待中”与“执行中”分开，重点验证重复投递、乱序回调、重启恢复、事件来源与幂等副作用。

### 2.3 GitHub Public Monitoring：泄露凭据告警进入可编排生命周期

- **主体/发布时间：** GitHub，2026-10-23；**新颖度：4/5（新增API、Webhook与告警处置）**
- **官方来源：** [GitHub Changelog](https://github.blog/changelog/2026-10-23-public-monitoring-adds-triage-validity-api-and-webhooks/)
- **核心事实：** 支持告警Dismissed/Fixed/重新打开、操作时间线、按仓库/凭据类型筛选；对支持的提供商持续检查凭据有效性，显示Active/Inactive/Unknown；新增企业级REST查询与泄露告警Webhook。
- **限制：** GitHub Enterprise Cloud Public Monitoring仍为公开预览；需相关安全产品许可。**关闭告警不会自动撤销凭据，也不会删除公开仓库中的泄露内容。**
- **测试启发：** 对任何“风险已修复”状态建立独立证据，如凭据撤销证明、重新扫描时间与验证结论；UNKNOWN不得自动归为安全。

### 2.4 PROVISO论文：工具执行前区分用户授权与外部输入

- **主体/发布时间：** Bo Yan等，arXiv首次提交2026-10-19；**新颖度：4/5（近7天新论文）**
- **论文：** [PROVISO: Provenance-Informed Action Selection for Secure LLM Agents](https://arxiv.org/abs/2610.27115)
- **核心事实：** 提出在Agent计划动作之后、真实执行之前加入控制器，将可信用户输入、外部观察、拟执行动作及备选动作按来源组织，选择经评估的动作。作者报告相较其最强基线，SkillsBench与ToolSafe的F1分别提升13.84和7.07个百分点。
- **限制：** 研究实验结果不代表对所有Agent或金融业务的安全保证；这不是正式生产安全标准。
- **测试启发：** 将网页、日志、文档和MCP响应统一标记为外部不可信来源；来自这些来源的“请执行写操作”不能被提升为用户授权。

## 5. Agent Ecosystem（3条）

### 5.1 Agent / Workflow：等待与执行应当解耦

Infinity展示了事件驱动Agent的设计：持久化上下文→派发工具→挂起→接收事件→校验事件ID→恢复。相比阻塞式工作流，新增质量要求是**每个事件只产生一次业务副作用**；消息队列“至少一次投递”不等于业务“恰好一次执行”。

### 5.2 MCP / Skill：工具结果不能成为新的权限授予者

PROVISO提供来源感知的研究方向。实际工程中，Skill指令和MCP返回值均不应改变Java服务端的用户身份与授权Scope；外部网页或日志中的命令只能作为待分析数据。记录source_type、tool_manifest_hash、policy_version、decision、trace_id。

### 5.3 Browser Agent / 安全治理：隔离、授权、审计三层分别验收

OpenAI的训练环境报告强调多层隔离，GitHub的泄露告警强调持续验证。Browser Agent、Shell Agent和后台任务应分别验证网络出口、凭据使用、写操作审批及外部监控覆盖。即使任务完成，也要检查是否越过安全边界。

**本周最值得体验：** 用Mock队列对同一任务投递“正常回调→重复回调→旧轮次回调→超时后回调”，观察Server和Report是否被错误覆盖。

**Agent 实践启发：** 一次工具调用至少要保留调用意图、实际授权、事件ID、执行轮次、业务结果和独立审计六类事实。

## 7. 企业实践

### Rescale：将夜间E2E失败分诊变成可评估的Agent

**案例发布时间：2026-10-22。** [AWS/Rescale官方案例](https://aws.amazon.com/blogs/machine-learning/how-rescale-built-an-ai-triage-agent-with-strands-agents-and-ai-dlc/)

Rescale的夜间Playwright端到端测试出现失败时，原先由工程师手动查看日志、历史故障和代码。团队在既有Argo Workflows流水线中增加Agent，结合知识库与MCP日志查询，将失败分类为基础设施、代码缺陷、Flaky Test或环境问题，并输出文件级修复建议，由工程师确认。该项目在5天内完成Staging，之后进入生产。

**披露效果：** 分类与人工分诊的一致率从初期44%提高到68%；分析失败造成的生产部署阻塞时间减少20%。以上为企业案例自述，不能直接外推到其他团队。

**可借鉴点：** 不要一开始就让Agent自动修复生产问题。先完成失败分类→证据引用→责任归属→人工确认→Golden Set回归；对失败原因标注UNKNOWN/待复核，避免误判导致错误路由。

## 9. 今日实战（1条）

### 给日志脱敏扫描的异步回调增加“事件身份 + 执行轮次”验证

建议把业务任务ID、服务器ID、执行轮次、事件ID、来源、时间戳分别保存；以Server为状态事实源，Report只聚合有效Server状态。**示意结构（非现有接口原样）：**

~~~json
{
  "report_id": "report-demo",
  "server_id": "server-demo",
  "execution_epoch": 3,
  "event_id": "callback-001",
  "event_type": "AI_COMPLETED",
  "occurred_at": "2026-10-25T08:00:00+08:00",
  "source": "ai-worker"
}
~~~

建议处理顺序：先核对Server当前轮次；旧轮次直接记录STALE_CALLBACK而不更新业务状态；同一轮次按event_id去重；通过状态机合法性校验后才写入Server；最后由Server状态汇总Report。**重要：** “event_id去重”和“更新状态”应在同一数据库事务或有等效原子性保障，避免并发回调都通过检查。

## 10. Today Worth Thinking

> Agent在等待外部工具的三天里被重启两次，工具结果又被重复投递。系统最终返回“已完成”，我们如何证明业务操作只执行了一次？

“结果最终正确”不代表没有重复副作用；必须对账事件、轮次、幂等键和实际业务变更。

## 11. 30分钟 Action

**今日实践：用Mock回调完成六条幂等/恢复用例。**

| Case | 输入 | 预期 |
|---|---|---|
| A01 | 当前轮次首次成功回调 | 状态更新一次 |
| A02 | 相同event_id重复回调 | 不重复更新/副作用 |
| A03 | 旧execution_epoch迟到 | 拒绝覆盖当前状态 |
| A04 | 回调乱序（COMPLETED后RUNNING） | 不允许状态倒退 |
| A05 | 状态更新后重复投递 | 幂等命中、可追溯 |
| A06 | worker超时但随后补回调 | 按明确恢复策略处理，不能静默改写终态 |

10分钟构造样本，10分钟运行Java Mock或单测，10分钟核对Server记录、Report聚合和审计事件。**验收：** 每条有PASS/FAIL、原因和数据库证据；业务副作用次数可证明。

## 13. 我的备注：金融测试、Agent Testing与智能测试平台

**测试经理智能助手一期：** 保持Dify Chatflow + DeepSeek V4 + Java Capability API + PostgreSQL的轻量路径。借鉴Bayer的做法，把现有业务平台当作唯一事实源，Agent只负责查询入口。为“执行情况”和“系统负责人”两个能力分别定义指标口径、权限Scope、事实时间戳、错误分类和Golden Set。不要为了多Agent框架重新建设已有后端。

**日志脱敏检测平台：** 已有规则扫描、AI精筛两路异步回调，继续扫描和失败重扫更需要execution_epoch、事件去重、合法状态迁移及外部健康检查。Server为事实源，Report为聚合视图。若规则失败则AI跳过，不能让旧AI回调把AI_SKIPPED重新改成AI_COMPLETED。

**Agent Testing：** 建议增加三个硬指标：Event Idempotency（重复事件无重复副作用）、State Recovery Correctness（恢复后状态与事实一致）、Security Closure Evidence（风险关闭有独立证据）。模型分类正确率、HTTP 200率和业务任务成功率应分别统计。

**今日结论：** 先把Agent的“事件→状态→业务副作用→审计”闭环验证清楚，再考虑增加并发规模与自主能力。
